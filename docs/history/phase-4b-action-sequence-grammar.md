> Part of the [Transflux roadmap](../../todo.md). Shipped inside v0.4.0, interrupting Phase 4, which resumes now; kept verbatim as the record of what landed. Design: [one grammar for declaring a sequence of actions](../design/action-sequence-grammar.md).

## Phase 4b: Action Sequence Grammar (v0.4.0, with Phase 4)
*Target: every position that holds an ordered list of actions — a declarative container, a conditional branch, a conditional's default branch — admits the same member grammar, declared once on a self-typed `ActionSequence<T, C, SELF>` base. A branch member may carry a mapper, be forked, or declare a conditional inline; a container member may declare a sequence inline; a forked member may be declared inline; a transition may attach a conditional inline. Additive: every call shape that compiles today still compiles, and nothing on `TransitionResult`, the paths, or the compensation stack changes shape.*

> **What the phase actually did, where it left the target behind.** The additive promise held through §4b.4 and then stopped: §4b.5 removed the `Identifiable` overload family and `OperationDef.usingContext`, §4b.5.1 removed every class form, and §4b.5.3 made a transition's body a sequence rather than a slot — which added a fourth position the target does not name, and narrowed what builds, since a transition's members claim ids in the state-machine-wide table where an attached action claimed none. Two defects were found and fixed on the way (§4b.2's cycle detector missing a branch's by-id edge, §4b.5.2's one context rule answering two questions). The one target item that landed as written is §4b.6, where the runtime turned out to need no change at all.*

### 4b.1 Branches carry bound members
*The one step with runtime risk, landed alone and behaviour-neutral: no DSL change, no new member forms, no new logging. One existing spec changed — see the last item.*
- [x] `ResolvedBranch(branchId, condition, List<String> stepIds)` becomes a branch holding the same resolved member records a container holds — `CompositeMember`, promoted out of `OperationDefImpl` to a top-level record in `core.impl` carrying the dispatch both positions now share, and resolved at build time by the same `ActionRef.resolve` + `MapperRef.resolve` pair `OperationDefImpl.buildBound` runs.
- [x] The conditional's executor dispatches the selected branch's members through `CompositeMember.dispatch`, the same call the container makes, so a branch member reaches `ExecutingTransitionImpl.runAction` through the path every other member already takes. Path qualification, compensation capture, nesting and listener notification stay where they are; the conditional owns nothing of its own beyond branch selection and the no-match policy.
- [x] `BranchDefImpl` / `DefaultBranchDefImpl` already held `ActionRef` lists — what changed is that the conditional stops flattening them to ids. **Building a conditional now takes two passes**: `buildBoundAction(conditionRegistry)` keeps its position in `InlineRegistrationSink` (shape validation, branch conditions, the `BoundAction` that goes into the enclosing scope), and a new `bindBranchMembers(...)` fills in the members afterwards. They cannot be one pass: the bound action must be in the scope before its own members resolve, because a sibling member may reference the conditional by id and such a reference captures the bound action by value.
- [x] `StateMachineDefImpl.validateBranchRefs` did **not** fold into `checkRefs` — that was impossible, since `checkRefs` runs before construction and the scopes it would need do not exist yet. It was **subsumed by binding**, which is strictly stronger: an unknown or wrong-kind branch id now throws out of `ActionRef.resolve`, with the sibling-scope enrichment `checkRefsResolvable` never had. The walk survives as `bindConditionalBranchMembers`, invoked from `StateMachineImpl`'s constructor after every container is built and before `flatten()`. It stays a pass of its own rather than moving into `buildBound`, because containers are registered into the root registry as they are built — binding inside `buildBound` would stop a branch from referencing a container declared after its own.
- [x] Specs: every conditional, compensation, listener and path spec passes unchanged. **One exception**, deliberate: `StateMachineDefImplBuildLoggingSpec`'s phase list drops to three, since the build phase that announced the deleted validation pass went with it. Three cases added — a branch referencing a later-declared container (the regression pin for the paragraph above), a branch member's declared compensation receiving the mapped child context its branch ran against, and a branch member naming an id registered as a condition.

### 4b.2 `ActionSequence<T, C, SELF>`
*The invariant, expressed once. Self-typed so a generic helper — the Phase 5 YAML mapper first of all — keeps the concrete chain type: `<S extends ActionSequence<T, C, S>> void fill(S sequence)`.*
- [x] `ActionSequence<T, C, SELF extends ActionSequence<T, C, SELF>>` in `core.action`, carrying the full member grammar: `run` (7 overloads), `fork` (7), `step` (6: instance, class, configurer, each with its `Identifiable` sibling), `conditional` (2), and `operation` (2, from §4b.3). No `Def` suffix — it is a grammar mixin with no identity, like `ContextScope`.
- [x] `OperationDef<T, C> extends ActionDef<T, C>, ActionSequence<T, C, OperationDef<T, C>>`; `BranchDef<T, C> extends ActionSequence<T, C, BranchDef<T, C>>`; `DefaultBranchDef<T, C> extends ActionSequence<T, C, DefaultBranchDef<T, C>>`. The per-subtype member declarations go; what stays on `BranchDef` is `condition(...)`, and on `OperationDef` the action-level surface (`usingContext`, compensation, routes, listeners). JavaDoc for each member form lives on the base, once.
- [x] Branch and default-branch members gain the call-site mapper — the `run(id, mapperId)` / `run(id, inlineMapper)` / `run(id, Identifiable mapper)` forms and their siblings — with the same `checkRefs` context-compatibility check a container member gets, descending through `ActionRef.Conditional` into each branch.
- [x] Branch and default-branch members gain `fork(...)` in all seven forms, with the same per-member forkability warning §4.3.1 emits for a container member.
- [x] Branch and default-branch members may declare a `conditional(...)` inline — recursion. The nested conditional registers into the enclosing container's scope like every other inline member; ids stay globally unique, and the definition is a finite tree by construction, so no new cycle case.
- [x] `definitionForks()` descends through conditionals, branches and (from §4b.3) nested containers instead of stopping at state-machine-level and transition-attached containers. Without this a definition that forks only from inside a branch never gets an executor.
- [x] **The cycle detector descends through conditionals and branches.** `getByIdReferenceIds()` walked one container's own member list, so a cycle closed by a branch's `run("some-container")` was invisible at build time and recursed without bound at execution. Not in this section's original list, and fixed here rather than later because everything after it widens what a branch may hold. The descent is one walk — `ActionSequenceSink.visitAllMembers` over `ActionRef.visitNestedMembers` — shared with `declaresFork()`; it terminates by construction, since inline nesting is literal source and a by-id edge is deliberately not followed. **This narrows what builds**: a container whose conditional recurses by id from one branch while another branch terminates it used to build and run, and is now rejected as a cycle. That is the intended reading — the detector cannot see which branch is selectable, so it cannot tell a base case from an unbounded recursion, and the direct form (a container referencing itself) was already rejected. Closing the branch route makes the two agree rather than leaving recursion expressible only through a conditional.
- [x] `ActionSequenceSpec`: reflects over `OperationDef`, `BranchDef` and `DefaultBranchDef` and asserts that the set of member-grammar methods — name, parameter types, and return type equal to the declaring subtype — is identical across the three. This is the test nothing else replaces.
- [x] `JavaDslSurface` gains every new call shape on a branch and a default branch — each mapper form, each fork form, an inline conditional inside a branch — and `JavaDslSurfaceSpec` drives them. Groovy alone would not catch an overload that stopped resolving.
- [x] Specs: `StateMachineImplForkSpec` gains a forked branch member (runs on another thread, appears on neither path, listener sees it under `conditional/branch-member`); `StateMachineImplForkCompensationSpec` gains a forked branch member's own stack; a mapped branch member's compensation receives the mapped context; a nested conditional reports `outer/inner/member` on `executedPath`.

### 4b.3 Inline sequence at a member position
*The cell the table in the design doc had empty, and what a forked inline group needs.*
- [x] `operation(String id, Consumer<OperationDef<T, C>> configurer)` and its `Identifiable` sibling on `ActionSequence`. The child is typed against the enclosing container's `C` and runs pass-through, like every inline declaration; `usingContext(...)` remains callable inside the configurer but cannot re-type: it returns `SELF`, so the only compilable argument is the enclosing type restated. The build-time boundary check (widen yes, narrow no) therefore only ever answers a caller that evaded javac — Groovy, raw types, or the Phase 5 YAML mapper. Giving an inline declaration a context of its own is §4b.5.
- [x] The inline container's `Registry` parents onto the enclosing container's registry, not the root, so its inline ids are visible only within its subtree and it can reach the enclosing container's inline ids — the same lexical rule an inline conditional follows today. `flatten()` at the end of construction still makes runtime resolution one lookup: it walks the whole ancestor chain, so a two-deep scope needs no ordering between a parent's flatten and a child's.
- [x] **Every container binds its members in a deferred pass.** An inline container cannot resolve its members while scopes are still being populated — there is no `StateMachineImpl` yet, and an SM-level callee may not be built — so `buildBound()` produces the bound action and `bindMembers(...)` fills in the members afterwards, exactly as a conditional already built in two passes. The two root forms moved onto the same schedule rather than keeping a second, eager one: a member may now name a container declared after its own wherever it sits, which is what a branch could already do.
- [x] `checkRefs` and the cycle detector descend into the inline container. An inline container cannot close a cycle by itself (it is literal source), but a by-id reference from inside it can, and the existing detector has to see the edge. The descent is free: `ActionRef.InlineOperation.visitNestedMembers` feeds the one walk `declaresFork()` and `getByIdReferenceIds()` already share.
- [x] Build-time validation names the nesting in its messages (`transition 't' > operation 'outer' > operation 'inner'`), since an inline id claimed twice at different depths is otherwise hard to find. Retrofitted to conditionals and branches too, so one convention covers every position; `defLabel()` stays flat, since the configurer guard names a def rather than a position.
- [x] `JavaDslSurface` gains an inline operation inside a container, inside a branch, and two deep; `JavaDslSurfaceSpec` drives them.
- [x] **The cycle detector's nodes are every dispatching action, not only the state-machine-level containers.** An inline container and a conditional are each registered under their id in the enclosing scope, so a sibling — or one of their own descendants — can name them, and a self-reference resolved and then recursed without bound at execution. Not in this section's original list, and fixed here because §4b.3 is what widens the exposure: recursion is what a nested container invites. The node table is collected once per build over both roots, the roots become every node in it (so a cycle buried under a transition-attached container is entered at all), and the edge lists stay over-approximate exactly as before. Only an id that **resolves** becomes a node: a transition-attached container is registered nowhere, so nothing can name it and it lies on no cycle — entering it would let its id answer for a same-named container's edges, which both rejects sound definitions and hides real cycles.
- [x] Specs: `OperationDefImplSpec` gains scope visibility for an inline container's ids (reachable from inside, rejected from a sibling); `StateMachineImplCompensationSpec` gains an inline container's additive compensation unwinding members-first inside its parent; an `executedPath` case at three levels. Also a container declared in a branch, the fork walk descending into an inline container, id collisions across the nesting boundary, and the context-boundary rejection.

### 4b.4 Transition slot accepts an inline conditional
*Independent of the rest; small.*
- [x] `TransitionDef.conditional(String id, Consumer<ConditionalOperationDef<T, C>> configurer)`, beside the existing `step(...)` and `operation(...)` attachment forms. The slot still takes no `fork` — nothing continues past it. No `Identifiable` sibling: §4b.5 removes that family, and adding one here would be adding it to delete it.
- [x] **`ConditionalOperationDefImpl` joins the sealed `ActionDefImpl` hierarchy** — the revisit `CLAUDE.md` deferred to exactly this point, since `attachAction` takes an `ActionDefImpl` and a wrapper is ruled out by `requirements.md` §3.4 ("neither form needs a wrapper to reach a position the other can occupy"). It is a net deletion: the 18 listener overloads, `getListeners`, `withCompensation` ×2, `forException` and the two sinks it hand-rolled *because* it could not inherit them all go. `declaresFork()` and the cycle detector's edge source become hooks, which also fixes a latent bug — `definitionForks()` asked `instanceof OperationDefImpl`, so an attached conditional whose branch forks would have built with no executor.
- [x] **A conditional owns its members' scope**, parented on the nearest enclosing one. Every branch reaches what any branch declares, so a step common to several is declared once, while a sibling of the conditional cannot reach in; previously only the first half held, since branch members registered into the enclosing container's scope. `ConditionalBranchExecutor` pushes that scope while dispatching, capturing it at construction so an earlier machine keeps the scope it was built with. The scope field and the flatten / collect / scan walks over it moved to `ActionDefImpl` and are written once — two forms own scopes now, and a hand-copied transitive descent is how three walks previously missed containers declared inside a branch.
- [x] `JavaDslSurface` and `JavaDslSurfaceSpec` gain the shape; specs cover attachment, path reporting (`route/branch-member`, with no synthetic level), the default-branch fall-through, the `NoMatchBehavior.ERROR` case failing the transition, branches sharing the attached conditional's scope, and a fork declared inside an attached conditional's branch still building a pool.

- [x] **A conditional registers at state-machine level too** — `StateMachineDef.conditional(id, Class<C>, cfg)` and its `forContext` sibling — closing the other half of the deferred decision, which `requirements.md` §3.4.3 already promised ("registered under `operations:` and referenced with `run:`") and the Phase 5 mapper needs. `smCompositeOperations` widens from `OperationDefImpl` to `ActionDefImpl`; every pass over it already went through a hook, so only the loop variables changed. It shares one namespace with steps, operations and conditions, and is a cycle node like any other registered action.

### 4b.5 API shape: identity, and where a context is declared
*Three linked breaking changes to the DSL surface, taken as one item because each rewrites `JavaDslSurface` and `ActionSequenceSpec`'s golden list — done separately, that happens three times. Pre-1.0, and the README already declares the API unstable. Lands **before** §4b.6, since the fork declaration verbs must mirror whatever shape this settles.*

- [x] **Drop the `Identifiable` overloads.** 191 declarations across the public API (672 counting impl overrides) exist only to take an enum where a `String` id is wanted. The safety they advertise is not delivered: `Identifiable` is a *single untyped* interface, so `run(MyStates.TRIAL)` compiles where an action id is expected, and what a host actually gets is scoped constants — which a `States` class of `static final String` already gives for free. The cost is ×2 on every one-id method and ×4 on every two-id method, which is where the surface explodes. The rule was already unenforceable in practice: **`run(Identifiable, ContextMapper)` and `fork(Identifiable, ContextMapper)` do not exist**, so an enum-tagged action id already cannot carry an inline mapper, and neither the stated parity rule nor `ActionSequenceSpec`'s golden list caught it. Call sites write `.getId()`. The `Identifiable` *interface* stays — every `*Def` implements it, and that is how a def reports its own id. Landed in three slices — the runtime firing surface, the action DSL, the definition DSL — since a partial removal compiles at each of those boundaries and the spec diff is otherwise one unreviewable change. `addEventTrigger(Identifiable event)` was the one member that was a capability rather than a sibling: it used its single argument as both trigger id and event id and had no String counterpart, so it became `addEventTrigger(String eventId)` rather than being deleted. `ConditionDescriptor.ref(Identifiable)` went with the rest.
- [x] **Drop `OperationDef.usingContext(Class<C>)`.** It returns `SELF` rather than a re-typed def, so inside `operation(id, cfg)` the only compilable argument is the enclosing `C` restated — it structurally cannot do what its name promises. The context-compatibility validation reads `componentContextTypes`, populated by the typed *registration* overload and never by this method. It was wired to slightly more than the binding DEBUG log tag this item claimed, though: it also fed the widen-yes/narrow-no check on a nested container, which only a caller that evaded javac could ever reach. Those two pins moved onto `operation(id, Class<N>, cfg)` rather than being deleted with the method. **`TransitionDef.usingContext` stays**: `<C2> TransitionDef<T, C2>` genuinely re-types, and a transition has one action slot, so the re-type cannot strand a member declared before it — an operation holds an ordered list, where it could. **`forContext(Class<C>, scope -> ...)` stays**: it types registrations, a different job that keeps its own verb.
- [x] **A context is declared where the action is declared**, in both DSLs. For a registered component that is the registration (`smd.operation(id, Class<C>, cfg)` ↔ YAML's `context:` key under `operations:`); for an inline one the call site *is* the declaration site, so both DSLs put context and mapper on the same entry and there is nothing to reconcile. Each inline declaration verb gains two shapes beside the inheriting one — distinct arities, no erasure hazard:
  ```java
  operation(String id, Consumer<OperationDef<T, C>> cfg);                                 // inherits C
  operation(String id, Class<N> ctx, Consumer<OperationDef<T, N>> cfg);                   // pass-through, N from C
  operation(String id, Class<N> ctx, ContextMapper<C, N> mapper, Consumer<...> cfg);      // mapped
  ```
  This also settles two things the current arrangement gets wrong for want of a place to say the context: a registered action's inline members are tagged `Object` in the binding log unless its configurer separately restates the type (true of a container today, and unfixable for a conditional, which has no `usingContext` at all), and the fork-boundary warning's `operationId=` key names whichever position owns the context rather than an operation. Answering "why can `run(id, mapper)` cross a context boundary when an inline declaration cannot?" — it now can. The runtime needs almost nothing: `ActionRef.InlineOperation` overrides `mapperRef()`, and `bindMembers` already resolves a `ResolvedContextMapping` for every member regardless of kind. With `Identifiable` gone this is 3 methods per verb, not 12 — and per *authoring form*, so `step` gains six (its instance, class and configurer forms each get the two new shapes) while `operation` and `conditional` gain two each: 21 methods on `ActionSequence`, up from 11 and down from the 24 it carried before the removal. §4b.5.1 later took the class forms out, leaving 18.

  This turned out to open a hole and close it in the same item. A by-id reference reads its callee's context from `componentContextTypes`, which only *registrations* write, so an inline id resolved to `Object` and was admitted whatever the contexts were. That was safe only while every action in a subtree necessarily shared one context — which is exactly what declaring a context ends, and both `run("x")` beside a mapped declaration and a reference out of a nested context to an enclosing member built clean and threw `ClassCastException` at execution. `collectInlineMemberContexts` now records each inline declaration's *effective* context before any reference is checked, as a pass of its own for the same reason member binding is: a reference may name an id declared after it. It cannot consult the lexical scopes instead, because those do not exist until construction.
- [x] **The fork-boundary warning names the position that owns the context.** The advice text had already been reworded when the conditional joined the action-def hierarchy, so only the `operationId=` key was outstanding — it named whichever container held the member, which is not who declared the context being shared. It becomes `contextOwner=`, carrying a labelled position, updated wherever a declaration names the context its subtree actually runs against. Ownership turns on `declared == own` rather than "declared anything": a declaration naming `Object` runs pass-through, so its members are handed the enclosing context and the enclosing position is still what a host changes.
- [x] `JavaDslSurface` is rewritten against the reduced surface — it is the only check that the remaining overloads still resolve for a Java caller — and `ActionSequenceSpec`'s golden list shrinks to match. Every spec passing an enum to a DSL method moves to `.getId()`.
- [x] `CLAUDE.md`: the "**`Identifiable` overload parity**" rule goes, along with its two documented exceptions; the "`forContext` vs `usingContext`" paragraph narrows to transitions; the erasure and verb-count paragraphs drop the `Identifiable` term from their arithmetic. `requirements.md` §4.2.1 loses the enum-id example — §2.2.1 never carried one, so the pointer was wrong — and §4.3 and §2.2.10 lose the "every id-bearing form has an `Identifiable` sibling" sentence.

### 4b.5.1 Instance-only authoring
*Every host-implemented contract reaches the DSL as an instance or a configurer; the class form goes. Lands **before** §4b.6, since the fork declaration verbs mirror whatever `step` / `operation` / `conditional` settle on. Breaking, pre-1.0.*

The class form is `getDeclaredConstructor().newInstance()`, so the classes it accepts are exactly the ones that need no injection — it is sugar for `new X()` that fails at build rather than at compile, and it cannot express a dependency. Every story it was meant to serve is an instance already: a bean, a scoped proxy and a lambda all arrive that way, and a host wires them at the definition site by constructor injection. §2.1.2 had already told hosts not to build on the instantiation strategy. YAML keeps `class:` — a document cannot hold an object — and the Phase 5 mapper resolves it through a factory into the instance form, which is where container resolution belongs in any case.

- [x] **Action class forms.** `ActionSequence.step(id, Class)` and its two context-declaring shapes, `StateMachineDef.step` ×2, `ContextScope.step`, `TransitionDef.step`, `StepDef.using(Class)`. Internally this deletes an arm of the sealed `ActionRef` — `InlineClass`, with its factory and `InlineRegistrationSink.registerInlineActionClass` — plus `registerStepClass` and `ActionRegistration`'s class slot.
- [x] **Condition class forms, and `ConditionDescriptor.ClassBased` with them.** `StateMachineDef.condition` ×2, `ContextScope.condition`, `TransitionDef.preCondition` / `postCondition`, `BranchDef.condition`, `DataTriggerDef.condition`, `ManualTriggerDef.preCondition`. The descriptor grammar drops to four forms in Java; `ClassBased` stays a YAML serialization the Phase 5 factory resolves, so `permits` narrows and `ConditionResolver.resolveClassBased` goes.
- [x] **`conditionPredicate` / `conditionExpression` on `StateMachineDef` become `condition(...)`.** The documented reason for the distinguishing names — erasure against `condition(id, Class<? extends Condition<T, C>>)` — does not hold and never did: the two differ in arity, the five typed erasures are pairwise distinct, and `ContextScope` has been compiling every form under one `condition` name all along. Implicitly-typed lambdas separate on SAM arity, `Condition` taking three parameters where `BiPredicate` takes two and `Predicate` one. The single-argument `conditionExpression(String)` / `preConditionExpression(String)` on `TransitionDef`, `BranchDef` and the triggers **keep** their names — there `condition(String)` really is taken, by the reference-by-id form.
- [x] **Listener, compensation and mapper class forms.** The eight `StateMachineDef.onAny*`, `StateDef.onEntry` / `onExit`, `TransitionDef.onStart` / `onComplete` / `onError`, `ActionDef`'s three and their twelve covariant overrides, the three `*ListenerDef.using(Class)`; `withCompensation(Class)` on `ActionDef`, its three overrides and `CompensationRouteDef`; `StateMachineDef.mapper(id, P, N, Class)` and `MapperDef.using(Class)`. `EventTriggerDef.filter(Class)` goes with them: the contract is a `BiPredicate` rather than one of ours, but the pattern and the reflective instantiation are the same, and leaving it would keep the mechanism alive for one caller.
- [x] **The plumbing that existed only for it.** `InstanceOrClassSource` loses its class half and becomes `InstanceSource` — the warn-on-overwrite and the not-set rejection are still shared by seven owners. `ReflectionUtils` goes entirely, `instantiateNoArg` being its only member and now unreferenced. `claimCanonical` loses the branch that made the same class under the same id idempotent, no payload being a class any more. The "a class-form global listener is instantiated once rather than once per state" rationale on the three binding methods is vacuous once every listener is an instance.
- [x] **The Groovy hazard governs how this is verified.** Groovy resolves overloads at runtime, so a missed call site surfaces as a spec failure rather than a compile error, and `JavaDslSurface` — the one javac guard — never covered the listener, condition or mapper class forms. The full suite runs per slice, and the typed condition family gains its four lambda shapes in the fixture so the rename is pinned where it can fail early.
- [x] Specs: roughly 130 call sites across 35 files, of which ~40 features exist for class-form behaviour specifically and delete outright, along with ten `Ctorless*` fixtures, fourteen `'class'` rows in listener data tables, `ReflectionUtilsSpec`, and three golden entries in `ActionSequenceSpec` (21 → 18).
- [x] Documents: `requirements.md` §2.1.2, §2.2.1, §2.2.5, §2.2.9, §2.2.11, §2.2.12, §3.6.1, §4.1.1, §4.2.1, §4.2.2, §4.3, §4.4.1, §4.4.2, §4.5.1, §4.5.2, §4.6.2, §4.7.1, §4.7.2, §4.8.2 and §7.1 — the worked example in §4.4.2 is class-form throughout and is rewritten rather than patched. §4.1.3's `ComponentRegistry` **keeps** its class forms: resolving a class through a container is what that SPI is for, and it is unbuilt Phase 6 surface this decision was never about. `CLAUDE.md` loses the "Typed condition-registration names" paragraph, the instance-or-class asymmetry note, and the class arm of the mapper and step registration lines. Phase 5's "four authoring flavours" item marks the class flavour YAML-only.

### 4b.5.2 One rule, asked two questions
*A defect found while reviewing §4b.5.1, predating it. Independent of §4b.6, so it can land either side of it.*

- [x] **`subtreeContext` is asked what context a subtree runs against, and two different passes mean different things by it.** For a declaration naming `Object` and running pass-through, the runtime context *object* handed down is the enclosing one — which is what the fork-boundary warning needs, and what `ownerBeneath` documents. But the *type* its members are declared against is `Object`: javac types them from `OperationDef<T, Object>`, and `effectiveContext` tags the registry the same way. `collectMemberContexts` asks the second question and is handed the first answer, so an inline member of such a container is recorded against a context that appears nowhere in the definition, and a by-id reference into that subtree is checked against it.
- [x] The symptom is a false rejection that names a type the host never wrote — *"references action 'leaf' declared for context CtxA"* where the enclosing declaration said `Object` — and an asymmetry underneath it: the same dispatch written imperatively as `view.run("leaf")` builds and runs, because the registry tag it consults is the `Object` one. The member genuinely tolerates either context, so the declarative refusal is the wrong half.
- [x] The fix is to separate the two questions rather than to pick a winner: the fork warning keeps asking which object flows down, while the reference-checking and context-recording passes ask which type the declaration named. Whichever way it is spelled, the pass that records and the pass that tags must agree, since disagreement between them is the shape of this defect.
- [x] **Fold in the sibling oversight in the same commit.** §4b.5 changed the conditional-nested-in-a-conditional case to name the nested conditional as the owner of the scope its branches bind against; the identical case in `OperationDefImpl.bindMembers` — a conditional declared inside a container — still passed the container's id. The claim that this misnames a diagnostic turned out to be **unobservable**, and the one-line fix landed on symmetry alone: the id reaches `MapperRef.ById.resolve`'s message, which no member can trigger because `checkRefs` rejects an unknown mapper id first, and `ActionRef.unknownIdMessage`'s enrichment skip, which cannot suppress a true hit either way — both the container's scope and the conditional's are on the resolution chain, so an id held by either would have resolved. Worth keeping as the counterpart to a rule already stated, and as one less trap the next unchecked path would fall into.
- [x] **`ownerBeneath` had the same defect, found in review of this item.** Ownership turns on `declared == own`, which also fires when a declaration *restates* the enclosing context - intended for a real type, wrong for `Object`, and `Object` is the default a transition declaring no context gets. So `operation('inner', Object, ...)` under such a transition took ownership, and the fork warning advised declaring a context on `inner`, where declaring one unmapped is a build error: `boundaryIsLegal` computes `CtxX.isAssignableFrom(Object)`. `Object` now never takes ownership, since naming it says nothing about what flows. Diagnostic only; none of the four existing ownership cases move.
- [x] Specs: the declarative and imperative dispatches into an `Object`-declared container agree — one build-only pin for the reference the old rule rejected, one execution pin that both surfaces hand the same object; and `a nested container declaring Object does not take ownership` gains the `contextType=` half, which is what pins the fork warning to the flowing chain. The third case is **not written**: an unknown-mapper message inside a branch is unreachable, per the bullet above.

### 4b.5.3 A transition is a sequence
*The attachment slot is a one-element `ActionSequence` that grew a verb at a time - `run`, then `step`, then `operation`, then `conditional` (§4b.4) - until it carried the member grammar minus the length. Making it the real thing deletes the slot, and every recent argument about what may attach to a transition with it. Breaking, pre-1.0; lands **before** §4b.6 so the fork verbs are settled once, on one grammar, rather than landing at three positions and then being re-asked at a fourth.*

- [x] **`TransitionDef<T, C> extends ActionSequence<T, C, TransitionDef<T, C>>`.** The five attachment verbs go - `run(String)`, `step` ×2, `operation`, `conditional` - and the transition inherits the whole family, `fork` included. What a transition still has that an operation does not is everything *around* the body: source and target, pre- and post-conditions, triggers, the applier commit, and the state and transition listeners. That difference is real and stays; the body itself is an ordered member list like any other.
- [x] **Existing call shapes keep compiling and keep their paths.** `t.operation("op", c -> ...)` is now an inline operation member and reports `op`, `op/step` - what it reported as an attachment; `t.step("s", a)` reports `s`, as before; `t.run("shared")` reports `shared`, as before. The one behavioural change is that a second declaration **appends** rather than overwriting with a warning: `t.step("a", ...).step("b", ...)` runs both, in order, and the "Transition action overwritten" warning goes. `fork` at transition level - `t.step("commit", ...).fork("notify")` - is the commonest asynchronous shape there is and needed a wrapper operation until now; "nothing continues past the slot" was only ever true of a slot.
- [x] **No synthetic root.** The body is not an action: it has no id in the action namespace, no compensation of its own, and no action listeners, and it does not appear on `executedPath` or in any listener payload. A member's path starts at the member. Rooting at the transition id would repeat a fact `TransitionResult.transitionId` and every payload's `transition` already carry, and a synthetic action would keep the near-duplicate the action-listener invariants documented - the root action's `onStart` firing beside the transition's own. What goes is the *structural* guarantee of it: nothing now forces an action notification to follow the transition's `onStart`, though one still does when the first member happens to be declared there. A host that attached listeners or a compensation to the attached operation itself still has them: it is an inline operation now, and they ride on it as before. A whole-body compensation with no operation to hang it on is the one thing that becomes more verbose - wrap the body in `operation(...)` - and it is rare enough to leave there.
- [x] **`TransitionDef.usingContext` goes**, by the argument that removed `OperationDef.usingContext`: it survived §4b.5 because a one-slot transition could not strand a member declared before the re-type, and a sequence can. `transitionsTo(target, id, Class<C>, cfg)` already pre-binds the context, so nothing is lost; the pass-through `transitionsTo(target, id, cfg)` keeps defaulting to `Object`.
- [x] **Implementation: `TransitionDefImpl` owns its body as an anonymous `OperationDefImpl`** and delegates the grammar to it, so every pass `StateMachineDefImpl` already runs over `td.getActionDef()` - `checkRefs`, `collectMemberContexts`, `bindMembers`, `definitionForks`, the cycle nodes, the scope walks, `validateComponents` - keeps working with no change to its shape; the body's scope is parented on the root exactly as an attached container's was. What changes at runtime is the entry: `executeTransitionInternal` dispatches the body's `CompositeMember`s with the body's scope pushed instead of running one root action through `runRootAction`, and `BoundTransition` keeps its nullable `BoundAction`, now the body's - `null` when the transition declares no members, which is what lets every pass over `getActionDef()` keep the shape it had when a transition could carry no action. The by-id context-assignability check `TransitionDefImpl.buildBoundAction` performs for `run(id)` becomes the sequence's ordinary `checkRefs` pass-through check. The cycle detector's "an attached container is registered nowhere and so is never a node" reasoning transfers to the body unchanged - and closes a gap on the way, since an inline `operation("op")` declared on a transition is now registered in the body's scope and therefore *is* a node, where the attached container it replaces was not.
- [x] **Ids become unique at this position too, and that narrows what builds.** A transition's members go through `InlineRegistrationSink` like any others, so they claim their ids in the state-machine-wide canonical table where an attached action claimed none - `StepDefImpl.bindScope` is a no-op, so a step attached to a transition never reached the table at all. Three shapes that used to build are now rejected as duplicates: the same step id on two transitions (the likeliest of them in existing host code), a step or operation on a transition reusing a state-machine-level id, and `t.operation("op")` beside `smd.operation("op")`. Declaring the *same instance* under one id stays idempotent, as it is everywhere else. For the same reason an operation or conditional declared on a transition is now a cycle node, so `t.operation("op", o -> o.run("op"))` is rejected at build instead of recursing at execution. None of this was foreseen when the item was written; all of it is the id rules finally holding at a position that escaped them, rather than new rules. **A per-transition namespace was considered and rejected** - it would break global uniqueness to preserve a gap in it. Visibility stays lexical, as for any container: the body owns a scope, so its inline ids resolve only from inside its own subtree.
- [x] **`claimCanonical`'s message stops naming the same class twice.** Two declarations of one action type under one id - the common shape, and the one these rejections surface - produced *"already registered with payload 'X'; cannot re-register with 'X'"*, which reads as a framework fault rather than a duplicate id. It now says "a different X" in that case, and both branches carry the advice. Pre-existing weakness, newly on a path hosts will hit.
- [x] **`ActionSequenceSpec`'s `SEQUENCES` gains `TransitionDef`** - the golden list, "offers every member form" and "declares no member form of its own" all hold for four types. `JavaDslSurface` gains the transition-level shapes that were impossible before - two members in a row, and a `fork` beside a `step` - and drops `usingContext`; every existing fixture compiles unchanged. Specs: a two-member transition runs both in order; a forked transition member appears on neither path; `executedPath` for an inline operation on a transition is unchanged from the attachment form; a self-referencing `operation("op", o -> o.run("op"))` on a transition is rejected as a cycle; the listener specs that asserted the root action's near-duplicate notification are rewritten to assert its absence.
- [x] **Documents, in this item rather than §4b.7 where the change makes the text false:** `CLAUDE.md`'s "one execution path" paragraph drops "or the action attached to the transition itself"; the two listener-invariant paragraphs drop the near-duplicate; "the slot still takes no `fork`" and "the two positions that are *not* sequences" become one position, the dispatch from inside an action body; "`forContext` vs `usingContext`" narrows to `forContext` alone. `requirements.md` §4.4.1's "a transition that forks its whole action is a transition that does nothing" loses its premise and is rewritten. **YAML follows in Phase 5**: a transition's body is a single `action:` key today (§3, the `transitions:` examples) and becomes an `actions:` list, which gives the mapper one member-list grammar everywhere instead of a one-slot special case - noted there, not done here.

### 4b.6 Inline forked declarations
*Deferred from §4.3.2 with the name `forkStep` reserved; lands here because once the grammar is declared once, a declaration verb per authored form costs a handful of methods rather than thirty.*

**Decision: the full grammar ships.** A `forkOperation`-only surface was considered - it is the closed form, since a step, a conditional or a nested container all go inside one, which makes `forkStep` and `forkConditional` sugar over it at a cost of nine methods. It was rejected in favour of an exact mirror of the synchronous verbs, so the grammar needs no footnote about why the asynchronous half is narrower. The three `fork(...)` reference forms were never in question: wrapping a reference demands a second invented id, and the rewrite `forkOperation("x", op -> op.run("id", "mapper-id"))` would move `mapTo` from the submitting thread to the worker, which is the isolation §4.5.3.2 exists to provide. With §4b.5.3 landing first, every verb below is inherited at a transition position too.
- [x] `forkStep(...)` (6 overloads mirroring `step`), `forkOperation(...)` (3, mirroring `operation`) and `forkConditional(...)` (3, mirroring `conditional`) on `ActionSequence`, taking it from 18 methods to 30. They cannot be overloads of `fork` — an implicitly-typed lambda is applicable to `ContextMapper<C, ?>` and to `Consumer<StepDef<T, C>>` alike — so the `fork` prefix keeps the asynchronous surface together under autocomplete while the suffix names the form. Each mirrors its synchronous sibling's three context shapes, §4b.5 having put the context where the action is declared.
- [x] Runtime: the same `ActionRef` carrying the same fork flag beside it — which turned out to mean **no runtime change at all**. `DeclaredMember(ref, forked)` already carried the flag beside every variant, and every pass downstream of it is variant-agnostic: `bindMembers` builds a `CompositeMember` with `member.forked()` whatever the ref, `declaresFork()` ORs the flag over the whole source-nesting tree, `checkRefs` runs the §4.3.1 boundary check on `member.forked()` alone, and `CompositeMember.dispatch` never asks how the action was authored. What stood in the way was seven hard-coded `false`s in the sink's declaration verbs, where the reference verbs had threaded the flag through a shared helper all along; closing that asymmetry was the whole implementation. A declaration that names no mapper takes the context from `ForkableContext.fork()` or shares the reference, with the §4.3.1 warning applying per member; one that names a mapper gets its own context from it, exactly as `fork(id, mapper)` does, and `mapFrom` stays unreachable because a branch has no moment at which to write back.
- [x] `JavaDslSurface` gains every overload once at a container position, plus one per verb at a branch position and at a transition position - an inherited signature resolves identically wherever it is inherited, and `ActionSequenceSpec` forbids a subtype redeclaring one, so repeating all twelve at every position would catch nothing; `JavaDslSurfaceSpec` drives them; `StateMachineImplForkSpec` gains an inline forked step, an inline forked operation whose members run in order on the worker, and an inline forked conditional. `OperationDefImplForkSpec` gains a data-driven feature over all twelve shapes asserting each records a forked member - the pin that catches a copy-paste `false` in one delegate, which the golden list, the fixture and an execution spec that happens not to use that shape would all miss. Three additions were not in this list: `OperationDefImplForkValidationSpec` pins that an inline forked declaration draws the same §4.3.1 warning a forked reference does, and that a mapped one draws none, since that is the one behaviour this item relies on without touching; `StateMachineImplAsyncExecutorSpec` pins that a definition whose only fork is an inline declaration still builds a pool; and `JavaDslSurface`'s trail became a `CopyOnWriteArrayList`, a latent race that twelve concurrent branches would have turned into a flaky suite.

  **The `CLAUDE.md` verb paragraph moved here from §4b.7**, since shipping the verbs is what makes "reserved as `forkStep(...)`" and the 18-method arithmetic false. The eight verbs are a table now, which is what the count growing to 30 needed. One thing found while writing it and worth keeping: `OperationDefImpl` gained a `getMembers()` accessor for the twelve-shape pin, and Groovy resolves `.members` as a property, so four spec call sites reaching the sink's private field through `td.actionDef.members.members()` had to route through the accessor instead.
