## Phase 3: Triggers & Listeners (v0.3.0)
*Target: The 1.0 trigger set (Manual, Event, host-driven Data) and full listener parity between DSLs.*

### 3.1 Trigger Framework
- [x] `Trigger` interface and base implementations. (`core.trigger.Trigger` runtime view + `TriggerType`; triggers attach to transitions like pre/post-conditions rather than going through the `Component`/`Registry` machinery.)
- [x] Trigger registration and lookup on transitions. (`TransitionDef.addManualTrigger(...)`; ids are a per-state-machine namespace, uniqueness enforced at build.)
- [x] Trigger catalog API on the state machine — enumeration by id (`StateMachine.getTriggers()` / `getTrigger(id)`). **Kind-based discrimination ("by type") is deferred to 3.3**: with only manual triggers, a type filter is vacuous. When event/data triggers land it will be added class-based (`getTriggers(Class<? extends Trigger>)` with return-type narrowing) rather than via a parallel enum.

### 3.2 Manual Triggers
- [x] `ManualTrigger` implementation. (`ManualTriggerDef` builder + internal `ManualTriggerImpl` runtime.)
- [x] Per-trigger metadata: description, trigger-specific pre-conditions distinct from the transition's defaults. Trigger pre-conditions **augment** the transition's (transition's run first, then the trigger's). ~~**Listener bindings are deferred to 3.5**, where listeners are introduced.~~ **Closed in 3.5, delivered differently**: `TransitionExecution.firedBy()` exposes the firing trigger to any transition listener, which covers the "react only when *this* trigger fired" case without a per-trigger listener list.
- [x] Invocation API — shipped as a dedicated `stateMachine.entity(e).fire(triggerId[, ctx])` (no target-state arg; the trigger names its transition). `transitionTo(...)` stays trigger-free, so triggerless transitions remain directly invocable and absent from the catalog.

### 3.3 Event Triggers
- [x] `EventTrigger` implementation. (`core.trigger.EventTrigger` runtime view + `EventTriggerDef` def-side builder; internal `EventTriggerImpl` / `EventTriggerDefImpl`.)
- [x] `processEvent(event, eventData)` API on the entity binding. (`entity(e).processEvent(eventId, eventData[, ctx])`; returns `ProcessResult<T>` — `fired()` / `result()` / `firedTriggerId()`. `eventData` is bound only for filter evaluation; the firing context is a separate argument.)
- [x] Event filtering via expressions / predicate classes. (`filter(BiPredicate)` / `filter(Predicate)` / `filter(Class)` / `filterExpression(String)`; SpEL binds entity as root, payload as `#event`, context as `#context`.)
- [x] Entity correlation (matching events to entities) for the in-process case. (Host-driven: the host binds the entity via `entity(e)` and the framework matches the published event id + filter against that entity's eligible triggers — correlation is the host's choice of which entity to process.)
- [x] **Trigger kind discrimination (deferred from 3.1).** `<X extends Trigger> Collection<X> getTriggers(Class<X> kind)` with return-type narrowing; public `ManualTrigger` / `EventTrigger` / `DataTrigger` subtypes of `Trigger` are what the filter selects on. No runtime `TriggerType` enum.

### 3.4 Data Triggers (host-driven)
- [x] `DataTrigger` implementation. (`core.trigger.DataTrigger` runtime view + `DataTriggerDef` def-side builder; internal `DataTriggerImpl` / `DataTriggerDefImpl`.)
- [x] `processDataChange()` API — host-initiated re-evaluation only. (`entity(e).processDataChange([ctx])`; returns `ProcessResult<T>`. First eligible trigger whose gate holds fires.)
- [x] Data-trigger condition uses the standard Condition Descriptor grammar. (Reference / instance / class / predicate / expression, resolved via the shared `ConditionResolver`.)
- [x] Documented and tested non-goal: no field watching, no ORM hooks, no background polling (those are post-1.0). (`StateMachineImplDataDispatchSpec` asserts nothing fires until an explicit `processDataChange` call.)

### 3.5 Listeners
- [x] **State Listeners**
  - [x] `StateListener` interface (entry / exit). (One functional `onState(entity, context, change)` for both hooks, plus the `StateChange` payload record and its `StatePhase` discriminator — the phase is a field rather than a second interface so a globally-registered listener can tell the hooks apart. `StateListenerDef` is the def-side builder; ids are required and form their own SM-wide namespace, outside `Registry` / `Component`, per the trigger precedent.)
  - [x] Per-state and global registration. (`StateDef.onEntry` / `onExit` and `StateMachineDef.onAnyStateEntry` / `onAnyStateExit`, each in instance / class / configurer forms with `Identifiable` siblings. Ordering is per-state first, then global, declaration order within each group.)
  - **Deferred to Phase 5:** the YAML DSL's `listeners:` component library (requirements §3.1.1) references listeners by id from a shared pool, while the Java DSL attaches them inline under an id. Closing that parity gap needs a listener registry, which belongs with the rest of the YAML component-resolution work rather than here.
  - [x] Invocation in execution flow: source-state `onExit` at step 4; target-state `onEntry` at step 8 (requirements §2.4). (Listeners are **purely observational**: a thrown exception is logged and swallowed, never reaching `TransitionResult`. The payload's transition is a `TopologyTransition`, so a listener cannot dispatch steps. The context reaches listeners untyped — a state has no single context type to bind, which is the deliberate dividing line against transition listeners.)

- [x] **Transition Listeners**
  - [x] `TransitionListener` interface (start / complete / error). (One functional `onTransition(entity, context, execution)` for all three hooks, plus the `TransitionExecution` payload record and its `TransitionPhase` discriminator, following the `StateChange` shape. **`onComplete` and `onError` partition the outcomes** — exactly one follows every `onStart`, so a completion listener needs no success check. Both pair with `onStart`: a transition rejected by a pre-condition notifies nothing, since §2.4 places the start hook after the pre-conditions. The context is **typed** (`TransitionListener<T, C>`), which is the dividing line against state listeners; global registrations take `Object` because they span transitions that differ.)
  - [x] Per-transition and global registration (`onAnyTransitionStart`, etc.). (`TransitionDef.onStart` / `onComplete` / `onError` and `StateMachineDef.onAnyTransitionStart` / `onAnyTransitionComplete` / `onAnyTransitionError`, each in instance / class / configurer forms with `Identifiable` siblings. Ordering is per-transition first, then global. Listener ids share **one** SM-wide namespace with state listeners; a transition's own ids are checked at build, because a transition def holds no reference back to the SM def.)
  - [x] **Trigger listener bindings (deferred here from §3.2) — delivered differently.** Rather than a per-trigger listener list, `TransitionExecution.firedBy()` returns the `Trigger` that caused the execution (`null` for a direct `transitionTo`), so a listener that should react to one invocation path branches on it. Same capability, no new DSL surface, and no per-kind question to answer. `requirements.md` §2.2.8 / §3.3.2 lost their "listener bindings" mentions accordingly. Threading it required `executeTransitionInternal` to take the firing `TriggerImpl` instead of a pre-extracted pre-condition list, which also gave the event and data dispatch paths the trigger they previously dropped.
  - **Moved to Phase 4:** async listener execution. Phase 4 owns the executor and thread-pool decisions, and designing a listener-specific dispatch ahead of it would mean designing that twice.

- [x] **Action Listeners**
  *Rationale: debugging and audit need something metrics cannot give — recording individual payloads when they match a condition ("where does this null come from?", "how does this user reach this end state?"). The `MetricsCollector` SPI covers counters and timings; this covers payload capture.*
  - [x] **One listener kind covers every action**, discriminated on the payload rather than split into mirrored `onAnyStep*` / `onAnyOperation*` families. After §3.8 there is one runtime type to observe, so a split would cost twelve global methods and two payload records to express a distinction one field already carries.
  - [x] `ActionListener`, an `ActionExecution` payload carrying phase + `ActionPath` + `ActionKind`, and `onAnyActionStart` / `onAnyActionComplete` / `onAnyActionError` on `StateMachineDef`. `ActionKind` discriminates the authored form (imperative / declarative, equivalently leaf / container) — the distinction a listener filtering noise actually wants. (The payload also carries the transition, as a read-only topology view, and the failure at `ERROR`; `actionId()` reads the leaf off the path. `ActionListenerDef` is the def-side builder, following `StateListenerDef` / `TransitionListenerDef`.)
  - [x] Global form dispatched from `TransitionView.runAction`, the single seam §3.8 left behind. (Globals are bound once on the state machine and appended at notification time rather than merged into each `BoundAction`, since one bound action is shared by every call site that reaches it — merging would bind a class-form global once per action.)
  - [x] Per-action declarative form on `StepDef` and the declarative-container defs, plus the member call sites. (Hooks live on `ActionDef` and are return-type narrowed on `StepDef` / `OperationDef` / `ConditionalOperationDef`. Inline members gained the configurer form they were missing — `step(id, Consumer<StepDef>)` on `OperationDef`, `BranchDef`, `DefaultBranchDef` and `ContextScope` — since the bare instance and class forms leave no def to hang metadata or listeners on.)
  - [x] **Open design question** for the declarative form: by-id references (`view.run(id)` and container `run(id)`) have no def at the call site to carry an attachment. ~~Either the global form covers them alone, or the imperative call site grows a way to name one.~~ **Answered: neither.** A listener attaches to the action's own def and fires wherever that action runs — transition attachment, container member, branch member, or dispatched by id from another action's body. Which observers an action has is a property of the action, exactly as its compensation is, so a reference has nothing to carry.
  - [x] **One asymmetry to document rather than discover:** a transition's root action notifies at almost the same moment as `onStart`. It should still fire, since a listener walking the execution tree wants the root node, but the near-duplicate needs stating. (Stated in `ActionListener`'s JavaDoc and `requirements.md` §2.2.10.)
  - [x] Reuses what this phase settled: the shared listener id namespace, the observe-don't-gate rule, and the payload-record shape. (An action's own listener ids are claimed at build over a throwaway copy, so building the same definition twice does not report them as duplicates.)
  - **Found during the work:** `mapFrom` had to move out of the notification scope in `runAction`. A `mapFrom` failure belongs to the parent and must not turn the child's completion into an error as well — the child did complete. A failure notifies each enclosing action on its way out and is rethrown unchanged, so the transition still reports what actually failed.
  - **Deferred to Phase 5, with the rest of the listener library:** the YAML spelling. It is not the state/transition blocks with a third noun substituted — attachment-to-the-action plus YAML's inline action definitions leave open where the attachment is written and how a referenced action inherits it. (`requirements.md` §3.7.)

- [x] **Component `validate()` hook** (deferred from the Phase 2.5 plan, Step 3c)
  - [x] Add a `validate()` method to each `Component<T>` sealed variant (`Component.Step`, `Component.Operation`, `Component.Condition`, plus any new variants Phase 3 introduces such as `Component.Trigger` and the listener-related variants if listeners get componentized). (No new variants were needed: neither trigger nor listener went through `Registry` / `Component`. All three existing variants now check that the component's id agrees with its payload's — the invariant that makes a registry lookup honest.)
  - [x] Invoke `validate()` once per component at the end of `StateMachineDefImpl.build(...)` — after the registry chain is settled and after the existing context-compatibility + cycle-detection passes. Failure throws `TransfluxValidationException` with the component id and a clear diagnostic. (Moved out of `RegistryImpl.register`, which had been calling it eagerly at registration time. The variants' own messages name the offender, so the build pass re-throws rather than wrapping.)
  - [x] Original use case driving the hook: a `Component.Step` may reject listener attachments that are illegal for its position (e.g. a transition-level listener attached to a sub-step). (**That consumer did not materialise here** — listeners stayed out of the registry, so no attachment reaches a `Component`. It arrives with the per-action declarative form in the Action Listeners task above; relocating the invocation now means that task will not have to touch the registry pipeline.)
  - [x] In practice, the hook lands here in Phase 3 rather than as empty stubs in 2.6. Each variant's default `validate()` is a no-op; only variants with structural rules override it.

### 3.7 Component Metadata Model (remainder after 2.6.13)
*Phase 2.6.13 pulled forward the `step` / `simpleOperation` lambda-configurer overloads — they only depended on the `IdentifiedDefImpl` base that landed in 2.6.11a and unblocked themselves. What was left: the parked `Describable` super-interface, `ConditionDef` and the overloads depending on it, the mapper configurer, and the listener-payload shape. The mapper configurer and the payload shape shipped; the other two were closed as decisions rather than as code, for the reasons below.*

#### Closed: `Describable` super-interface — dropped
- [x] **Decision: do not introduce it.** The original Phase 3.7 plan proposed `Describable extends Identifiable` (default-`null` `getName()` / `getDescription()`) retrofitted onto six public Def interfaces. The analysis done alongside 2.6.13 found:
  - Each Def interface already declares `getName()` / `getDescription()` independently. Collapsing them into a super-interface is cosmetic — no behavior change.
  - The presumed consumers (`StateListener`, `TransitionListener`, diagnostic logging) all know the *concrete* Def type they hold; none of them need polymorphic metadata access. The polymorphic case that would justify a common super-type does not yet exist.
  - Per CLAUDE.md's "Don't design for hypothetical future requirements", introducing a new public-API type now means exporting a symbol whose removal would be a breaking change, for speculative payoff.
- [x] **Both gates now answered.** (a) *per-kind*: every listener payload — `StateChange`, `TransitionExecution`, `ActionExecution` — either exposes a concrete accessor (`State<T>`, `Transition<T, ?>`) or carries the fields flat; nothing reads metadata polymorphically across Def kinds. (b) *cannot be answered here*: whether Phase 5's YAML serialiser walks Defs polymorphically is Phase 5's to determine, and reintroducing `Describable` then is purely additive. Closing the item now rather than carrying it costs nothing and stops a speculative type from shipping. **Moved to Phase 5.0** as an explicit decision point.
  - **Two real anomalies surfaced while checking, recorded for Phase 5.0's self-consistency review rather than fixed here:** `StateDef` and `TransitionDef` publish the `withName` / `withDescription` setters but not the matching getters (which exist on `IdentifiedDefImpl`, so the omission is in the published contract only); and the runtime `Transition<T, C>` exposes no `getName()` while `State<T>` does.

#### Outstanding items
- [x] ~~Add `ConditionDef<T, C>`~~ **Deferred to Phase 5.0.** Its only payload beyond what exists is a name and a description, and nothing reads either: there is no `Condition` runtime view, no condition catalog, and no payload that carries one. Making the metadata reach runtime means widening all five `ConditionDescriptor` records plus `BoundCondition`, and mirroring the resulting family across five defs (`StateMachineDef`, `ContextScope`, `TransitionDef`'s two slots, `BranchDef`, `ManualTriggerDef`, `DataTriggerDef`). The sealed descriptor grammar it has to intersect is exactly what the YAML schema work pins down, so the design pass belongs there.
- [x] Add lambda-configurer overloads where step / condition / operation / mapper registrations exist:
  - [x] *(Done in 2.6.13)* `StateMachineDef.step(String id, Class<C> contextType, Consumer<StepDef<T, C>> configurer)`
  - [x] *(Done in 2.6.13)* `StateMachineDef.simpleOperation(String id, Class<C> contextType, Consumer<SimpleOperationDef<T, C>> configurer)` — since renamed by §3.8 to `step(String id, Class<C> contextType, Consumer<StepDef<T, C>> configurer)`, which merged with the identical `step(...)` overload it had become.
  - [x] `StateMachineDef.mapper(String id, Class<P> parentType, Class<N> childType, Consumer<MapperDef<P, N>> configurer)` — **shipped as `mapperDef(...)`**, not `mapper(...)`: under one method name at most one lambda-shaped overload can exist, and `mapper` already had one. `MapperDefImpl` moved onto `IdentifiedDefImpl` for the configurer guard, the same migration `StepDefImpl` got when it was first exposed to a user lambda.
    - **Found while doing it, and fixed:** `mapper(id, P, N, ContextMapper<P, N>)` and `mapper(id, P, N, Function<P, N>)` have the identical function descriptor `(P) -> N`, so *no* lambda could resolve between them — `mapper("m", A.class, B.class, p -> child)` did not compile from Java at all, and only a cast worked. The Groovy specs never surfaced it because they write `as Function`. The `Function` overloads were redundant anyway (a lambda handed to the `ContextMapper` form produces the identical mapper, `mapFrom` already defaulting to a no-op), so they and `MapperDef.using(Function)` were removed. Overload count on the family is unchanged at six.
  - [x] *(Added alongside)* `ContextScope.step(String id, Consumer<StepDef<T, C>> configurer)` and its `Identifiable` sibling — a `forContext` block could otherwise declare a step but give it neither metadata nor listeners, which the flat form allowed. Both routes now share one registration path.
  - [x] ~~`StateMachineDef.condition(...)` / `TransitionDef.preCondition(...)` / `postCondition(...)` configurer forms~~ — **deferred with `ConditionDef`**, which they depend on. Note for whoever picks them up: `condition(String, Consumer<…>)` collides with `condition(String, String)` and `condition(String, Predicate<T>)` the same way the mapper configurer collided, so the naming question is already answered by precedent (`conditionPredicate` / `conditionExpression` / `mapperDef`) rather than open.
- [x] *(Done in 2.6.13)* Existing flat overloads stay as sugar for the no-metadata case.
- [x] Listener payloads (§3.5) surface `id` + `name` + `description` from the relevant def — concrete shape pinned down alongside the `*Listener` interfaces. **Resolution of the `Describable` parked item depends on what shape this lands at.** (Landed as `StateChange`, a payload record carrying `phase` + the `State<T>` entered or left + the responsible `Transition<T, ?>`. Metadata is read off those concrete types, so the access is per-kind — see the `Describable` note above. The listener's *own* id / name / description live on `BoundStateListener` and surface in diagnostics rather than in the payload; a listener already knows which one it is. `TransitionExecution` and `ActionExecution` followed the same rule; the action payload carries its fields flat, since an action has no runtime view type to read metadata off.)


### 3.8 Action Model Unification
*Collapses `Step` and `Operation` into a single runtime concept. **Sequenced before §3.5's Action Listeners**, which would otherwise design `ActionKind` and the dispatch seam against a model about to change — and before Phase 4, which fixes compensation semantics, and Phase 5, which writes the YAML schema. This is the largest refactor left before 1.0; it wants a written design note before it becomes a plan.*

**Design note: [docs/design/action-model-unification.md](../design/action-model-unification.md).** It settles what the items below leave open. The executable interface is `Action<T, C>` (both `Step` and `Operation` are deleted); the def hierarchy is `ActionDef` -> `StepDef` / `OperationDef` / `ConditionalOperationDef`; the package becomes `core.action`. The DSL splits its verbs by what the call site does rather than by what the callee is: every by-id **reference** uses `run(...)` (container member, branch member, transition attachment, and imperative dispatch alike), while **declaration** keeps the nouns `step(...)` / `operation(...)` / `conditional(...)` - it cannot collapse to one verb, because the two configurer forms would erase to the same signature. The two runtime paths converge on one rule (capture compensation -> record id -> push operation stack -> execute -> pop) rather than branching on `ActionKind`, which fixes two live defects in `executedPath`: a child dispatched from a step is qualified under the wrong parent and listed before it, and a throwing step lands on `compensatedPath` without ever appearing on `executedPath`. Container compensation stays Phase 4 - this phase documents the semantics without shipping the DSL.

#### Why
The split has already collapsed in practice, and the codebase pays to maintain it:
- `Step.execute` and `Operation.execute` have identical signatures — `(entity, context, transition)`.
- `BoundAction` is already a sealed supertype of `BoundStep` / `BoundOperation`, `CompositeMember` wraps one, and `TransitionResult.executedPath` records both kinds interleaved in a single list.
- Containment is not the differentiator: a `Step` receives the same `Transition` view an operation does, so it can dispatch by id too. §4.4.1's own example shows a simple operation doing exactly that.
- `StateMachineDefImpl` carries `checkIdNotRegisteredAsStep` / `checkIdNotRegisteredAsOperation` purely to keep two kinds apart inside one id space.
- The remaining differences are policy, not capability: compensation is step-only, and only an operation may attach to a transition. CLAUDE.md already documents the workaround the second one forces — "authoring a single-step composite is the way to use a step as a stand-alone operation target".
- BPMN, the source of the container framing, unifies: Task and SubProcess are both Activities, and a SubProcess attaches wherever a Task does. The current split is more restrictive than the model that inspired it.

#### The model
- [x] One runtime type. Two authoring forms, mutually exclusive: **declarative** (an ordered child list; declaration order *is* execution order) and **imperative** (a Java body, no bound children, free to dispatch ids declared elsewhere). (`Action<T, C>`; `Step` and `Operation` deleted.)
- [x] **Vocabulary: "step" is an imperative action, "operation" is a declarative one**, applied consistently. `SimpleOperationDef` disappeared into `StepDef`; `CompositeOperationDef` took over the `OperationDef` name; `ConditionalStepDef` became `ConditionalOperationDef`. The base is `ActionDef`, and the package moved to `core.action`.
- [x] **"Action" is the runtime noun, not a declaration verb** — but the split landed on *call-site category* rather than on dispatch alone. Every by-id **reference** uses `run(...)` (container member, branch member, transition attachment, and dispatch from an action body); **declaration** keeps the nouns `step(...)` / `operation(...)` / `conditional(...)`. Declaration cannot collapse to one verb: `action(String, Consumer<StepDef>)` and `action(String, Consumer<OperationDef>)` erase to the same signature. `Transition` went 16 overloads to 8; `OperationDef` went 26 member overloads to 14.
- [x] **Any action attaches to a transition.** The single-step-composite workaround is gone, and a spec pins the difference: `['charge']` where the wrapper gave `['wrapper', 'wrapper/charge']`.
- [x] Retain the authored form as metadata on the bound record so diagnostics still say "step" or "operation" rather than flattening to "action". (`BoundAction(id, action, kind)` with the public `ActionKind`; it is metadata only and never selects a runtime path.)
- [x] **Not planned, delivered anyway: one execution path.** Collapsing the two runners was not on this list, but leaving them meant `ActionKind` selecting behaviour, which is the split under a new name. `TransitionView.runAction` now applies one order to every action — capture compensation, record the id, push the nesting stack, execute, pop. That fixed two live defects in `executedPath`: a child dispatched from a step was qualified under the wrong parent *and* listed before it, and a throwing action was absent from `executedPath` while its compensation appeared on `compensatedPath`.

#### Compensation
- [x] Any action may declare a compensation, container or leaf. Pushed onto the enclosing execution's stack on entry and unwound LIFO, which the existing single stack already gives for free — children drain before the container that owns them. (The dynamic `getCompensation` hook; the static def-side `withCompensation(...)` is Phase 4.1.)
- [x] **Document: container compensation is additive, not a replacement.** A container's own compensation and its children's all run; the container's does not supersede. (`requirements.md` §2.2.11.)
- [x] **Document: push-on-entry means a container's compensation runs even when its first child fails immediately**, before the container itself did anything. Consistent with the existing "capture before execute" rule, but it reads as a bug in a stack trace unless stated. (§2.2.11.)
- [x] Note the surviving asymmetry: an imperative action can return its compensation dynamically from `getCompensation(entity, context)`; a declarative container has no Java object to hang that on and declares one statically on its def. (§2.2.11, and carried into the Phase 4.1 item that ships the static form.)
- **Found during the work, deferred to Phase 4.1:** the rollback drain hands every compensation the *transition's* context, not the context its action actually ran under. Harmless for compensations that close over what they need, wrong for mapped children that use their parameters. Phase 4 owns the compensation engine, so it owns this.

#### Fallout
- [x] `Component.Step` + `Component.Operation` collapse to `Component.Action`; the cross-kind id checks and the "registered as a step, not an operation" `ActionRef` error disappear. The two SM-level registration maps merged into one, and `ActionRef` went from six variants to four.
- [x] **Rename `StepPath` to `ActionPath`.** The accessors keep their names; only the element type changed.
- [x] `requirements.md` §2.2.5 / §2.2.6 rewritten around one concept; §2.1.4's "compensations are step-level only" reconciled with §2.2.11's "unified across operations and steps", which contradicted each other. Resolved in favour of §2.2.11: any action may compensate.
- [x] Migration note: "operation" changes meaning, from "unit of work attached to a transition" to "declarative container". (Design note, Migration section.)
