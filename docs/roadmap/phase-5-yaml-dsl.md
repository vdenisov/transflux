**Three decisions that hold across the phase.**
- **The mapper only emits `Def` calls.** Everything the Java build already checks — reference existence, action cycles, state-machine-wide id uniqueness, context compatibility — is checked there and nowhere else. The loader adds only what a document can get wrong before a def exists (structure, unknown keys, unloadable classes, import cycles) and attributes a build failure to the file and line that declared the offending def.
- **Parity is capability, not spelling.** `InstanceBased` conditions are Java-only and `class:` is YAML-only already; SpEL forms of the state resolver, the state applier, a mapper's `mapTo` and a compensation route's guard join the YAML-only side (§5.9, §5.8, §5.10), since Java has a lambda for the same job. Where YAML needs something the Java DSL has no equivalent of *capability* for — a listener or trigger declared once and attached in several places — Java gains it (§5.4).
- **The loader validates; the schema is for editors.** A mapper walking the YAML node tree knows the line, the column and what is being declared, so it can say `subscription.yml:42: action entry declares both 'run' and 'step'` where a schema validator says `must be valid to exactly one schema`. The JSON Schema ships for IDE autocomplete and is kept honest by a spec rather than used at runtime (§5.12).

### 5.3 Java/YAML Alignment and Decisions
*A design item: its output is `requirements.md`, not code. §3 was rewritten whole, with §2.2.1, §2.2.2, §2.2.8, §2.2.10 and §4.1 brought into line; what the decisions cost in Java is §5.4.*
- [x] **Alignment walk.** Every top-level element compared side by side. Beyond the questions already listed here it surfaced: `@bean` expressions with no resolver behind them, inline `class:` / `predicate:` conditions missing the id §2.2.1 requires, a `- condition:` wrapper contradicting the descriptor's own rule, an event filter and a route guard spelled as conditions though neither judges `(entity, context)`, three spellings of a class-valued key, a global-listener block implying selectors that do not exist, `mappers:` absent from §3 altogether, two import spellings and two document envelopes.
- [x] **Shared triggers: one trigger, many transitions.** A registration claims the id and carries everything the trigger is; a transition attaches it by id. The catalog lists it once with every transition it sits on, `firedBy` is unchanged (the payload already names the transition), and `fire(id)` takes the attachment leaving the entity's current state — two attachments of one manual trigger leaving the same state fail the build. §2.2.8.
- [x] **Shared listeners: the id names the listener, not the attachment.** Registered once under its category, attached by id any number of times, `withAsync` on the registration. One listener may be attached to an owner and state-machine-wide at once; a disable then suppresses the global delivery only. No other component kind needs a pool — nothing references a compensation, a resolver or an applier by id. §2.2.10.
- [x] **Inline declarations keep the inline-action rule**: the id is claimed state-machine-wide, visibility is local. An inline listener is visible to its owner's other hooks (forward references included) and to nothing else — not to the owner's members; the state machine's `onAny*` hooks are one owner. An inline trigger is visible to its transition alone. A reference from outside is its own build error, telling the author to register it. §3.1.2.
- [x] **§4.1 rewritten** against the shipped model: registrations, by-id references, "a method taking the def" as today's answer to sharing across machines, and the registry trimmed to a Phase 6 sketch of the kinds a factory method can return. The constraint stands: the loader registers through `StateMachineDef` and keeps no component table of its own.
- [x] **Action listeners in YAML.** Every owner carries the same `listeners:` block keyed by its Java hook names; for an action it is written on the declaration, registered or inline. `listeners:` and `disableGlobalListeners:` on a `run:` entry are errors naming where the action is declared. State-machine-wide listeners sit under `stateMachine.listeners:` keyed by the eight `onAny*` names. Disables are one key: a list of ids, or `true`. §3.7.
- [x] **`ConditionDef`: no, and the keys are rejected rather than dropped.** A condition carries an id only, in both DSLs; `name:` / `description:` on one are unknown keys. §4.7.2 is deleted. Reopen with a condition catalog. §2.2.1, §3.6.1.
- [x] **`Describable`: stays closed. `Identifiable`: goes.** The loader is per-kind, and so would a definition dumper be — one section per kind. Both are additive if a polymorphic consumer ever appears.
- [x] **A transition's body is an `actions:` list**, with no single-action key and no string shorthand; an `actions:` list is the only position an action occupies.
- [x] **`conditional` is renamed `choice`, in both DSLs** — `condition` / `conditional` sat a few letters apart on the same surfaces. `choice` / `forkChoice`, a `choices:` section, `ChoiceDef`; `branch`, `default`, `onNoMatch` and `NoMatchBehavior` are unchanged.
- [x] **SpEL bindings** for every expression position are one table in §3.9: resolver and applier against the entity, a mapper's `mapTo` against the parent context with no entity in scope, its `mapFrom` entries against the child with `#parent` bound, a route guard against the failure. §3.9 also states that a definition is code — full SpEL, classes instantiated by name — which makes the `DefinitionSource` a trust boundary, and that `@name` needs the DI integration of §6.1 and otherwise fails at first evaluation.
- [x] **`mapFrom:` has an expression form after all**: a map of assignments into the parent context, not an expression returning a new one — the parent is already referenced by the host, the rollback stack and the enclosing actions, so write-back has to mutate. No Java change; a write-back with logic stays a class. §3.5.2.
- [x] **Loose ends.** `contexts:` is cut — `context:` is a class name everywhere, optional on every registered kind. `version` stays, optional and opaque, for hosts loading definitions from external sources; component-level versioning metadata is cut. `config.metrics` is an unknown key until Phase 6.3 adds it. The long-form `ref:` is cut.
- [x] **One document envelope**: `apiVersion`, `imports` (bare strings), seven component sections, and `stateMachine:` in the root only — a library is a document without one. `config:` and the global listeners moved inside `stateMachine:`. Diamond imports are legal; an imported document carrying `stateMachine:` is an error.
- [x] **Spelling rules.** A key whose value can only be a class is a bare class name (`context`, `compensation`, `exception`); `filter:` and `guard:` take `class` / `expression` and are not conditions; a listener's `async:` / `onRejection:` are flat; a registered listener's category is inferred from its class, with `type:` only when it implements several; `mappers:` use `parentType` / `childType`.
- [x] **The three consistency questions from §5.2.** `State<T>` loses its type parameter; `getContextType()` is the one spelling (`getParentType()` / `getChildType()` on `MapperDef`); the state machine's id, name, description and version are all optional and land on the runtime `StateMachine`, per definition — they follow `replaceDefinition`, which does not compare ids.
- [x] **Inline nested declarative containers in the Java DSL** - moved to [Phase 4b](../history/phase-4b-action-sequence-grammar.md), which closed the whole parity gap rather than this one cell: a member-position `operation(id, ...)`, a conditional nested inside a branch, mappers and forks on branch members, and one shared member grammar (`ActionSequence`) the loader is written against. **Shipped.**

### 5.5 `StateMachine` as Handle + `replaceDefinition`
*Per `requirements.md` §2.7. Independent of every YAML item except §5.13's demo, so it ran early. Watcher-driven automatic reload stays Post-1.0 (§7.2).*
- [x] **Executor ownership, decided first: handle-owned, first configuration wins.** One executor per handle for its lifetime, created at `build()` or at the first swap whose definition needs one; a later definition's pool or host executor is logged as ignored and the one in force keeps running; `close()` shuts down exactly one, and only a pool the framework built. Per-snapshot pools were rejected because a snapshot is never retired: its pool would either be shut down under an in-flight transition that could still fork into it, or be kept per generation forever. `BLOCK` against a host executor in force is refused at the swap, since a definition's own build check only sees the executor that definition declares. Captured in §2.7.6.
- [x] **`StateMachine<T>` is the host-facing handle.** The per-version data and the execution engine moved into an internal `StateMachineSnapshot<T>`; the handle **keeps the name `StateMachineImpl`**, rather than the rename this item first sketched - it is still the impl of `StateMachine<T>` and still the class a reader enters through, so the ~25 `StateMachineImpl*Spec` files keep their names under the spec-naming convention. External callers see no source-incompatible change.
- [x] **Every external entry point captures the snapshot once** and delegates against it; an `EntityBinding` returned by `entity(...)` is such a capture and runs on the snapshot it took, however late its terminal method is invoked.
- [x] **`ExecutingTransitionImpl` holds its snapshot**, and so do `AsyncBranchTask`, every `bindMembers` / `resolve` signature, and `StateMachineDefImpl.bindDeferredMembers`.
- [x] **The reentrancy guard and the async-branch ban key on the handle.** `EntityKey` is `(handle, entity)` and the deque names handles, so an execution in flight against generation N rejects a reentrant call arriving after the swap to N+1, and a branch forked under N may not drive N+1.
- [x] **`long generation()`**, starting at `1` and incremented by exactly `1` per successful swap.
- [x] **`long replaceDefinition(StateMachineDef<T> newDef)`**, serialised on a lock: entity-type check, `BLOCK`-against-a-host-executor check, then `StateMachineDefImpl.buildSnapshot(handle, generation)` - the same pipeline `build()` runs, so validation, binding and the completion INFO all happen before the volatile write and a throw changes nothing. Then the swap, the increment, and an INFO on `build.lifecycle`.
- [x] **The entity type became mandatory at `build()`** - it is the handle's identity contract, and §5.7's raw-type checks need it. `Transflux.defineStateMachine(Class)` already declares it; the witness form declares it with `forEntityType(...)`.
- [x] The snapshot reference is `volatile`, which also discharges the safe-publication contract for a snapshot a swap installed. The build INFO line gained `generation=`.
- [x] **Specs:** `StateMachineImplReplaceDefinitionSpec` covers atomic-or-nothing, entity-type rejection across subtype / supertype / unrelated, a foreign and a null definition, in-flight isolation against two concurrent swaps, a pre-swap `EntityBinding`, reentrancy and the branch ban across a swap, generation monotonicity, and the executor rules end to end (adopted at a swap, a differing declaration ignored with one WARN, a host executor left alone, `BLOCK` refused, one pool closed).
- [x] **Java DSL hot-swap demo** - `JavaDslSurface.definitionReplacement()` builds, drives, replaces with a topologically different definition and drives again, from Java through the public DSL; `JavaDslSurfaceSpec` asserts the generations and the trail.

### 5.6 Definition Sourcing SPI
*Per `requirements.md` §2.6. The SPI and its implementations only — no parser needed. What the loader does with a source (imports, import-chain errors, import cycles) is §5.11.*
- [x] **Home: `transflux-yaml`, package `org.transflux.yaml.source`.** The module did not exist yet, so this item took §5.7's first bullet: the repository is a parent POM (`transflux-parent`) with `transflux-core` — the existing library, renamed from `transflux` — and `transflux-yaml` as modules. Toolchain, Surefire's `**/*Spec` include, JaCoCo and every dependency version sit in the parent; the core module gained no dependency.
- [x] `DefinitionSource`: `Optional<DefinitionResource> open(String identifier)`, a functional interface, plus `default Set<String> prefixes()` (empty). Empty from `open` means "no such document" and nothing else; an unreadable document or a refused identifier throws.
- [x] `DefinitionResource`: a final `AutoCloseable` class carrying `identifier()`, `bytes()` (an `InputStream`), and nullable `location()`, `lastModified()` and `etag()` (`Optional` is kept for `open`'s answer, not for metadata, as in core); `close()` closes the stream. `location()` names where the answering source found the document, which the identifier stops doing once a composite scans; §5.7's error model prints it.
- [x] Identifiers are **opaque, source-defined strings** — no path canonicalisation, no implicit `.yml` suffix, no relative-to-importer resolution by the framework.
- [x] `ClasspathDefinitionSource` (context class loader at construction, or one passed in; prefix `cp:`). `FileSystemDefinitionSource(Path root[, SymlinkPolicy])` (prefix `file:`): absolute, drive-rooted and `..`-bearing identifiers refused with a `TransfluxValidationException`; `SymlinkPolicy` `WITHIN_ROOT` (default) / `FOLLOW` / `REJECT`, junctions included; the root itself may be a link. Both take `withPrefixes(...)`. `CompositeDefinitionSource.of(sources...)`: an ordered list; a declared prefix selects the sources declaring it and is stripped, anything else scans every source verbatim; first found wins; a matched prefix never falls through to the scan. One source per prefix (the first cut's map) could not express "config directory, then home directory" under one `file:`.
- [x] Logger leaf `org.transflux.yaml.source` (DEBUG: the route taken, where a miss looked), in the module's own package-private `Loggers` holder with a module-local `LoggersSpec`. §5.7 decides where `yaml.parse` / `yaml.binding` are declared.

### 5.8 Parsing: Component Libraries
*A document's component sections loaded into registrations on a `StateMachineDef`. No state machine, no imports yet: the sections are read from the root document, by a per-document reader §5.11 runs on each import.*
- [x] Document envelope per §3.1.1: `apiVersion`, the component sections at top level, no `metadata` / `spec`. `operations:` / `choices:` stay unknown keys until §5.10, `imports:` until §5.11.
- [x] `steps:` — `class`, `context` (a bare class name, optional on every kind), `name` / `description`, `compensation` and `errorHandling` routes (`exception`, `guard:` as `class` or an expression over the failure, `compensation`), `onRejection`, and — ahead of §5.10, since §3.1.1's library example needs them — `listeners:` and `disableGlobalListeners:`. The keys every action declaration shares are one reader (`ActionKeys`) §5.10 reuses for operations, choices and inline declarations; the `listeners:` hook block is one reader (`ListenerEntries`) §5.9 reuses for states, transitions and the `onAny*` hooks.
- [x] `conditions:` and the Condition Descriptor grammar, one reader (`ConditionDescriptors`) for every position: a string references, a block declares with exactly one of `class:` / `predicate:` / `expression:`; no `name:` / `description:`. A `predicate:` class implementing both `BiPredicate` and `Predicate` is refused, as the Java call would be ambiguous.
- [x] `mappers:` — `parentType` / `childType` and either `class:` or `mapTo:` with an optional `mapFrom:` map. The SpEL adapter is a `ContextMapper` built in this module (`Expressions`); `mapFrom:` assigns through a `StandardEvaluationContext`, so a string converts to an enum-typed property.
- [x] `listeners:` and `triggers:` onto the §5.4 registrations. A listener's category is inferred from its class, `type:` required only when it implements several; a registered state listener refuses `context:`, and an inline listener has no `context:` key at all — it takes its owner's (§3.7 changed accordingly). `onRejection:` without `async: true` is an error; `FAIL` is refused by core. Triggers: `type: manual | event | data` and only that kind's keys; `filter:` is `class` (`BiPredicate<Object, T>` xor `Predicate<Object>`) or `expression`.
- [x] Component identification per §2.2.1: `id` mandatory, inline expression conditions excepted.
- [x] **Expressions are parsed where they are declared, in core.** Condition and event-filter expressions used to be parsed at first evaluation; the def setters now parse them, so a malformed one is a `TransfluxValidationException` from the call that declared it — which `NodeMap.at` turns into the document's line, and which a Java host gets at declaration as well. The loader parses only the expressions that never reach core as strings: `mapTo`, `mapFrom`, a route's guard.
- [x] Classes are checked against the position as javac would (§3.1.5): entity contravariant, context exactly the owner's. A registration without `context:` leaves its own class's context argument unchecked, as Java's untyped instance form does, but what is declared on it - and an untyped transition or action listener registration - is checked against `Object`, which is what keeps a typed listener off the `onAny*` hooks.
- [x] `operations:` and `choices:` registered at library level use §5.10's member grammar, and closed there.

### 5.8.1 Transitions Declared on the State Machine
*Found while planning §5.9: YAML lists `states:` and `transitions:` side by side, each transition naming `from` / `to`, while Java declared a transition inside its source state's configurer. The two could express the same machines, but the loader would have had to regroup transitions by source state and check `from` itself. Java moved to the document's shape rather than the other way round: a transition body nests deep enough in YAML without two more levels above it.*
- [x] **`StateMachineDef.transition(id, source, target, [Class<C>,] cfg)`** replaces `StateDef.transitionsTo(target, id, [Class<C>,] cfg)`, which is removed. The id comes first, as on every other registration. A state keeps its metadata, its entry and exit listeners, and its disables.
- [x] **`StateMachineDef.state(id)`** for a state that configures nothing, which most states became once transitions left them.
- [x] **Both ends are checked at build**: a transition whose source or target is not a declared state is refused. The target never was checked before - a typo built and failed at runtime, when the resolver read the undeclared state back. States and transitions may be declared in either order.
- [x] Transitions are held in declaration order. Dispatch is unaffected, since it only scans transitions leaving the current state; the catalog lists them as declared.
- [x] Every call site moved (the specs, `JavaDslSurface`, the JavaDoc examples, `requirements.md` §2.2.3, §2.2.4, §4). `StateMachineDefImplTransitionSpec` holds the transition cases `StateDefImplSpec` used to.

### 5.9 Parsing: the State Machine
*One def call per document entry. The loader checks nothing about states or transitions itself: §5.8.1 made the Java DSL flat, so `from` and `to` are arguments core validates at build.*
- [x] `stateMachine:` — `id`, `name`, `description`, `version` (all optional) and `entityType`, read by `StateMachineSection`. It is required in the root document; refusing it in an imported one waits for §5.11, which is what reads an import.
- [x] **State resolver and state applier**: `class:` through the instantiation seam, or `expression:` through an adapter built in this module. The resolver evaluates against the entity with `#entity` bound and returns the state id, an enum contributing its `name()` and anything else its `toString()`; the applier assigns the id through the expression. **The assignment does convert a `String` to an enum-typed property** — `StandardEvaluationContext`'s default converter does it, and `ExpressionsSpec` pins it — so §3.2.1 needed no correction.
- [x] `states:` — metadata, `listeners: { onEntry, onExit }`, `disableGlobalListeners:`.
- [x] `transitions:` — `from` / `to`, `context:`, `preConditions` / `postConditions`, `triggers:` by reference or declared in place in all three kinds, `listeners: { onStart, onComplete, onError }`, `disableGlobalListeners:`. A transition's `actions:` stays an unknown key until §5.10.
- [x] State-machine-wide listeners — `stateMachine.listeners:` keyed by the eight `onAny*` names, all three categories in one block. That is what put the category on `ListenerEntries.Hook`, since a block is read once.
- [x] **Reading triggers moved to `TriggerEntries`**, which now also attaches them to a transition; an inline trigger takes its transition's context and has no `context:` key, as an inline listener does. `ConditionDescriptors.Target.of(...)` builds a target from one def verb per form, for the four positions that now take conditions.
- [x] **A reference reaching another owner's inline listener stays core's check**, raised at the host's `build()`. Attributing it to the declaring line is the same problem as every other build failure, so it moved to §5.13 rather than being duplicated in the loader.

### 5.10 Parsing: Member Grammar, Compensation, Fork
*One walk, generic in the concrete def type, fills all four positions that hold an ordered list — a container, a branch, a default branch, a transition's body. That is what `ActionSequence<T, C, SELF>` is self-typed for.*
- [x] **Java first: a declaration names a registered mapper.** §3.4.2's example and §4.5.2.1 put a mapper id on a declaring entry, which `ActionSequence` had no form for, and the loader keeps no component table to resolve one itself. Every mapped declaring shape gained a `String mapperId` twin - `step` x2, `operation`, `choice` and their `fork*` forms, 33 -> 41 methods - and the build checks it as it checks a by-id reference: the registered mapper's parent against the enclosing context, its child against the declared one. The runtime needed nothing: an inline def already carried any `MapperRef`.
- [x] Verb-keyed entries, read by `ActionEntries`: `run:` (reference) against `step:` / `operation:` / `choice:` (declarations); exactly one per entry. Declarations nest to any depth. One walk fills all four `ActionSequence` positions; an operation's and a branch's `actions:` are required, a transition's is optional.
- [x] **Context shapes**: a declaration's own `context:` key, alone (pass-through) or with a `mapper:` (mapped), which needs `context:` beside it. A `mapper:` at any call site accepts a registered mapper id, a `class:` block, or `mapTo:` with an optional `mapFrom:` map (§5.8's adapter, whose block reader `mappers:` now shares). Mapper instances are Java-only.
- [x] **`fork: true`** beside any verb, mapping to the verb's forked twin; `onRejection:` beside it — the call-site rung on a `run:` (refused without `fork: true`), the def's own declaration on a declaring entry. **A `mapFrom:` written in a call-site block beside `fork: true` is refused**, since a fork never writes back; a registered or class mapper's write-back is written elsewhere and stays silently unapplied, as in Java.
- [x] `choice:` — `branches:` (id, condition descriptor, `actions:`), `default:`, and `onNoMatch:`. A branch and a default carry nothing else.
- [x] `compensation:` and `errorHandling:` routes on any action, in declaration order - `ActionKeys`, shipped with §5.8, applied to every declaration.
- [x] Action listeners and `disableGlobalListeners:` on a declaring entry, and both rejected on a `run:` entry with a message naming the action whose declaration they belong on. Naming its declaring *line* was dropped in §5.11: the index built there sees registrations only, so it would name a line for some callees and not others.
- [x] Library-level `operations:` and `choices:` (left open by §5.8) and transition bodies (left open by §5.9) both closed here; `steps:` moved into `ActionEntries` beside them. `ActionEntriesSpec` loads, builds and runs §3.4.2's `complex-activation` example, its classes swapped for fixtures.

### 5.11 Imports and Global Configuration
- [x] **Imports flow through the source.** Each `imports:` entry is handed verbatim to the `DefinitionSource`, depth first and before the importing document's own sections - the root's `entityType` is read first, since a library names none. A document is read once per load, keyed by the identifier *as asked*, so a diamond import is opened once; `DefinitionResource`'s JavaDoc said deduplication used the identifier the source reports, and was corrected rather than the loader, since identifiers are opaque. The loader caches nothing across loads.
- [x] A missing import, one the source refuses, a **circular import** (the message names the cycle), an entry that is not a non-null scalar, and an imported document carrying `stateMachine:` or no valid `apiVersion` are each refused at the line that wrote them.
- [x] **Import chain in every error**: `root.yml -> lib.yml:12:5: condition 'foo': ...` - the importers lead the §5.7 location, and `DefinitionLoadException.importChain()` carries them root first. `Document` holds the chain, so every error raised against it has it without further plumbing.
- [x] **Duplicate ids name both declarations - where core refuses them at the def call.** `DeclarationSites` records the first site of each id a load declares, in the id sets core checks at declaration time (actions, conditions and mappers apart, since only the build compares the three), and appends `; first declared at lib.yml:3:9` to core's rejection. It covers registrations, states, transitions, and listeners declared in place on a state or the state machine. A collision core only finds at `build()` - an inline action against a registration, a step against a condition, two transitions' inline listeners - is §5.13's "build failures in YAML terms"; the loader adds no check of its own.
- [x] `config.async` → `withAsyncPool(...)` / `withAsyncRejectionPolicy(...)`; any `async:` block asks for a pool, `async: {}` at the default sizing. **`threadPoolSize` and `queueCapacity` are given together or not at all**: Java has no form sizing one of them, and the loader repeating the default formula would copy a number §3.8 says is not a contract. `config.logging` → `withExecutionLogging(...)` with `level`, `includeContext`, `includeTimings`. A bare `async:` or `logging:` is refused rather than read as absent, since the block's presence is the statement; `metrics` is an unknown key.

### 5.12 JSON Schema
*Written last, against a grammar that has stopped moving.*
- [x] **JSON Schema 2020-12**, `docs/schema/transflux-v1.schema.json`: GitHub Pages serves it at its `$id`, `https://vdenisov.github.io/transflux/schema/transflux-v1.schema.json`, and the pom copies the same file into the `transflux-yaml` jar as `org/transflux/yaml/transflux-v1.schema.json`. Draft-07 came first, for editor reach; with IntelliJ and yaml-language-server 1.20+ both on 2020-12, `unevaluatedProperties` lets the shared key sets (an action's keys, a trigger's, a listener's) be written once and composed, and the generator that kept draft-07's copies equal went with it. An editor that predates it reads the objects as open, which misses errors but never invents one.
- [x] **The schema never refuses what the loader accepts**, bar one exception taken for autocomplete's sake: a bare `true` / `false` where text is expected, and a quoted boolean or number. Everything else the loader reads loosely - a number where it reads text, `null` as absent - the schema admits too. What only loading can see stays the loader's: classes, type arguments, SpEL, imports, duplicate ids, and the YAML features `Document` refuses.
- [x] **Agreement spec**, `YamlDefinitionLoaderSchemaSpec`, over `corpus/{valid,invalid,loader-only}/`: both accept, both refuse, or only the loader refuses. A refused document pins the loader's message (`# error:`) and the schema error's JSON pointer (`# schema:`), and under a union of definitions - an action entry is one of four shapes - the definition that must raise it (`# rule:`). Documents are read as editors read them, under YAML 1.2's core schema, rather than through the validator's own YAML 1.1 reader. networknt `json-schema-validator` 2.0.x, test scope; core dropped the `jackson-core` it never used, and Jackson is on 2.22 through its BOM.
- [x] **Every YAML example in `requirements.md` is in the valid corpus.** Each carries a `<!-- corpus: name -->` anchor naming its copy under `corpus/valid/requirements/` (`none` for the two grammar sketches), and the spec requires every example to be anchored, each copy to hold its example and every copy to have an anchor. The classes the examples name are inert stubs under `com.example` (test scope). The first load found one example that could not have built - §3.7's `run: charge-card` passed a missing context through - and it was fixed to the implementation.
- [x] **The loader specs' whole documents moved into the corpus**, loaded by id through `LoaderFixtures.resource` / `loadResource`: the five a success feature wrote out in full. Documents a helper builds or a where-table splices into, and refusals beside their messages, stay inline.
- [x] **Documents are named `*.transflux.yml`**, the pattern an editor or a SchemaStore entry maps to the schema; every document in the repository follows it.
