## Phase 4b: Action Sequence Grammar (v0.4.0, with Phase 4)
*Target: every position that holds an ordered list of actions — a declarative container, a conditional branch, a conditional's default branch — admits the same member grammar, declared once on a self-typed `ActionSequence<T, C, SELF>` base. A branch member may carry a mapper, be forked, or declare a conditional inline; a container member may declare a sequence inline; a forked member may be declared inline; a transition may attach a conditional inline. Additive: every call shape that compiles today still compiles, and nothing on `TransitionResult`, the paths, or the compensation stack changes shape.*

### 4b.1 Branches carry bound members
*The one step with runtime risk, landed alone and behaviour-neutral: no DSL change, no new member forms, no new logging. One existing spec changed — see the last item.*
- [x] `ResolvedBranch(branchId, condition, List<String> stepIds)` becomes a branch holding the same resolved member records a container holds — `CompositeMember`, promoted out of `OperationDefImpl` to a top-level record in `core.impl` carrying the dispatch both positions now share, and resolved at build time by the same `ActionRef.resolve` + `MapperRef.resolve` pair `OperationDefImpl.buildBound` runs.
- [x] The conditional's executor dispatches the selected branch's members through `CompositeMember.dispatch`, the same call the container makes, so a branch member reaches `ExecutingTransitionImpl.runAction` through the path every other member already takes. Path qualification, compensation capture, nesting and listener notification stay where they are; the conditional owns nothing of its own beyond branch selection and the no-match policy.
- [x] `BranchDefImpl` / `DefaultBranchDefImpl` already held `ActionRef` lists — what changed is that the conditional stops flattening them to ids. **Building a conditional now takes two passes**: `buildBoundAction(conditionRegistry)` keeps its position in `InlineRegistrationSink` (shape validation, branch conditions, the `BoundAction` that goes into the enclosing scope), and a new `bindBranchMembers(...)` fills in the members afterwards. They cannot be one pass: the bound action must be in the scope before its own members resolve, because a sibling member may reference the conditional by id and such a reference captures the bound action by value.
- [x] `StateMachineDefImpl.validateBranchRefs` did **not** fold into `checkRefs` — that was impossible, since `checkRefs` runs before construction and the scopes it would need do not exist yet. It was **subsumed by binding**, which is strictly stronger: an unknown or wrong-kind branch id now throws out of `ActionRef.resolve`, with the sibling-scope enrichment `checkRefsResolvable` never had. The walk survives as `bindConditionalBranchMembers`, invoked from `StateMachineImpl`'s constructor after every container is built and before `flatten()`. It stays a pass of its own rather than moving into `buildBound`, because containers are registered into the root registry as they are built — binding inside `buildBound` would stop a branch from referencing a container declared after its own.
- [x] Specs: every conditional, compensation, listener and path spec passes unchanged. **One exception**, deliberate: `StateMachineDefImplBuildLoggingSpec`'s phase list drops to three, since the build phase that announced the deleted validation pass went with it. Three cases added — a branch referencing a later-declared container (the regression pin for the paragraph above), a branch member's declared compensation receiving the mapped child context its branch ran against, and a branch member naming an id registered as a condition.

### 4b.2 `ActionSequence<T, C, SELF>`
*The invariant, expressed once. Self-typed so a generic helper — the Phase 5 YAML mapper first of all — keeps the concrete chain type: `<S extends ActionSequence<T, C, S>> void fill(S sequence)`.*
- [x] `ActionSequence<T, C, SELF extends ActionSequence<T, C, SELF>>` in `core.action`, carrying the full member grammar: `run` (7 overloads), `fork` (7), `step` (6: instance, class, configurer, each with its `Identifiable` sibling), `conditional` (2), and `operation` (2, from §4b.3). No `Def` suffix — it is a grammar mixin with no identity, like `ContextScope`.
- [x] `OperationDef<T, C> extends ActionDef<T, C>, ActionSequence<T, C, OperationDef<T, C>>`; `BranchDef<T, C> extends ActionSequence<T, C, BranchDef<T, C>>`; `DefaultBranchDef<T, C> extends ActionSequence<T, C, DefaultBranchDef<T, C>>`. The per-subtype member declarations go; what stays on `BranchDef` is `condition(...)`, and on `OperationDef` the action-level surface (`usingContext`, compensation, routes, listeners). JavaDoc for each member form lives on the base, once.
- [x] Branch and default-branch members gain the call-site mapper — the `run(id, mapperId)` / `run(id, inlineMapper)` / `run(id, Identifiable mapper)` forms and their siblings — with the same `checkRefs` context-compatibility check a container member gets, descending through `ActionRef.Conditional` into each branch.
- [x] Branch and default-branch members gain `fork(...)` in all seven forms, with the same per-member forkability warning §4.3.1 emits for a container member.
- [x] Branch and default-branch members may declare a `conditional(...)` inline — recursion. The nested conditional registers into the enclosing container's scope like every other inline member; ids stay globally unique, and the definition is a finite tree by construction, so no new cycle case.
- [x] `definitionForks()` descends through conditionals, branches and (from §4b.3) nested containers instead of stopping at state-machine-level and transition-attached containers. Without this a definition that forks only from inside a branch never gets an executor.
- [x] **The cycle detector descends through conditionals and branches.** `getByIdReferenceIds()` walked one container's own member list, so a cycle closed by a branch's `run("some-container")` was invisible at build time and recursed without bound at execution. Not in this section's original list, and fixed here rather than later because everything after it widens what a branch may hold. The descent is one walk — `ActionSequenceSink.visitAllMembers` over `ActionRef.visitNestedMembers` — shared with `declaresFork()`; it terminates by construction, since inline nesting is literal source and a by-id edge is deliberately not followed. **This narrows what builds**: a container whose conditional recurses by id from one branch while another branch terminates it used to build and run, and is now rejected as a cycle. That is the intended reading — the detector cannot see which branch is selectable, so it cannot tell a base case from an unbounded recursion, and the direct form (a container referencing itself) was already rejected. Closing the branch route makes the two agree rather than leaving recursion expressible only through a conditional.
- [x] `ActionSequenceSpec`: reflects over `OperationDef`, `BranchDef` and `DefaultBranchDef` and asserts that the set of member-grammar methods — name, parameter types, and return type equal to the declaring subtype — is identical across the three. This is the test nothing else replaces.
- [x] `JavaDslSurface` gains every new call shape on a branch and a default branch — each mapper form, each fork form, an inline conditional inside a branch — and `JavaDslSurfaceSpec` drives them. Groovy alone would not catch an overload that stopped resolving.
- [x] Specs: `StateMachineImplForkSpec` gains a forked branch member (runs on another thread, appears on neither path, listener sees it under `conditional/branch-member`); `StateMachineImplForkCompensationSpec` gains a forked branch member's own stack; a mapped branch member's compensation receives the mapped context; a nested conditional reports `outer/inner/member` on `executedPath`.

### 4b.3 Inline sequence at a member position
*The cell the table in the design doc had empty, and what a forked inline group needs.*
- [x] `operation(String id, Consumer<OperationDef<T, C>> configurer)` and its `Identifiable` sibling on `ActionSequence`. The child is typed against the enclosing container's `C` and runs pass-through, like every inline declaration; `usingContext(...)` remains callable inside the configurer but cannot re-type: it returns `SELF`, so the only compilable argument is the enclosing type restated. The build-time boundary check (widen yes, narrow no) therefore only ever answers a caller that evaded javac — Groovy, raw types, or the Phase 5 YAML mapper. Giving an inline declaration a context of its own is §4b.5.
- [x] The inline container's `Registry` parents onto the enclosing container's registry, not the root, so its inline ids are visible only within its subtree and it can reach the enclosing container's inline ids — the same lexical rule an inline conditional follows today. `flatten()` at the end of construction still makes runtime resolution one lookup: it walks the whole ancestor chain, so a two-deep scope needs no ordering between a parent's flatten and a child's.
- [x] **Every container binds its members in a deferred pass.** An inline container cannot resolve its members while scopes are still being populated — there is no `StateMachineImpl` yet, and an SM-level callee may not be built — so `buildBound()` produces the bound action and `bindMembers(...)` fills in the members afterwards, exactly as a conditional already built in two passes. The two root forms moved onto the same schedule rather than keeping a second, eager one: a member may now name a container declared after its own wherever it sits, which is what a branch could already do.
- [x] `checkRefs` and the cycle detector descend into the inline container. An inline container cannot close a cycle by itself (it is literal source), but a by-id reference from inside it can, and the existing detector has to see the edge. The descent is free: `ActionRef.InlineOperation.visitNestedMembers` feeds the one walk `declaresFork()` and `getByIdReferenceIds()` already share.
- [x] Build-time validation names the nesting in its messages (`transition 't' > operation 'outer' > operation 'inner'`), since an inline id claimed twice at different depths is otherwise hard to find. Retrofitted to conditionals and branches too, so one convention covers every position; `defLabel()` stays flat, since the configurer guard names a def rather than a position.
- [x] `JavaDslSurface` gains an inline operation inside a container, inside a branch, and two deep; `JavaDslSurfaceSpec` drives them.
- [x] **The cycle detector's nodes are every dispatching action, not only the state-machine-level containers.** An inline container and a conditional are each registered under their id in the enclosing scope, so a sibling — or one of their own descendants — can name them, and a self-reference resolved and then recursed without bound at execution. Not in this section's original list, and fixed here because §4b.3 is what widens the exposure: recursion is what a nested container invites. The node table is collected once per build over both roots, the roots become every node in it (so a cycle buried under a transition-attached container is entered at all), and the edge lists stay over-approximate exactly as before. Only an id that **resolves** becomes a node: a transition-attached container is registered nowhere, so nothing can name it and it lies on no cycle — entering it would let its id answer for a same-named container's edges, which both rejects sound definitions and hides real cycles.
- [x] Specs: `OperationDefImplSpec` gains scope visibility for an inline container's ids (reachable from inside, rejected from a sibling); `StateMachineImplCompensationSpec` gains an inline container's additive compensation unwinding members-first inside its parent; an `executedPath` case at three levels. Also a container declared in a branch, the fork walk descending into an inline container, id collisions across the nesting boundary, and the context-boundary rejection.

### 4b.4 Transition slot accepts an inline conditional
*Independent of the rest; small.*
- [x] `TransitionDef.conditional(String id, Consumer<ConditionalOperationDef<T, C>> configurer)`, beside the existing `step(...)` and `operation(...)` attachment forms. The slot still takes no `fork` — nothing continues past it. No `Identifiable` sibling: §4b.5 removes that family, and adding one here would be adding it to delete it.
- [x] **`ConditionalOperationDefImpl` joins the sealed `ActionDefImpl` hierarchy** — the revisit `CLAUDE.md` deferred to exactly this point, since `attachAction` takes an `ActionDefImpl` and a wrapper is ruled out by `requirements.md` §3.4 ("neither form needs a wrapper to reach a position the other can occupy"). It is a net deletion: the 18 listener overloads, `getListeners`, `withCompensation` ×2, `forException` and the two sinks it hand-rolled *because* it could not inherit them all go. `declaresFork()` and the cycle detector's edge source become hooks, which also fixes a latent bug — `definitionForks()` asked `instanceof OperationDefImpl`, so an attached conditional whose branch forks would have built with no executor.
- [x] **A conditional owns its members' scope**, parented on the nearest enclosing one. Every branch reaches what any branch declares, so a step common to several is declared once, while a sibling of the conditional cannot reach in; previously only the first half held, since branch members registered into the enclosing container's scope. `ConditionalBranchExecutor` pushes that scope while dispatching, capturing it at construction so an earlier machine keeps the scope it was built with. The scope field and the flatten / collect / scan walks over it moved to `ActionDefImpl` and are written once — two forms own scopes now, and a hand-copied transitive descent is how three walks previously missed containers declared inside a branch.
- [x] `JavaDslSurface` and `JavaDslSurfaceSpec` gain the shape; specs cover attachment, path reporting (`route/branch-member`, with no synthetic level), the default-branch fall-through, the `NoMatchBehavior.ERROR` case failing the transition, branches sharing the attached conditional's scope, and a fork declared inside an attached conditional's branch still building a pool.

- [x] **A conditional registers at state-machine level too** — `StateMachineDef.conditional(id, Class<C>, cfg)` and its `forContext` sibling — closing the other half of the deferred decision, which `requirements.md` §3.4.3 already promised ("registered under `operations:` and referenced with `run:`") and the Phase 5 mapper needs. `smCompositeOperations` widens from `OperationDefImpl` to `ActionDefImpl`; every pass over it already went through a hook, so only the loop variables changed. It shares one namespace with steps, operations and conditions, and is a cycle node like any other registered action.

### 4b.5 API shape: identity, and where a context is declared
*Three linked breaking changes to the DSL surface, taken as one item because each rewrites `JavaDslSurface` and `ActionSequenceSpec`'s golden list — done separately, that happens three times. Pre-1.0, and the README already declares the API unstable. Lands **before** §4b.6, since the fork declaration verbs must mirror whatever shape this settles.*

- [ ] **Drop the `Identifiable` overloads.** 191 declarations across the public API (672 counting impl overrides) exist only to take an enum where a `String` id is wanted. The safety they advertise is not delivered: `Identifiable` is a *single untyped* interface, so `run(MyStates.TRIAL)` compiles where an action id is expected, and what a host actually gets is scoped constants — which a `States` class of `static final String` already gives for free. The cost is ×2 on every one-id method and ×4 on every two-id method, which is where the surface explodes. The rule was already unenforceable in practice: **`run(Identifiable, ContextMapper)` and `fork(Identifiable, ContextMapper)` do not exist**, so an enum-tagged action id already cannot carry an inline mapper, and neither the stated parity rule nor `ActionSequenceSpec`'s golden list caught it. Call sites write `.getId()`. The `Identifiable` *interface* stays — every `*Def` implements it, and that is how a def reports its own id.
- [ ] **Drop `OperationDef.usingContext(Class<C>)`.** It returns `SELF` rather than a re-typed def, so inside `operation(id, cfg)` the only compilable argument is the enclosing `C` restated — it structurally cannot do what its name promises, which is why it is wired to nothing but the binding DEBUG log tag. The context-compatibility validation reads `componentContextTypes`, populated by the typed *registration* overload and never by this method. **`TransitionDef.usingContext` stays**: `<C2> TransitionDef<T, C2>` genuinely re-types, and a transition has one action slot, so the re-type cannot strand a member declared before it — an operation holds an ordered list, where it could. **`forContext(Class<C>, scope -> ...)` stays**: it types registrations, a different job that keeps its own verb.
- [ ] **A context is declared where the action is declared**, in both DSLs. For a registered component that is the registration (`smd.operation(id, Class<C>, cfg)` ↔ YAML's `context:` key under `operations:`); for an inline one the call site *is* the declaration site, so both DSLs put context and mapper on the same entry and there is nothing to reconcile. Each inline declaration verb gains two shapes beside the inheriting one — distinct arities, no erasure hazard:
  ```java
  operation(String id, Consumer<OperationDef<T, C>> cfg);                                 // inherits C
  operation(String id, Class<N> ctx, Consumer<OperationDef<T, N>> cfg);                   // pass-through, N from C
  operation(String id, Class<N> ctx, ContextMapper<C, N> mapper, Consumer<...> cfg);      // mapped
  ```
  This also settles two things the current arrangement gets wrong for want of a place to say the context: a registered action's inline members are tagged `Object` in the binding log unless its configurer separately restates the type (true of a container today, and unfixable for a conditional, which has no `usingContext` at all), and the fork-boundary warning's `operationId=` key names whichever position owns the context rather than an operation. Answering "why can `run(id, mapper)` cross a context boundary when an inline declaration cannot?" — it now can. The runtime needs almost nothing: `ActionRef.InlineOperation` overrides `mapperRef()`, and `bindMembers` already resolves a `ResolvedContextMapping` for every member regardless of kind. With `Identifiable` gone this is 3 methods per verb, not 12.
- [ ] **The fork-boundary warning's advice is rewritten with the rest of the context story.** It currently says "declare `usingContext(...)`, implement `ForkableContext`, or map at the call site", and names `operationId=`. Both are wrong once a conditional can hold the fork: a conditional has no `usingContext`, and for a transition-attached one the actual fix is `transitionsTo(target, id, Class<C>, ...)`. Since this item removes `OperationDef.usingContext` outright, the message is reworded once here rather than twice — it should name the position that owns the context and the way *that* position declares one.
- [ ] `JavaDslSurface` is rewritten against the reduced surface — it is the only check that the remaining overloads still resolve for a Java caller — and `ActionSequenceSpec`'s golden list shrinks to match. Every spec passing an enum to a DSL method moves to `.getId()`.
- [ ] `CLAUDE.md`: the "**`Identifiable` overload parity**" rule goes, along with its two documented exceptions; the "`forContext` vs `usingContext`" paragraph narrows to transitions; the erasure and verb-count paragraphs drop the `Identifiable` term from their arithmetic. `requirements.md` §2.2.1 and §4 lose the enum-id examples.

### 4b.6 Inline forked declarations
*Deferred from §4.3.2 with the name `forkStep` reserved; lands here because once the grammar is declared once, a declaration verb per authored form costs ten methods rather than thirty.*
- [ ] `forkStep(...)` (6 overloads mirroring `step`), `forkOperation(...)` (2, mirroring `operation`) and `forkConditional(...)` (2, mirroring `conditional`) on `ActionSequence`. They cannot be overloads of `fork` — an implicitly-typed lambda is applicable to `ContextMapper<C, ?>` and to `Consumer<StepDef<T, C>>` alike — so the `fork` prefix keeps the asynchronous surface together under autocomplete while the suffix names the form.
- [ ] Runtime: the same `ActionRef` carrying the same fork flag; an inline forked member never carries a mapper, so the context is `ForkableContext.fork()` or the shared reference, with the §4.3.1 warning applying per member.
- [ ] `JavaDslSurface` gains each verb at a container position and a branch position; `JavaDslSurfaceSpec` drives them; `StateMachineImplForkSpec` gains an inline forked step, an inline forked operation whose members run in order on the worker, and an inline forked conditional.
