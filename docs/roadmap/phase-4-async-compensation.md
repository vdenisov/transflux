## Phase 4: Async Operations & Error Handling (v0.4.0)
*Target: The compensation engine, async anchoring, and exception-specific recovery.*

### 4.1 Compensation Engine
*§3.8 already delivered the dynamic half: one `Compensation<T, C>` interface, captured before every action runs and pushed onto the single per-execution LIFO stack. What remains here is the static def-side declaration and the routing.*
- [x] A single `Compensation<T, C>` interface (entity + context), declarable by **any** action in either authoring form.
- [x] LIFO compensation stack management. **One stack per synchronous execution path.** Nested actions push onto the enclosing execution's stack so unwinding interleaves child and sibling compensations correctly. Async branches own their own stack — see §4.4.
- [x] Compensation registration before each action runs (so an action that throws partway through producing side effects still gets its compensation invoked).
- [x] **`withCompensation(...)` on the def side.** An imperative action can return its compensation dynamically from `getCompensation(entity, context)`; a declarative container has no Java object to hang that on and needs a static declaration on its def. §3.8 documented the intended semantics without shipping the DSL: a container's compensation is **additive** (its own and its members' all run), and because the container is pushed on entry its compensation runs even when the first member fails immediately. (Shipped on `ActionDef` in instance and class forms (§4b.5.1 has since dropped the class form), return-type narrowed on `StepDef` / `OperationDef` / `ConditionalOperationDef`, and reachable from every declaration position through the configurer forms that already exist — no new declaration overloads were needed. The declaration rides on `BoundAction` alongside the id, kind and listeners, and `ExecutingTransitionImpl.runAction` is the single point that decides between the two channels. **A declaration wins over `getCompensation`**, which is then not consulted at all: the declaration site is the more specific statement, and one action to one compensation keeps `compensatedPath` from carrying the same qualified path twice. The bare instance and class member forms on a container still have no def, so — as with listeners — they carry no declaration. The precedence rule stated here held only as long as the declaration was unconditional; §4.2 turned it into a chain.)
- [x] **Post-condition violation triggers full compensation; entity state is *not* applied.** `executeTransitionInternal` used to return from the post-condition branch without draining the stack, so that path reported an empty `compensatedPath` even when actions had registered compensations. (The violation now *throws* the same `TransfluxValidationException` it used to return, so it unwinds through the catch that already drains, reports `compensatedPath`, and notifies `onError` — the path a post-condition that *throws* always took. The state applier sits below the throw and is skipped.)
- [x] **Found during the work: observers could dispatch, and the pre-condition path proved it.** Review of the post-condition fix asked why the *pre*-condition rejections a few lines above still return without draining. They receive the live view, so a pre-condition calling `view.run(...)` followed by a second one returning `false` discarded that action's compensations silently — and an expression-based condition could reach the same dispatch through SpEL's `#transition`. Rather than making pre-conditions drain too, the capability was removed: `Transition` is now the read-only runtime view and the new `ExecutingTransition<T, C>` carries `run(...)`, handed only to an action's body. Conditions, branch conditions, data-trigger gates and all three listener kinds take the read-only type, which makes the pre-condition `return` correct by construction — nothing can have been pushed. Payload records dropped the type parameters only the old type needed (`ActionExecution` is non-generic, `TransitionExecution<T>` lost its `C`), and `TransitionImpl` copies the three topology strings instead of wrapping its `BoundTransition`, since SpEL resolves `#transition` reflectively against the runtime object and a wrapper would expose the resolved graph.
- [x] **Found during the work: a compensation was invoked against the wrong context.** `Compensation.compensate` documents a context "matching what was passed to the original `execute(...)` call", but the drain handed every compensation the *transition's* context. Dynamic compensations got away with it by closing over the child context and ignoring the parameter; a declared `Compensation<T, ChildCtx>` behind a `ContextMapper` would not have. `BoundCompensation` now carries the effective context from push time and the drain hands it back.

### 4.2 Exception-Specific Compensation
*Shipped. The grammar that landed is `forException(...)`, not the `onException(...)` / `onAllExceptions(...)` pair this section asked for; the reasons sit under the items.*
- [x] **The route DSL, on every action def rather than only on declarative containers.** `forException(Class<X>)` opens a `CompensationRouteDef` carrying an optional `matching(Predicate<X>)` guard and a terminal `withCompensation(instance | class)` that hands the action def back, so routes chain off the same fluent position everything else on a def does. (Restricting them to containers would have put the declaration one level away from the code that knows: a gateway timeout and a card decline roll back differently and both come out of one `charge-card` step. `onAllExceptions(...)` was dropped rather than implemented — `withCompensation(...)` from §4.1 already *is* the unconditional declaration, so it became the fallback of the chain, and a second spelling of it would only have raised the question of which of the two wins. The route deliberately is not a `ConfigurableDefImpl`: it has no id, name, description or children, and it borrows the owning def's configurer guard instead of carrying a second copy — the same borrowing `ActionListenerSink` does. Storage and validation for the whole surface, fallback and routes together, live in one `CompensationSink` that both `ActionDefImpl` and the conditional drive, which is what keeps the conditional's position outside the sealed hierarchy from costing a second implementation.)
- [x] **Matching by class hierarchy plus an optional predicate.** A route answers when the failure is an instance of its declared type — subclasses included — and then when its guard accepts. (The guard is consulted only after the type held, so it is handed the failure already narrowed to `X`; that is what the extra type parameter on `CompensationRouteDef` buys, and it is why widening the guard to `Predicate<Throwable>` at bind time is safe. **A guard that throws is a non-match, not a second failure** — this runs inside a drain that is already unwinding one, and letting a second one out would lose the first. Same posture as a compensation that throws mid-drain.)
- [x] **Chaining and ordering: first match in declaration order, and exactly one compensation per action.** The rule a conditional's branches obey, and the one a Java `catch` chain obeys. (Not several compensations running for the same action, which is the other thing "chaining" could have meant: that would put the same qualified path on `compensatedPath` twice, which is precisely what §4.1's one-action-one-compensation rule exists to prevent. An unguarded route on a broad type therefore shadows every narrower route declared after it, exactly as the equivalent `catch` would.)
- [x] **Found during the work: §4.1's precedence rule had to become a chain.** That rule was "a def-side declaration wins over `getCompensation`, which is then not consulted at all", and it does not survive routes: a route that misses has said nothing about this failure and must not veto on the action's behalf. The rollback is now the first of three things that answers — a matching route, the declared fallback, then `getCompensation` — so a def declaring *only* routes no longer suppresses the dynamic hook, while a def declaring a fallback still does, since that fallback answers everything anyway. The fold happens at push time in `ExecutingTransitionImpl.resolveRouter` rather than at the drain, because the hook is documented to see the same references `execute` will, and that is only true before `execute` runs.
- [x] **Found during the work: every stack entry routes against the transition's failure, not one it threw itself.** Most entries on the stack never threw anything — they completed, and are being rolled back because something later did. So a route is matched against the throwable that ended the transition, which is the same one for every entry in a single drain. Worth stating in the JavaDoc, since `forException` reads like "when *this* action throws" and it is not that.
- [x] **Found during the work: two build-time checks the continuation shape needs.** A route opened and never closed with `withCompensation(...)` is the one mistake the fluent shape can hide, so the build rejects it by name instead of letting the route silently declare nothing. And a route an earlier unguarded route on a supertype provably swallows gets a WARN — a warning rather than an error, because an earlier *guarded* route may reject exactly the cases the later one wants and the framework cannot tell, so only the provable case is reported.
- [x] **"Nothing answers" is a real outcome, not a hole.** An action carrying routes that all miss and no fallback of any kind is not rolled back and does not appear on `compensatedPath`, which reports what actually ran rather than what was eligible to. The drain's INFO line says `candidates=` for that reason.

### 4.3 Async Operation Support
*Shipped, and not as an `async` block: async became a property of a member position, spelled `fork(...)`. The reasoning is under the first item, and it is the change that made the rest of this section smaller.*
- [x] **`fork(...)` on declarative containers, in place of the anchored `async` block.** The seven overloads `run(...)` has, at the same positions, with the same call-site grammar - so a forked member reads as what it is, an ordinary member that the container does not wait for. (The block's only content was its anchor, and the anchor's own justification was the join point: "anchor `startBefore(stepD)` so the async kicks off as soon as the branches converge". A member list already expresses that position - declaring the member after the conditional and before `stepD` *is* the join point - so `startBefore(x)` was a named spelling of "the position before x", and `startAfter(x)` of "the position after x". Dropping both deleted four types, a block id in the SM-wide namespace, a path segment, and five of the seven build-time checks the block needed, and left the runtime unchanged: each member was already its own branch with its own fork and its own stack, so the block grouped things that shared no context, no lifecycle and no outcome. It also brings YAML closer rather than further: §3.1.1 already spells async as a per-component `config: { async: true }` flag.)
- [x] **Anchor forms** - dropped with the block. Position is the anchor. `startAfter`'s "only when the named member succeeded" falls out for free: a member declared after one that throws never runs.
- [x] **Configurable thread pool and queue capacity.** `withAsyncPool(threads, queueCapacity[, ThreadFactory])`, or `withAsyncPool()` for the default sizing; or `withAsyncExecutor(...)` to supply one. (The default was a fixed ten threads and a hundred slots until §4.3.2 made `withAsyncPool()` a statement a host would actually write, at which point a fixed number became one the host copied; it now scales as `max(4, 2 × processors)` threads and ten slots per thread, documented as the current choice rather than a contract.) (Both live on `StateMachineDef` rather than in the `TransfluxConfiguration` of §4.10.1, because the state machine is the thing that can own a pool's lifecycle: `StateMachine` is now `AutoCloseable`, and `close()` shuts down a pool the framework built while leaving a host-supplied executor alone. Core threads time out, so an idle machine holds no threads; the threads are daemons, so a host that forgets to close can still exit.)
- [x] **Async result handling and callbacks** - answered as **fire-and-forget**, which is what the section was missing rather than a feature it was missing. `TransitionResult` is unchanged: a forked member appears on neither `executedPath` nor `compensatedPath`, its failure never reaches the caller, and hosts observe branches through the action listeners already attached to those actions. (Both spec cross-references for this - §4.5.3.2's "§4.10" and §4.5.2.7's "the standard async result-handling rules" - pointed at sections that contained nothing of the kind. There was no design to follow, so there is one now.)
- [x] **Async operation cancellation semantics** - **none, deliberately.** Submission is the commitment point: once a branch is handed to the executor it runs, whatever the sync path does afterwards. §4.4 already said an async failure never triggers sync compensation; this is the same rule read in the other direction, and it removes the interrupt policy that a cancellation API would have needed. What a *refused* submission does is the host's call instead, through `withAsyncRejectionPolicy(...)` - `DROP` (the default) warns and loses that branch, `FAIL` fails the transition.
- [x] **Found during the work: an acquisition failure is not a rejection.** Both surface on the submitting thread, and they look alike, but a `mapTo` or `fork()` that throws is host code that is broken and always fails the transition (§4.5.2.7's existing attribution rule, which async does not get to override), while a refused submission is a saturated or closed pool and obeys the policy above. The default makes them behave differently on purpose.
- [x] **Found during the work: `run(id, lambda)` never compiled, and the fork surface inherited it.** `run(String, Function<C, ?>)` and `run(String, ContextMapper<C, ?>)` both carry the descriptor `(P) -> N`, so an implicitly-typed lambda matches both and javac refuses the call - a shape `requirements.md` documented as supported, on `OperationDef` and on `ExecutingTransition` alike, uncallable except through a cast. It survived because **every spec in the repo is Groovy**, and Groovy resolves overloads at runtime against the argument's actual class rather than running Java's applicability analysis: the specs exercised the *method*, never the *call shape*. The `Function` overload is now gone from both surfaces (a lambda already is a `ContextMapper`, and its `mapFrom` defaults to the no-op), `MapperRef.InlineFunction` went with it, and `src/test/java` now exists so the DSL has a Java caller - `JavaDslSurface` holds every call shape and fails `test-compile` if one stops resolving, with `JavaDslSurfaceSpec` driving it so the shapes are proven wired as well as legal. It earned its keep immediately: it rejected two call shapes written from memory while it was being added.
- [x] **Found during the work: the inline declaration form cannot be an overload of `fork`.** `fork(String, Function<C,?>)` and `fork(String, ContextMapper<C,?>)` are needed for the call-site mapper, and an implicitly-typed lambda is applicable to both of those *and* to `Consumer<StepDef<T,C>>` - the erasure trap behind the "one lambda-shaped overload per name" rule, and the reason `mapperDef` is not called `mapper`. Inline forked declarations are deferred with the name `forkStep(...)` reserved; see the open items below.

#### 4.3.1 Async Context Handling (requirements §4.5.3)
*Shipped alongside §4.3, which could not be built without it: a branch has to get its context from somewhere.*
- [x] `ForkableContext<C>` interface with single `C fork()` method, in `core.action` beside `ContextMapper` - the type it competes with at the same call site.
- [x] **Runtime fork-at-boundary**, once per forked member rather than once per group, on the submitting thread and before the branch is handed over. A `fork()` returning `null` is rejected as a broken implementation.
- [x] **`ContextMapper` on a forked call site**, through the same overloads a synchronous reference has: `fork("id", "mapperId")`, `fork("id", parent -> child)`, `fork("id", mapperInstance)`. `mapFrom` is not applied to a forked member, and that is structural rather than policed: the branch is run with a `null` mapper because `mapTo` already ran at submission, so `runAction`'s write-back call is unreachable for it. (This section asked for a definition-time *rejection* of an overriding `mapFrom`, and one shipped briefly before being removed. The check asked which class declares the erased two-argument form, which is right for a lambda and for a plain implementation but wrong for every JDK dynamic proxy: a proxy declares each interface method itself, defaults included, so an AOP-proxied or mocked mapper failed the build with a message about an override it does not have. Since the behaviour is already correct without the check, and proxied components are on the roadmap, the check went rather than the capability.)
- [x] **Definition-time warning**, per *member* rather than per group - a container may mix a mapped member with an unmapped one, and only the unmapped one is sharing. Silent when the member maps, when the context type is `Void`, or when it implements `ForkableContext`; a distinct "forkability cannot be checked" message when the declared type is `Object`, which is the honest answer for a type the framework can prove nothing about. On `build.validation`, with the rest of the definition-time noise.
- [x] **Documented memory-model guarantees.** The executor submission's happens-before edge is the only synchronisation in the design, which is what makes §4.5.3.4's other two bullets true by construction rather than by promise. Two additions the section was missing: the entity is unsynchronised across the boundary too, and a shared `Action` / `ActionListener` / `Compensation` instance can now run on two threads at once.
- [ ] **`JacksonForkableContext` - deferred, and its premise corrected.** "Jackson is already a core dependency" is wrong: the pom carries `jackson-core` only, and a round-trip `fork()` needs `ObjectMapper` from `jackson-databind`. Shipping the adapter means adding a dependency for something a host writes in four lines against its own mapper, so it waits for someone to ask.
- [x] Specs: `StateMachineImplForkContextSpec` covers fork-once-per-member on the submitting thread, mapper-beats-fork, the shared-reference fallback, a throwing `fork()` and a throwing `mapTo` both failing the transition, and a branch compensation receiving the branch's own context; `OperationDefImplForkValidationSpec` covers the `mapFrom` rejection in all four call-site forms and every case of the warning; `ReflectionUtilsSpec` pins the bridge-method detection.

#### 4.3.2 Deferred from the fork work

- [x] **Inline forked declarations, reserved as `forkStep(...)`** - shipped in [Phase 4b §4b.6](../history/phase-4b-action-sequence-grammar.md) as `forkStep` / `forkOperation` / `forkConditional` on the shared `ActionSequence` grammar. Both constraints found here held: it is not an overload of `fork` (the erasure note in §4.3), and it needed the inline `operation(...)` member form Phase 4b §4b.3 added.
- [x] ~~**A per-fork rejection-policy override.**~~ Superseded by §4.3.3, which puts the policy on the def rather than the call site — the arithmetic that made it fourteen overloads was the call-site placement, and the "separate executor" answer to mixed criticality stopped being the only one once `BLOCK` existed.

- [x] **`fork(...)` on `ExecutingTransition`.** Shipped as the six by-id forms `ActionSequence` already carries - three call shapes, each with and without a policy - so the body surface now holds the whole *reference* half of the grammar and none of the declaring half. Both open questions resolved as stated rather than needing a design. (a) The policy is not build-verifiable from a body, so `submitAsync` refuses `BLOCK` against a host-supplied executor itself, reusing `StateMachineDefImpl.blockUnavailable(...)` so the two messages cannot drift. It refuses **eagerly, at every submission** rather than only at a rejection: the build rejects the same declaration whether or not it is ever forked, and a policy that could never be honoured should fail the first time it is used rather than the first time a queue happens to fill. (b) A fork from inside a *forked* body is legal, and needed no code - the ban is on driving the machine, the declarative side already permits the same nesting, and `BLOCK`'s self-deadlock was already answered by the inline-run escape. The branch's lexical position also fell out for free: `submitBranch` seeds it from the nesting and scope stacks, which at that moment already hold the calling action, so a body-forked branch qualifies under its caller and resolves `run(id)` against the scope the body saw.

- [x] **Found during the work: nothing built a pool for a fork the build cannot see.** `definitionForks()` walks *declared* members, so a state machine whose only forks are written in Java bodies built no executor and failed at the first fork with "this state machine was built believing it had none" - technically true and useless. `withAsyncPool(...)` is now the second reason to build one: declaring a pool *is* the definition saying it forks. `withAsyncExecutor(...)` already worked, since a host-supplied executor is taken unconditionally. The alternatives were building a pool for every machine (drops the guarantee that a non-forking definition holds no threads and no queue) and building one lazily on first submission (a lock, and a build-time INFO that stops being a build-time event); asking is cheaper than both and is a statement the host has to be able to make anyway.

- [x] **Found during the work: `submitBranch` checked nothing about the context it hands over.** A declarative forked member is checked at build, so the gap was invisible - but an imperative call site has the callee's declared type in hand and nothing that could have checked it earlier. `submitBranch` now takes the callee's context type (`null` from a declared member, exactly as `runAction`'s two forms already differ) and applies the same `requireMappedContextAccepted` a mapped `run` gets. Unchecked, a mapper producing the wrong type or `null` surfaced as a `ClassCastException` on a worker thread, swallowed into a branch WARN that nothing joins.

- [x] **Found during the work: three definition-time facilities silently do not cover a body fork**, all for the same reason - `visitActionDefs` and `anyMember` walk declarations. The shared-context warning (§4.3.1) is not emitted; `declaresBlockingRejection()` does not see a body-chosen `BLOCK`, so it waits on an unfair queue (ordering under contention, never correctness); and `checkBlockingIsPossible` is the one whose absence mattered, which is what the runtime refusal above replaces. Documented in `requirements.md` §4.5.2.1 / §4.5.3.3 and CLAUDE.md rather than patched: a Java body is opaque to the definition by construction, and the honest answer is to say which guarantees stop at that line.

- [x] Specs: `ExecutingTransitionForkSpec` covers the three call shapes, the branch reaching neither reported path, the path nesting under the calling action, lexical `run(id)` inside the branch, a fork issued from a body already on a branch, the pool-opt-in failure and its fix, the eager `BLOCK` refusal, policy precedence in both directions, and the mapped-context guard for a wrong type and for `null`. `StateMachineImplAsyncExecutorSpec` covers a pool built from `withAsyncPool(...)` alone; `JavaDslSurface.forkFromActionBody()` pins all six call shapes for a Java caller.


#### 4.3.3 Async Rejection Policies
*Two policies and one grain were the wrong shape for the cases that actually turn up. A metrics ping may be skipped and must never fail the transition; an audit write must not be skipped and may wait; a user notification is the same but must still happen after the pool is gone. `DROP` and `FAIL` cover the first, and the machine-wide grain cannot say different things about the two. §4.5's async listeners have the same three cases and are built on this, so it lands first. A note on point 2 of the discussion that shaped this: `ExecutingTransition` carried `run` but no `fork` and gained one as its own item (§4.3.2); under the placement chosen here a policy chosen from inside a Java body is the one thing the build cannot see, and is refused at the submission instead.*

- [x] **Two more policies, and a rename.** `BLOCK` waits for a slot; `CALLER_RUNS` runs the work on the submitting thread. `AsyncRejectionPolicy` becomes `AsyncRejectionPolicy` — it now governs listeners too, and `requirements.md` §3.8 already spells the YAML block `async: { onRejection: ... }`, not `fork:`. (`CALLER_RUNS` was rejected once, as the pool's *default* handler, because it silently ran a branch mid-transition; as an explicit choice it is the one policy that still executes the work after `close()`, which `BLOCK` can never do.)
- [x] **`BLOCK` waits inside a `RejectedExecutionHandler`, and the framework meters nothing itself.** This bullet originally proposed a semaphore bounding submissions, sized `threads + queueCapacity`, with a `withAsyncExecutor(executor, maxInFlight)` overload so a host executor could be metered too. That shipped, was reviewed, and was withdrawn — see the note below. What replaced it: `AsyncRejectionHandler`, installed only on a pool the framework builds, answers `BLOCK` with `getQueue().put(...)` and declines every other policy by throwing, so `DROP` / `FAIL` / `CALLER_RUNS` keep one decision site in `submitAsync`'s catch, shared with the host-executor path. The policy rides on an `AsyncWork` record, since a handler is handed the `Runnable` and nothing else. No timeout on the wait, consistent with §4.4. The `maxQueued` overload is gone with the semaphore: `BLOCK` now requires the framework's own pool and fails the build against a host executor, naming the def. A host that wants blocking back-pressure installs a blocking handler on its own pool, where the queue is actually theirs to see.

- [x] **Found during the work: metering admission ourselves refused branches the executor would have taken.** A `ThreadPoolExecutor` accepts `threads` running *plus* `queueCapacity` queued, and a task handed straight to a new worker as `firstTask` never enters the queue — yet it holds its permit until it starts. Sizing the semaphore on queue capacity therefore collapsed admission to `queueCapacity`, silently under the default `DROP`; sizing it `threads + queueCapacity` instead broke `BLOCK`'s guarantee, because the queue can be full while a permit is held. Neither size is right, which is the tell: a second copy of a number the executor already knows exactly is a copy that can disagree with it. Two further defects fell out of the same design and are gone with it — a permit leaked by any accepted-but-never-run task (`shutdownNow()`, a discarding handler), which under `BLOCK` was an unbounded hang rather than a refusal; and a non-fair semaphore that let the fast path barge past a parked waiter. The queue is now made fair only when the definition actually declares `BLOCK`, so the fair lock is not charged to machines that never wait.

- [x] **Found during the work: `getQueue().put(...)` is off-label, and that is the real constraint on `BLOCK`.** `ThreadPoolExecutor.getQueue()` is documented as being for monitoring. The blocking-handler pattern is nevertheless the standard one, and it is sound here for a narrow reason: the framework built this pool, so it knows the queue is bounded and that the worker count cannot be zero while the queue is full. It needs the two-sided shutdown check — `isShutdown()` before the `put`, and `isShutdown() && queue.remove(work)` after it — or a task lands in a queue nobody will drain.
- [x] **`BLOCK` after `close()`** cannot ever succeed. A fork throws `RejectedExecutionException`, failing the transition — the host said this work must not be lost, and it is about to be; a listener is dropped with a WARN, because a listener has nothing else it can do. That asymmetry is the argument for `CALLER_RUNS` on a listener that matters.
- [x] **`CALLER_RUNS` changes the thread and nothing else.** A branch run inline is still its own stack and its own drain, its failure is still logged and swallowed rather than propagated, it is still on neither reported path, and the submitting thread is under the async-branch ban for the duration (`enterAsyncBranch()` / `exitAsyncBranch()` around the inline run). The alternative — "when async cannot be honoured, behave as if it was never declared" — would make the ban depend on which path a given invocation took.
- [x] **The policy is a property of the submission, and three parties can speak for one.** This bullet first said "the def, not the call site", on the grounds that criticality is a property of the work; the use cases said otherwise. An audit listener knows it must not be dropped, whatever attaches it. A notification step does not know — it is droppable in one flow and not in another, and only the flow forking it can say. And one operation forking a metrics update, a notification and a cache write needs three answers in one sequence, which no single grain above the member can give. So: **the position** wins (`fork(id[, mapper], policy)` on the three by-id forms), else **the def** (`ActionDef.withAsyncRejectionPolicy(...)`, inherited by step / operation / conditional and read only when the action is reached through a `fork*` verb), else **the machine** (`withAsyncRejectionPolicy(...)`, renamed with the enum). An inline forked declaration is its own position and declares on the def it declares; the bare instance member forms, which have no def and already carry no listeners and no compensation, take the machine default. The def's declaration is a default a position may override, not a floor — most-specific-wins is the rule compensation and context already follow, and a caller weakening `audit` to `DROP` does it at a named, reviewable position. Resolved once at bind time onto `CompositeMember`, beside the `forked` flag.

- [x] **Found during the work: the overload arithmetic against call-site placement was wrong.** §4.3.2 costed it at fourteen and "every later addition doubles again", and that was repeated here. It predates Phase 4b's own insight: an inline declaration's call site *is* its def, so `forkStep` / `forkOperation` / `forkConditional` with a configurer already carry the def-side setter with no new overloads. Only the three by-id `fork` forms have no configurer, and the instance-form `forkStep(id, Action)` carries no declaration of any kind by precedent. Call-site placement costs three overloads, and `ActionSequenceSpec`'s golden list grew by exactly that.
- [x] **`FAIL` has no meaning on a listener** and is rejected - at the `withAsync(FAIL)` call rather than at build, as it shipped with §4.5. At `onStart` / `EXIT` it could throw into the drain, but at `onComplete` / `ENTRY` the applier has already committed and there is no transition left to fail, and a policy whose meaning depends on the hook is the mistake §4.7.3 refused elsewhere. A listener admits `DROP` / `BLOCK` / `CALLER_RUNS` and defaults to `DROP`, independent of the machine-wide default. The listener-side surface itself ships with §4.5.
- [x] **Found during the work: the saturation lines were WARN per submission.** Which is a line per forked member for as long as the pool stays saturated - the state the policy exists to handle, and the moment a host least wants its log budget spent. CLAUDE.md's own table caps WARN at "rare" and keeps even INFO off the per-transition path, so both the blocked-submission and inline-run lines became DEBUG per occurrence with one WARN on entering the state. Sustained saturation is a metrics question, not a logging one.

- [x] **Found during the work: a mapper returning `null` slipped past the call-site guard.** `requireMappedContextAccepted` exempted a null child, mirroring the pass-through check that exempts a null caller context - but the two nulls are different. Pass-through's is the caller legitimately having none; a mapped null is host code, at the very call site the guard exists to name, answering "produce a context for this callee" with nothing. It now fails there rather than as an NPE inside the callee, matching what `ForkableContext.fork()` already did. (Carried over from Phase 4b, whose code this is; it shipped with no coverage either way.) **This is a behaviour change, not only a better diagnostic**, and the one place it can bite: a callee written to tolerate a null context, reached through a projection that is legitimately absent - `run("charge", ctx -> ctx.getPayment())` with no payment - used to run and now fails the transition. Nothing signals it at build time, and the pass-through guard two methods away still admits a null caller context, so the asymmetry is invisible from the DSL. The answer for that shape is the one the model already has: a component that runs with or without a context registers under `Object.class`, which both guards exempt.

- [x] **Observability, not policing.** Any system that blocks on a pattern is at the mercy of that pattern's performance; that is a generic problem and not one to solve here. What the host needs is to hear it: one WARN on `execution.async` per blocked submission once it resumes, with the path and the time waited, so an undersized pool is visible from the log. The `MetricsCollector` SPI (§6.3) is the proper channel when it lands.
- [x] **YAML parity noted for Phase 5**: §3.8's `onRejection` gains the two values, and the per-def form is a `config.onRejection` key on the component, next to the `fork:` flag it qualifies.
- [x] Specs: `StateMachineImplAsyncRejectionSpec` covers each policy under saturation and after `close()`, the def-level override against the machine default in both directions, a bare-instance member taking the machine default, `BLOCK` against a host-supplied executor rejected at build (machine-wide and per def), the inline run carrying the reentrancy ban and keeping its failure to itself, the blocked-submission WARN, and — as the regression guard for the withdrawn semaphore — that a pool admits everything it has room for, running plus queued. `StepDefImplSpec` covers the def surface; `JavaDslSurface` gained the bounded-executor and per-def call shapes.

- [x] **Found during the work: `BLOCK` deadlocks a pool against itself, and position is what tells it apart.** A branch may fork, and it submits to the pool it is running on. On a pool of one with one queue slot, a container that forks twice fills the slot with its first fork — which cannot start until the container returns the worker — and then parks that same worker waiting for a second slot. The wait is not "bounded by the running branches' durations" when the running branch *is* the waiter. `BLOCK` therefore does not wait on a thread already running a branch of this state machine: it runs the work inline, which is the one answer that always completes, and the thread is already a branch thread so nothing about the work's isolation changes. The check is the `ASYNC_BRANCH` thread-local the reentrancy ban already consults.

### 4.4 Async Compensation
*Shipped with §4.3, which needed it: a branch cannot share the sync view, so it cannot share the stack that view carries.*
- [x] **Per-branch LIFO stack.** A branch's view starts with an empty compensation stack and its own executed path, and copies only the two stacks that describe *where* it sits - the action-nesting stack, so its qualified paths read `container/member`, and the lexical scope stack, so `run(id)` inside it still resolves against the container's inline scope. Copies, never shares: the spawning thread goes on pushing and popping its own as it walks the rest of the member list.
- [x] **Sync-failure-while-async-running semantics.** Each side drains its own, and neither waits for the other. The drain itself is now one implementation (`CompensationDrain`) with two entry points, so the routing, the "record only once the table answers" rule and the `Exception`-not-`Error` posture cannot drift apart between them.
- [x] Async-branch failure does not trigger sync compensation, and the transition's result is untouched by it. Surfacing is §4.3's fire-and-forget answer: a WARN on `execution.async` naming the path and the throwable type, then that branch's own drain.
- [ ] **Timeout handling - dropped with cancellation.** A timeout is only meaningful if something can act on the deadline, and nothing can: there is no handle, no interrupt policy, and interrupting a branch mid-compensation is the hazard that ruled cancellation out. A host that wants a deadline enforces it inside its own action, where it knows what is safe to abandon.

### 4.5 Async Listener Execution
*Moved here from Phase 3.5, which shipped state and transition listeners synchronously. Phase 3 asked for "basic" async listener support, but the executor, pool sizing, and queueing are exactly what this phase owns — building a listener-specific dispatch ahead of it would mean designing the same thing twice.*

*The dependency this was waiting on is now settled: §4.3 shipped the executor, its configuration and its lifecycle, so an async listener dispatches through `StateMachineImpl`'s pool rather than one of its own. Two of the open questions below also have precedents to follow now rather than answers to invent - the fire-and-forget outcome rule, and the ban on driving the state machine from work it spawned.*

*Shipped, for all three listener categories rather than the two this section named: action listeners landed after it was written.*

- [x] **Per-listener opt-in on the def side**, as `withAsync()` / `withAsync(policy)` on `StateListenerDef`, `TransitionListenerDef` and `ActionListenerDef`, configurer form only. (One property with two overloads rather than a flag plus `withAsyncRejectionPolicy`: a policy on a synchronous listener is then unexpressible instead of a build rule. The YAML `config: { async: true, onRejection: ... }` of §3.1.1 maps onto it one-to-one. The instance form has no def and stays synchronous, the precedent compensation and fork policies set. The shared half lives on a `ListenerDefImpl` base the three impls now extend, and the public side went the same way: a self-typed `ListenerDef<L, SELF>` in `core` carries identity, `using` and `withAsync`, and the three listener def interfaces only bind it. The `Describable` question was closed on "no behaviour and no polymorphic caller"; for listener defs both now exist - `withAsync` is identical across categories, and Phase 5 applies `config` to any listener - so this family alone is reopened. It also dropped three stale `{@link #using(Class)}` references that had kept javadoc failing.)
- [x] **Rejection policy on the listener def, and only there.** `DROP` / `BLOCK` / `CALLER_RUNS`, defaulting to `DROP` whatever the machine says. `FAIL` is refused at the setter, naming the listener, rather than at build as §4.3.3 wrote it - it is a property of the argument alone. `BLOCK` against a host-supplied executor fails the build through the same `checkBlockingIsPossible`, reached by a new `visitListenerDefs` walk that also feeds pool creation and the fair-queue decision.
- [x] **Dispatch through the same pool**, via `submitAsync`. A definition whose only async work is a listener builds one.
- [x] **Semantics**, each decided rather than left open:
  - [x] *Ordering* - none promised. Notifications are submitted at the hook in declaration order, interleaved with sync listeners, and run whenever the pool runs them; an async `onComplete` may be handled before its transition's `onStart`. A per-listener serial queue was considered and rejected: its own saturation, `BLOCK` and `close()` story, for a guarantee a listener that needs it gets by staying synchronous.
  - [x] *Exceptions* - the sync rule holds on whichever thread: the invocation and its catch-and-warn travel together as one `Consumer`, so there is no second rule to keep in step.
  - [x] *Context* - `ForkableContext` applies: `fork()` on the notifying thread, once per async listener per notification, else the shared reference, as for a fork that does not map. A `fork()` that throws or returns `null` loses that notification with a WARN; unlike a fork site it cannot fail the transition, since a listener never gates.
  - [x] *Definition replaced* - submission is the commitment point, as for forks: the task captures the bound listener and payload. Nothing to build until `replaceDefinition` exists.
- [x] **Found during the work: an async listener has to carry the async-branch mark.** `AsyncWork` runs its task bare, so a listener submitted as-is would run on a worker with neither the reentrancy guard nor the branch ban - free to drive the same entity while the caller's next transition runs, and invisible to `BLOCK`'s self-deadlock escape. The task enters and exits the mark around the notification, which makes it stricter than a sync listener (no driving this machine for *any* entity) for the same reason a branch is: what it started would report to nobody.
- [x] **Found during the work: `BLOCK` after `close()` throws out of `submitAsync`.** `refuse` rethrows the rejection for `BLOCK` when no wait can help, which is right for a fork and would have escaped a notify seam here. `deliver` turns it into the same lost-notification WARN as `DROP`.
- [x] **Found during the work: volume is the real hazard, and it is per category.** A transition and its two states notify at most four times per transition; an action notifies twice per invocation at every depth, so a global async action listener scales with every action every transition runs, and a body calling `view.run(...)` in a loop multiplies it again. Under the default `DROP` that is loss at scale. Documented on `ActionListenerDef.withAsync` and in `requirements.md` §2.2.10 rather than defended against. **Decided: a lost listener notification WARNs per occurrence**, as a lost branch does, and unlike the once-then-DEBUG throttling §4.3.3 gave blocked and inline submissions. Those two are the policy working; a lost notification is data gone, and a spike of WARN lines is what makes an undersized pool or an over-eager async action listener visible, where a single WARN followed by silence would hide how much was lost.
- [x] Specs: `StateMachineImplAsyncListenerSpec` covers each category off-thread with the transition not waiting, submission order with a sync listener interleaved, a throwing async listener isolated, forked vs shared context and a failing `fork()`, the driving ban, `DROP` / `CALLER_RUNS` / `BLOCK` under refusal and saturation, `BLOCK` after `close()`, an async action listener on a forked branch, and a 1000-iteration dispatch loop overflowing the queue. `ListenerDefImplSpec` covers the declaration on all three defs; `StateMachineImplAsyncExecutorSpec` and `StateMachineImplAsyncRejectionSpec` the pool and the build check; `JavaDslSurface.asyncListenerShapes()` the Java call shapes.

### 4.6 Specifications
- [x] Compensation engine specs (LIFO order, exception routing, partial rollback, container compensation additivity). *(§4.1 brought `StateMachineImplCompensationSpec`, covering LIFO order, partial rollback, the post-condition paths, container additivity and first-member-fails, the conditional, the declared compensation at each declaration position, and the captured-context rule; `StepDefImplSpec` / `OperationDefImplSpec` / `ConditionalOperationDefImplSpec` / `ConfigurableDefImplSpec` / `ExecutingTransitionImplSpec` cover the def surface. §4.2 added `StateMachineImplExceptionRoutingSpec` for the runtime rules — subclass matching, first-match order, a guard that rejects and one that throws, the three-step precedence chain in each of its outcomes, a missed route contributing nothing to `compensatedPath`, routing against the transition's failure rather than the action's own, the post-condition path, a routed compensation behind a mapper, and a container routing independently of its members — plus `CompensationSinkSpec` and `CompensationRouteDefImplSpec` for the def surface, the unclosed-route rejection and the shadowing warning.)*

### 4.7 Logging & Diagnostics Baseline
*Pulled forward from §6.3, which carried this as a single line — "Consistent SLF4J logging with predictable logger names" — which is not enough to settle a shape. The library emitted thirteen statements when this was written, and both this phase and Phase 5 add code that should be born compliant rather than retrofitted. §6.3 now points here and keeps only the `MetricsCollector` SPI, which is a different concern (counters and timings, not "what did the framework decide"). §4.7.1 has shipped; §4.7.2 and §4.7.3 are still open.*

*Scope bound: the goal is being able to understand how the framework behaved — why a trigger fired nothing, why a YAML definition resolved the way it did. MDC keys, correlation ids, and a formally parseable record format stay post-1.0 themes. The policy itself is written up in CLAUDE.md §Logging; the items below are what implementing it requires.*

#### 4.7.1 Framework-emitted logging

#### 4.7.3 Disabling global listeners
*Motivating case: an action whose context carries sensitive data, running in a state machine whose host registered global listeners the action knows nothing about. The author wants that action observed on its own terms — typically by attaching a listener of its own that records a redacted line — without the generic globals seeing the payload.*

***Sizing this deliberately.** This is a convenience, not a security control. An application serious about PII or secret handling writes its own global listener that sanitises exactly what it needs to, and nothing we could ship competes with that. So the bar is "good enough and predictable", not "airtight" — which is what makes the deny-list below an acceptable shape rather than a defect.*

**Settled.**
- [ ] **Two forms on the def side**: disable named global listeners, and disable all of them. Nothing finer.
- [ ] **Scope is global listeners only.** An owner's own listeners always receive everything; attaching a listener to a specific owner *is* the consent, and it is also how the owner replaces what it just turned off — with whatever configuration it wants, through the same DSL the globals use.
- [ ] **Full suppression, not payload withholding.** The pattern is "replace the generic observation with a bespoke one", so notifying the global anyway — even context-free — produces a second record of the same execution. Consequence worth stating: **the public payload records do not change.** `ActionExecution` and `TransitionExecution` stay exactly as they are, and there is no `WITHOUT_CONTEXT` mode to decide about before 1.0.
- [ ] **Enforced at the `notify*` seams**, by filtering the global list on the way out. A flag that listeners are asked to honour would not be enforcement, and the listener that ignores it is the one the feature exists for.
- [ ] **The named form is a deny-list and fails open** — register a new global listener next year and owners that carefully disabled the old ones will not disable it. Accepted, given the sizing above, and it must be said plainly in the JavaDoc rather than left for a reader to infer a guarantee that was never offered.
- [ ] **A disable covers exactly the def it is declared on, never its children.** An operation that disables its global action listeners does not disable its members'; a transition that disables its global transition listeners does not touch the action listeners of the actions it runs, nor the state listeners of the states it moves between. PII-handling defs are few, so specificity beats inheritance — and inheriting would make an action's observers depend on its call site, which contradicts §2.2.10.
- [ ] **The category follows the owner.** "All globals" means all global *action* listeners on an action, all global *transition* listeners on a transition, all global *state* listeners on a state. No cross-category reach, and therefore no implicit downgrades: an earlier proposal had a marked transition silently hand global state listeners a `null` context, which was rejected — sensible in the moment, guaranteed WTF later. The consequence of the uniform rule (a transition's context still reaches global state listeners unless the state disables them too) gets documented, not patched over.
- [ ] **An unknown or non-global id fails the build.** A typo in a deny-list silently protects nothing, and that is the one failure mode this design cannot absorb. The id must name a registered global listener of the owner's own category — checked at build, for the same reason listener-id uniqueness is: a def holds no reference back to the SM def.

**DSL shape — settled.**
- [ ] **`disableGlobalListener(String id)`, repeatable**, with the `Identifiable` sibling the overload-parity rule requires. Chained one-per-call matches the rest of the DSL, which has no varargs anywhere today — pre-conditions, triggers and listeners are all declared this way. Repeats of the same id collapse: the disable list is a set, so declaring one twice is a no-op rather than an error.
- [ ] **`disableAllGlobalListeners()` wins.** When both forms appear on the same def, the blanket one takes effect and the named list becomes irrelevant — no error, and no sensitivity to the order the two were called in.
- [ ] **Carried by `ActionDef` (hence step / operation / conditional), `TransitionDef`, and `StateDef`** — one per listener category, each owner disabling globals of its own kind.
- [ ] **`disable` prefix, not `with`.** It is not a property setter. If a *configurable* form is ever wanted — binding the decision to a host config flag rather than declaring it — that one takes the setter convention: `withDisableAllGlobalListeners(config.isDisableAllGlobalListeners())`. Recorded so the naming is not re-litigated; no current need.

**DSL shape — open.**
- [ ] **Whether a plural bulk form joins the singular one.** It is less boilerplate for a consumer disabling three listeners at once, and it is safely deferrable: adding `disableGlobalListeners(...)` alongside the singular later is purely additive, breaks nothing, and can be decided on evidence once the singular is in use. Two notes for whoever decides. (a) The YAML argument is weaker than it looks — the mapper is code, not a DSL user, so it can loop over a YAML list into repeated singular calls; it needs no bulk entry point of its own. (b) Both bulk spellings collide with the `Identifiable` parity rule and need care: `(String...)` plus `(Identifiable...)` makes the no-argument call ambiguous, so it would have to be spelled `(String first, String... rest)`; and `Collection<String>` plus `Collection<Identifiable>` share an erasure and will not compile as overloads at all, so a collection form could only ever carry one of the two types.
