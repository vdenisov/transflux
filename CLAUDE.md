This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Transflux is a lightweight, embeddable microflow orchestration library (Java). It coordinates state changes for business entities — transitions, sequencing, pre-/post-conditions, triggers, listeners, and Saga-like compensations — without providing its own persistence. Project status: Phases 1 through 5 complete; next is Phase 6 (Integration, Polish & Release Prep). In Phase 5 (YAML DSL & Component System), §5.5 made `StateMachine<T>` a handle over a replaceable `StateMachineSnapshot<T>`, §5.6 split the build into modules and added the definition sourcing SPI in `transflux-yaml`, §5.7 laid the loader's infrastructure there, §5.8 reads a document's component sections, §5.8.1 moved transitions out of their source state onto the state machine, §5.9 reads the state machine itself, §5.10 reads the member grammar - every `actions:` list, forks and call-site mappers included - §5.11 reads imports and the state machine's `config:`, §5.12 shipped the JSON Schema and the corpus that keeps it and the loader in agreement, and §5.13 closed the phase: one state machine written in both DSLs and run side by side, YAML hot-swap through a definition source, and a review of every error message the corpus pins. Phase 4b (Action Sequence Grammar) interrupted Phase 4 and shipped first: every position holding an ordered list of actions — a declarative container, a choice's branch, its default branch, and a transition's body — carries one member grammar, and inline forked declarations came with it. Phase 4 (Async Operations & Error Handling) then closed: the compensation engine (§4.1), exception-specific compensation routing (§4.2), forked members with their per-branch rollback (§4.3, §4.3.1, §4.3.2 and §4.4's stacks), async listeners (§4.5), the framework-emitted logging baseline (§4.7.1), the shipped logging listeners (§4.7.2) and per-owner disabling of global listeners (§4.7.3) all landed; two items closed as won't-do (`JacksonForkableContext`, async timeouts). The public API is unstable.

`requirements.md` is the canonical spec for the vision and component model; consult it before designing new core abstractions. `todo.md` is the roadmap index (phase map, versioning policy, 1.0 contract, post-1.0 themes). Per-phase task breakdowns live one-file-per-phase: **remaining** phases under `docs/roadmap/`, **shipped** phases (verbatim) under `docs/history/`. A phase moves from `docs/roadmap/` to `docs/history/` when it ships. The toolchain/dependency/cadence baseline is in `docs/project-baseline.md`.

## Build & Test

- Modules: the root `pom.xml` is `transflux-parent`, holding the toolchain, plugins (Surefire's `**/*Spec` include, JaCoCo, GMavenPlus) and every dependency version; `transflux-core/` is the library and `transflux-yaml/` the YAML side, depending on it (the core module depends on nothing of Transflux's). Each module's paths below are relative to its own directory.
- Toolchain: Maven builds with **JDK 17+** (enforced via `maven-toolchains-plugin`) and compiles to **Java 17 bytecode** (`<release>17</release>`). A JDK 17+ must be discoverable through `~/.m2/toolchains.xml`.
- Run all tests: `mvn -q clean test`
- Run a single Spock spec: `mvn -q test -pl transflux-core -Dtest=StateMachineImplSpec`
- Run a single feature method: `mvn -q test -pl transflux-core -Dtest=StateMachineImplSpec#"feature method name"`
- Coverage report (JaCoCo, generated during `test` phase, per module): `transflux-core/target/site/jacoco/index.html`
- Surefire only picks up classes matching `**/*Spec` — Groovy/Spock specs in `src/test/groovy`. Plain JUnit tests would not be discovered without changing the include pattern.

## Architecture

The core domain is split into a public API surface (seven semantic subpackages) and a sibling implementation package:
- `core` — `Transflux` entry point, the `StateMachine` / `StateMachineDef` interfaces (the machine reports the id / name / description / version its definition declared, all nullable and copied at build), `ContextScope`, `ListenerDef<L, SELF>` (the self-typed surface all three listener defs inherit and declare nothing beyond), `ComponentFactory` (a class a definition names into an instance; `reflective()` is the no-arg-constructor default, and the YAML loader's only instantiation path), and the `Preconditions` helpers (`requireNotNull` / `requireNotBlank`) static-imported by public-API types.
- `core.state` — `State` / `StateDef`, the host-supplied `StateResolver` / `StateApplier`, and the state-listener surface: `StateListener` (a functional `onState(entity, context, change)`), its `StateListenerDef` builder, and the non-generic `StateChange` payload record (`phase` / `state` / `transition`) with its `StatePhase` (`ENTRY` / `EXIT`) discriminator. Listeners attach per state through `StateDef.onEntry(id, ...)` / `onExit(id, ...)` and to every state through `StateMachineDef.onAnyStateEntry(id, ...)` / `onAnyStateExit(id, ...)`; each hook offers instance, `Consumer<StateListenerDef<T>>` configurer, and one-argument by-id forms, the last attaching a listener registered through `StateMachineDef.stateListener(id, ...)` or declared at another of the same owner's hooks. Listener ids are required and form their own state-machine-wide namespace, claimed at declaration time — listeners do **not** enter `Registry` / `Component`, matching the trigger precedent.
- `core.transition` — `Transition` / `ExecutingTransition` (the read-only view plus the `run(...)` / `fork(...)` dispatch an action's body needs) / `TransitionDef` (an `ActionSequence`: a transition's body is an ordered member list), `TransitionResult`, `ActionPath` (qualified-id carrier exposed on `TransitionResult.executedPath` / `compensatedPath`), and the transition-listener surface: `TransitionListener` (a functional `onTransition(entity, context, execution)`), its `TransitionListenerDef` builder, and the `TransitionExecution` payload record (`phase` / `transition` / `firedBy` / `result`) with its `TransitionPhase` (`START` / `COMPLETE` / `ERROR`) discriminator. Listeners attach per transition through `TransitionDef.onStart(id, ...)` / `onComplete(id, ...)` / `onError(id, ...)` and to every transition through `StateMachineDef.onAnyTransitionStart(id, ...)` / `onAnyTransitionComplete(id, ...)` / `onAnyTransitionError(id, ...)`; each hook offers instance, `Consumer<TransitionListenerDef<T, C>>` configurer, and one-argument by-id forms, the last attaching a listener registered through `transitionListener(id, [Class<C>,] ...)` on `StateMachineDef` or `ContextScope`.
- `core.action` — `Action` (the single executable contract: `execute(entity, context, transition)` plus a default `getCompensation(entity, context)`), `ActionSequence<T, C, SELF>` (the member grammar every ordered action list shares — a container, a branch, a default branch, a transition's body — self-typed so a generic helper keeps the concrete chain type; it carries the inline `operation(...)` declaration too, so a sequence nests, and each inline declaration verb comes in three shapes so a member can declare the context it runs against), `ActionKind` (`STEP` / `OPERATION`, the authored form, carried for diagnostics only), `Compensation`, `ContextMapper`, and the def family: `ActionDef` base with `StepDef` (imperative — a Java body) and `OperationDef` (declarative — an ordered member list) as its two forms, plus `ChoiceDef` and the per-branch sub-builders `BranchDef` / `DefaultBranchDef` / `NoMatchBehavior`, `CompensationRouteDef` (the continuation `ActionDef.forException(...)` opens), `ForkableContext` (a host context that can copy itself for a forked member) and `AsyncRejectionPolicy`, and `MapperDef`. Also the action-listener surface: `ActionListener` (a functional `onAction(entity, context, execution)`), its `ActionListenerDef` builder, and the `ActionExecution` payload record (`phase` / `path` / `kind` / `transition` / `error` / `duration`, plus an `actionId()` reading the leaf off the path) with its `ActionPhase` (`START` / `COMPLETE` / `ERROR`) discriminator. Listeners attach per action through `ActionDef.onStart(id, ...)` / `onComplete(id, ...)` / `onError(id, ...)` — return-type narrowed on `StepDef` / `OperationDef` / `ChoiceDef` — and to every action through `StateMachineDef.onAnyActionStart(id, ...)` / `onAnyActionComplete(id, ...)` / `onAnyActionError(id, ...)`; each hook offers instance, `Consumer<ActionListenerDef<T, C>>` configurer, and one-argument by-id forms, the last attaching a listener registered through `actionListener(id, [Class<C>,] ...)` on `StateMachineDef` or `ContextScope`.
- `core.condition` — `Condition` and `ConditionDescriptor` (four-form sealed grammar: Reference, InstanceBased, PredicateBased — carrying a `BiPredicate<T, C>` over `(entity, context)`, with a `Predicate<T>` convenience overload on the DSL surface — and ExpressionBased). YAML's `class:` is a fifth *serialization* rather than a fifth form: the Phase 5 mapper resolves it to an instance and registers that.
- `core.exception` — `TransfluxException` and its subclasses.
- `core.trigger` — `Trigger` (runtime catalog view: id / name / description / `getTransitionIds()`) and its three public subtypes `ManualTrigger`, `EventTrigger` (adds `getEventId()`), `DataTrigger`; plus the def-side builders `ManualTriggerDef`, `EventTriggerDef` (`onEvent` + `filter`/`filterExpression`), `DataTriggerDef` (a single gate condition in the standard descriptor grammar). A trigger is either declared in place on a transition or registered once on the state machine - `manualTrigger` / `eventTrigger` / `dataTrigger(id, [Class<C>,] cfg)` on `StateMachineDef` and `ContextScope` - and attached by id through `TransitionDef.addTrigger(String)`, any number of times. The catalog supports plain enumeration (`getTriggers()` / `getTrigger(id)`) **and** kind-based discrimination via `<X extends Trigger> getTriggers(Class<X>)` (return-type narrowed; selects on the subtype). Manual triggers fire through `entity(e).fire(id[, ctx])`; event and data triggers fire through the host-driven `entity(e).processEvent(eventId, eventData[, ctx])` / `processDataChange([ctx])`, which return a `ProcessResult<T>` (in `core.transition`, alongside `TransitionResult`) rather than a bare `TransitionResult` — these entry points may match nothing (`ProcessResult.fired()` / `result()` / `firedTriggerId()`; `fired()` does not imply success). For an event trigger, `eventData` is bound for filter evaluation only (SpEL: entity = root and also `#entity`, payload = `#event`, context = `#context`) and is **not** the firing context; the first eligible filter-passing trigger fires. For a data trigger, the gate is evaluated against `(entity, context)` via a read-only probe view and the first eligible holding gate fires. Dispatch is first-match in declaration order among triggers on transitions leaving the entity's current state.
- `core.logging` — the shipped logging listeners: `ExecutionLogging<T>` (an immutable options value — level, context, timings, an entity label — that is also the factory for the three listeners, whose implementations stay package-private) behind `StateMachineDef.withExecutionLogging(...)`. They write to the `org.transflux.trace.*` subtree, not the framework's own.

**`#entity` is bound in every SpEL evaluation, beside the root it names.** Both contexts `SpelConditionEvaluator` builds - a condition's and an event filter's - put the entity at the root *and* under `#entity`, because passing the root whole to a method has no other spelling short of `#root`. `#context`, `#transition` and `#event` stay variables. `requirements.md` §3.9 is the one table of what each position binds.

**Dispatch is a capability, not a property of a transition.** `Transition` is the read-only runtime view — non-generic, `getId()` / `getName()` / `getDescription()` / `getSourceStateId()` / `getTargetStateId()`, the same kind of thing `State` and `Trigger` are. `ExecutingTransition<T, C> extends Transition` adds the `run(...)` and `fork(...)` overloads and is what `Action.execute` receives, because dispatch needs a live execution: the captured entity and context, the executed-path recorder, the compensation stack, and the active lexical scope. Everything that *observes* an execution — pre- and post-conditions, branch conditions, a data trigger's gate, and all three listener kinds — takes the read-only type, so code positioned where dispatched work could not be rolled back cannot express the dispatch. This replaced an earlier arrangement where one `Transition<T, C>` carried both and the observer path was handed an implementation whose `run(...)` threw; the throw is now a compile error instead. Two consequences worth keeping in mind: the payload records dropped the type parameters that only the old transition type needed (`ActionExecution` is non-generic, `TransitionExecution<T>` lost its `C`), and `TransitionImpl` — the implementation observers receive — *copies* the transition's strings rather than wrapping its `BoundTransition`, because SpEL resolves `#transition` reflectively against the runtime object, private fields included, and a wrapper would hand expression authors the whole resolved graph back.

**Trigger dispatch invariants.** Three rules hold across both host-driven entry points, and new trigger kinds are expected to keep them. (1) `fire()` is manual-only — it rejects an event or data trigger id, because firing one directly would skip the filter or gate that kind exists to impose; the check is a seam on the internal sealed `TriggerImpl`, not a scattered `instanceof`. (2) Context compatibility is part of *eligibility*: `processEvent` / `processDataChange` skip a trigger whose transition would reject the supplied context and keep scanning, so a filter or gate never sees a context its own transition refuses, and a later compatible trigger still fires; the targeted `fire()` / `transitionTo()` keep throwing on the same mismatch, since they name one specific target. (3) The gate is a condition and therefore receives the read-only `Transition`, which keeps it from running side effects outside the reentrancy guard with its compensations silently discarded. Filter and gate failures are wrapped with the offending trigger's id.

**One trigger, many transitions.** A trigger is declared in place on a transition or registered once and attached by id, and the two differ only in visibility. Five things to keep. (1) **Attaching claims nothing**, so one registration sits on any number of transitions and stays one trigger: it is built exactly once, the catalog lists it once, and `getTransitionIds()` reports them all - empty for a registration nothing attached, which is legal because a component library may register what a definition does not use. (2) **`fire(id)` selects by the entity's current state**, through a `triggerId -> sourceStateId -> transition` index, so a host fires `manual-cancel` without knowing which state the entity is in; the build rejects two attachments of one manual trigger leaving the same state, which is what makes the choice unambiguous. Event and data triggers need no such rule, their dispatch being first-match already. (3) **A trigger declared in place is visible to its transition alone.** Naming one from elsewhere is its own build error - it exists, it is simply not shareable - rather than an unknown id. (4) **Scan order is per transition**: its own declarations first, then the triggers it attaches. Indexing therefore walks the transitions rather than the triggers, or a registration attached by an earlier transition would drag a later one's attachment up with it. (5) **A registration carries its own context**, checked against every transition attaching it, and its own condition references are checked and its inline condition ids claimed against that context - no transition walk reaches a registration, so both need a pass of their own.

**Transition listener invariants.** (1) **`onComplete` and `onError` partition the outcomes**, and both pair with `onStart`: exactly one terminal notification follows every start, and neither occurs without one. A transition rejected by a pre-condition notifies nothing — it never reached the start hook, which §2.4 places *after* the pre-conditions. A pre-condition that *throws* lands in the same catch block as a failed operation, so a `started` flag gates the error hook rather than the catch itself. (2) **The payload carries the `TransitionResult`** the caller receives — the same instance, so a listener sees the executed path, the compensated path, the error, and the timings. It is `null` at `START`, and the record's compact constructor enforces the phase/result contract (`COMPLETE` ⇒ success, `ERROR` ⇒ failure). (3) **`firedBy` is the origin**, the `Trigger` that caused the execution or `null` for a direct `transitionTo`. It supersedes per-trigger listener bindings: a listener that should react to one invocation path branches on it. All three dispatch paths supply it, which is why `executeTransitionInternal` takes the firing `TriggerImpl` rather than a pre-extracted pre-condition list. (4) **The context is typed** (`TransitionListener<T, C>`) — a transition declares exactly one context type. Global registrations are the exception and take `Object`, since they span transitions that differ. (5) **Ordering mirrors the state rule**: the transition's own listeners first, then the global ones, declaration order within each group, merged onto `BoundTransition` at build time; a global listener is bound once and shared. Interleaved with the state hooks, §2.4's ordering gives start → exit … complete → entry.

**State listener invariants.** (1) **Listeners observe; they never gate.** Each invocation is wrapped individually — a thrown `Exception` is logged at WARN and swallowed, so it does not fail the transition, does not trigger compensation, does not stop the listeners declared after it, and leaves `TransitionResult` untouched. Rejecting a transition is a pre-condition's job. (2) **Firing points are the two gaps in `executeTransitionInternal`**: the source state's exit hook runs once the pre-conditions have passed and before the operation; the target state's entry hook runs after the `StateApplier` has committed (and still fires when no applier is configured, since that is the commit point either way). Two consequences that are documented and tested: a transition rejected by a pre-condition notifies neither hook, and an exit notification does **not** imply the transition succeeded. (3) **The payload's transition is the read-only `Transition`**, for the same reason the data-trigger gate gets one — a listener runs either before the operation or after the commit, so dispatched work would leave compensations that could never execute. (4) **The context is untyped (`Object`) by design**: a state can be entered from transitions carrying different context types, so there is no `C` to bind. That is the deliberate dividing line — a listener that needs a typed context belongs on a transition. (5) **Ordering is per-state listeners first, then global**, declaration order within each group, merged into a per-state index at build time; a global listener is bound once and shared across states rather than rebound per state.

**Action listener invariants.** (1) **A listener attaches to the action, not to the call site.** It rides on the action's own def and fires at every invocation of that action — container member, transition-body member, choice branch member, and by-id dispatch from another action's body. That is the rule compensation already follows, and it dissolves the question of how a by-id reference would carry an attachment: it does not have to. (2) **The single firing point is `ExecutingTransitionImpl.runAction`**, the seam the action-model unification left behind, so every action notifies at every nesting depth in whichever form it was authored. A transition has no root action of its own — its body is a member list, not an action — so the first member's `onStart` is the first action notification, and nothing fires between it and the transition's own `onStart`. (3) **The payload's `path` is the same `ActionPath` the invocation contributes to `executedPath`**, produced by one `qualifyActionPath` call that `runAction` reuses, so a listener lines its record up against the reported tree without reconstructing the nesting. Notification happens *inside* the nesting scope, so the path is the action's own. (4) **`mapFrom` runs after this action's notifications are closed.** A `mapFrom` failure is the parent's, and the child did complete, so it must not turn the child's `COMPLETE` into an `ERROR` as well — this is why the `mapFrom` call sits after the `try`/`finally` rather than inside it. (5) **`ERROR` fires at every enclosing level** as the failure propagates outwards, each reporting the same throwable, and the exception is rethrown unchanged so the transition still reports what actually failed. (6) **The context is the action's own** — the mapped child context at a mapped call site, i.e. the very object the body is handed, not the enclosing transition's. It is typed (`ActionListener<T, C>`); global registrations take `Object`. (7) **Globals are bound once on `StateMachineSnapshot` and appended at notification time**, rather than merged into each `BoundAction` the way transition listeners merge onto `BoundTransition` — one bound action is shared by every call site that reaches it, so merging would rebind the same global once per action. Ordering is still the action's own listeners first, then global, declaration order within each group. (8) **Observe-don't-gate and the read-only `Transition` carry over** from the other two kinds, and here the reasons are sharper: the hook sits in the middle of a live execution, so failing on an observer's behalf would compensate work the transition had no complaint about, and dispatched work would interleave into the executed path and the compensation stack as though the observed action had dispatched it.
**One listener, many hooks.** The id names the listener, not the attachment. A listener is declared in place at a hook or registered once under its category - `stateListener` / `transitionListener` / `actionListener(id, [Class<C>,] instance or cfg)` - and attached by the one-argument form of any hook. Six things to keep. (1) **A hook holds entries, not defs.** `ListenerEntry` is either a declaration or a reference, and both share one ordered list, so a hook notifies in the order it was written and a reference sitting between two declarations is delivered between them. (2) **Resolution is owner-first, then registrations.** A reference reaches anything the same owner declared at any of its hooks, in either order - which is how one listener serves `onStart`, `onComplete` and `onError` under a single id - and the eight `onAny*` hooks count as one owner between them. It resolves at build, so a reference may precede the declaration it names; one hook may not hold one id twice, a reference plus the declaration it names included, since attaching is not additive. (3) **A registration binds once**, and every attachment shares that bound record, which is what makes `withAsync` hold wherever it is attached. The resolver is per build: a second build must not hand out the first build's records, so `ListenerRegistrations` is created and cleared in `build()`, and the copy seeded onto every `ActionDefImpl` is cleared with it. (4) **Four rejections, each naming what was found**, because "unknown id" would be wrong for three of them: not registered, declared on another owner, registered in another category, or a context the owner does not satisfy. An action is checked against the context it *runs* against - `getContextType()` reports the `Object` sentinel for a declaration naming none, where the action inherits the enclosing one - which is why the check runs after `collectInlineMemberContexts`. (5) **Globals take `Object`.** A hook spanning every transition, or every action, cannot promise one context, so a typed registration attached there is refused; for the same reason the untyped instance registrations take `<? super T, Object>` rather than a wildcard, which would let a context-typed listener in against `Object` and defeat the check entirely. (6) **A registration is filed after its configurer returns and must declare a listener by then**, so a throwing configurer leaves the id free for the retry and an empty registration is reported where it is written rather than whenever something happens to attach it. A state and a transition follow the same rule for the listeners they declare in place: an id is refused at the hook call that takes it, and claimed when the owner registers.

**Disabling global listeners.** A state, a transition and an action may each suppress the state-machine-wide listeners of *its own* category, through `disableGlobalListener(id)`, its plural `disableGlobalListeners(id...)` and `disableAllGlobalListeners()` (the blanket form wins, order-independently; a repeated id collapses). Four things to keep. (1) **Enforcement is framework-side**, at the point each category's globals join the owner's list — a flag listeners were asked to honour would not be enforcement, and the listener that ignores it is the one the feature exists for. That point differs by category and the filter follows it: state and transition globals are already merged per owner at build (`buildStateListenerIndexes`, `buildTransition`), so filtering there costs notification nothing, while an action's globals are appended in `notifyActionListeners` — one `BoundAction` is shared by every call site, and `buildBound()` has no state machine to read the globals from — so the machine's constructor filters them once per disabling def into `filteredActionGlobals`, keyed by the declaration's identity, and notification is one lookup behind an early-out for the actions that disable nothing. A miss filters on the spot rather than failing open. (2) **An owner's own listeners are never filtered**, and suppression is total rather than context-free, so the public payload records did not have to change. (3) **A disable covers exactly the def it is declared on**: it is not inherited by members, by the actions a transition runs, or by the states it moves between — inheriting would make an action's observers depend on its call site, which §2.2.10's attachment rule rules out. (4) **The named form is a deny-list and fails open**, which is stated in the JavaDoc rather than left to inference; what does *not* fail open is a typo, which `StateMachineDefImpl.checkGlobalListenerDisables` rejects at build against the global ids of the owner's own category, reaching actions through `visitActionDefs`. The plural form is the singular applied per id, and refuses an empty call — naming no listener is far likelier a mistyped `disableAllGlobalListeners()` than an intention; what asked for it was the shipped logging, whose three action ids (`ExecutionLogging.*_LISTENER_ID`) are the first deny-list a host writes.

**Async listener invariants.** Any listener's def may declare `withAsync()` / `withAsync(policy)` (configurer form only; the instance form has no def and stays synchronous). (1) **One seam decides**: `StateMachineSnapshot.deliver` is what all three notify loops call per listener, with the invocation and its catch-and-warn as a `Consumer`, so a listener's catch travels with it to whichever thread runs it. A `null` policy on the bound record means synchronous. (2) **It is async work like a branch, not a second mechanism**: the task runs under `enterAsyncBranch` / `exitAsyncBranch`, so the ban on driving the machine applies — for any entity, stricter than a sync listener — and `BLOCK` from inside it runs inline instead of parking a worker. (3) **A listener fails nothing, including its own delivery**: a `ForkableContext.fork()` that throws or returns `null` loses that notification with a WARN on `execution.listener`; a refused submission — `DROP`, or `BLOCK` against a closed executor, which `refuse` rethrows — loses it with a WARN on `execution.async`. The exception to that is `BLOCK` notified from a thread running one of the machine's branches: `refuse` checks `insideOwnAsyncBranch()` before the closed case, so it runs inline even after `close()`, for listeners and forks alike, **per occurrence and deliberately** — unlike a blocked or inline submission, a lost notification is data gone, and a spike of WARNs is what shows an undersized pool or an over-eager async action listener. `RejectedExecutionException` never escapes a notify seam. (4) **`FAIL` is refused at the setter**, not at build: it depends on the argument alone. The listener default is `DROP` regardless of the machine default. (5) **The build sees listeners through one walk**, `StateMachineDefImpl.visitListenerDefs`, which feeds pool creation (`declaresAsyncListener()`), the fair queue and the `BLOCK`-against-a-host-executor check. (6) **No ordering is promised**, among async listeners or relative to sync ones; submission follows declaration order, execution does not. (7) **Mind the volume**: an action listener notifies twice per action invocation, so a global async one scales with every action every transition runs — the reason the default `DROP` is a real loss there, and the note on `ActionListenerDef.withAsync`.

User code should not depend on this package directly.

**A choice is an action, in the type system as well as the model.** It occupies every position an action can — a container member, a branch member, a member of a transition's body, and a state-machine-level registration under `choice(id, Class<C>, cfg)`, which shares one namespace with steps, operations and conditions. `ChoiceDefImpl` extends the sealed `ActionDefImpl` alongside `StepDefImpl` and `OperationDefImpl`, so the three authoring forms share one listener sink, one compensation sink, and one set of build hooks (`buildBound`, `checkRefs`, `bindMembers`, `bindScope`, `flattenScope`, `scanScopeFor`, `collectScopes`, `collectNestedCycleNodes`, `declaresFork`, `ownByIdReferenceIds`) — which is what lets a choice occupy every position an action can: a container member, a branch member, a member of a transition's body, and a state-machine-level registration. It sat outside that base for as long as it was only ever an inline member; attaching one to a transition is what ended that, and the duplicated sinks it used to carry went with it. One asymmetry is left and is deliberate: `buildBound()` takes no arguments, so a choice captures the resolved condition registry during `bindScope` and reads it back — the registry is available two build phases earlier, and threading it through a signature two subclasses ignore would cost more than the field does.

**Action model.** There is one runtime type, `Action<T, C>`, and two authoring forms: a **step** is imperative (a Java body), an **operation** is declarative (an ordered member list whose executable the framework synthesizes). The distinction is what the author wrote, not what the runtime does — both execute through one path and dispatch identically. `BoundAction(id, action, kind)` carries the form so diagnostics can name it; `ActionKind` never selects a runtime path, and if it ever starts to, the split has been reintroduced under a new name. Any action attaches to a transition, in either form. See [docs/design/action-model-unification.md](docs/design/action-model-unification.md) for why the previous `Step` / `Operation` split was collapsed. A second design — [docs/design/action-sequence-grammar.md](docs/design/action-sequence-grammar.md) — made the *member* grammar invariant across every position that holds an ordered list, through one self-typed `ActionSequence<T, C, SELF>` base; it shipped, and a transition's body became the fourth such position while it did. Read it for why the invariant exists before widening any of those surfaces piecemeal, and `requirements.md` §2.2.5.1 for what the grammar is now.

**One execution path.** Every action reaches the runtime through `ExecutingTransitionImpl.runAction`, whether it is a container member, a member of a transition's body, or a by-id reference from inside another action's body. The order is fixed: qualify the action's path once → capture the compensation and push it at that path → record the same path on `executedPath` → push the id onto the operation-nesting stack → execute → pop. One qualification serves the compensation, the executed path, and the listener payload, so the three cannot disagree. Capturing and recording *before* the nesting push puts both at the action's own qualified path rather than one level beneath it. Recording before `execute` means a throwing action still appears on `executedPath`, which keeps it consistent with `compensatedPath`. Pushing the nesting stack for every action means anything it dispatches is qualified underneath it, so the reported tree matches the tree that ran at every level rather than only at container boundaries.

**Verbs split by call-site category, not by callee kind.** The overload count no longer follows the position: **every position that holds an ordered member list carries the whole family**, declared once on `ActionSequence<T, C, SELF>` (`core.action`) and inherited by `OperationDef`, `BranchDef`, `DefaultBranchDef` and `TransitionDef` — 41 methods across eight verbs, self-typed so a chain keeps the concrete def type and a generic helper (the Phase 5 YAML mapper) does too. The one position that is *not* a sequence is a dispatch from inside an action body, which carries the reference half alone — the 3 `run` forms and the 6 `fork` ones (three call shapes, each with and without a policy) — and no declaring verb, since a Java body that wants to declare an action declares it in the sequence that encloses it. `ActionSequenceSpec` pins the invariant by reflection — a golden signature list plus "no subtype declares a member form of its own" — so a widening is a deliberate edit rather than a drift. The eight are four member forms crossed with whether the enclosing sequence waits:

| | reference | declaration: imperative | declarative | first-matching-branch |
| --- | --- | --- | --- | --- |
| synchronous | `run` (3) | `step` (8) | `operation` (4) | `choice` (4) |
| forked | `fork` (6) | `forkStep` (8) | `forkOperation` (4) | `forkChoice` (4) |

A **reference** names an action registered elsewhere or declared inline in the enclosing scope, and makes no claim about how it was authored; a **declaration** brings a new action into existence at that position and keeps the nouns, because the form is being chosen there. Each declaring verb's count is its authoring forms (instance and configurer for `step`, configurer alone for the other two) times the three context shapes a declaration comes in — inherit the enclosing context, declare one and run pass-through, declare one and map into it, through a `ContextMapper` or a registered mapper named by id (the second doubling the mapped shape's count). `fork` is `run`'s three call shapes twice over, each with and without an `AsyncRejectionPolicy` — the by-id forms have no configurer to declare one on.

Three things about the second row. It is a **distinct verb rather than a flag**, so autocompleting `fork` surfaces the whole asynchronous surface while `run` and `step` stay synchronous. The verbs are **prefix plus form** rather than overloads of `fork`, because `ContextMapper` and `Consumer<StepDef>` are both applicable to an implicitly-typed lambda — the erasure trap that named `mapperDef`, and the same reason declaration cannot collapse to one verb at all (`action(String, Consumer<StepDef>)` and `action(String, Consumer<OperationDef>)` erase to the same signature). And **forking is a property of the position, not of the action**: `forkStep(id, ...)` registers its action in the enclosing scope exactly as `step` does, so a sibling may still `run(id)` it in line. The asymmetry between the two rows' spellings is forced by the language, not chosen. Do not "fix" it.

**Definition vs. runtime split** — every concept has paired types:
- `*Def` interfaces + `*DefImpl` classes — fluent builders that capture configuration (states, transitions, operations).
- Runtime interfaces (`StateMachine`, `State`, `Transition`, `Operation`) + `*Impl` — immutable instances produced by calling `build()` on the definition.

Read a `*Def` to understand the DSL surface; read the matching runtime interface to understand execution semantics.

**The handle and its snapshot.** `StateMachine<T>` is a host-facing handle, and what is behind it can change: `StateMachineImpl` holds a `volatile StateMachineSnapshot<T>` and `replaceDefinition(newDef)` installs another. The snapshot is one built version - states, transitions, triggers, registries, bound actions, the listener indexes, and the execution engine - and is immutable once its constructor returns. Five things to keep. (1) **Every entry point captures the snapshot once** and runs against it, so a swap never splits an execution between two versions; an `EntityBinding` is such a capture, and `ExecutingTransitionImpl` holds the snapshot it was constructed with, which is what makes `run(id)`, the drain and the scope stack resolve against one topology. (2) **The swap is atomic-or-nothing**: `StateMachineDefImpl.buildSnapshot(handle, generation)` is the whole pipeline - the same one `build()` runs - so validation, binding and the completion INFO all happen before the volatile write, and a throw leaves the snapshot, the generation and the executor exactly as they were. Concurrent swaps serialise on a lock; `generation()` is a single-writer volatile read. (3) **The guards key on the handle, not the snapshot** - both the reentrancy set and the deque naming the machines whose branches the current thread is running - because a reentrant call after a swap arrives at the same handle. (4) **The executor is the handle's**, and the first definition that needs one configures it for the handle's lifetime; a later definition's pool or host executor is logged as ignored, and `close()` shuts down exactly one, only when the framework built it. Per-snapshot pools were rejected: a snapshot is never retired, so its pool would either be shut down under an in-flight transition that could still fork into it, or be kept per generation forever. A **closed** machine refuses a replacement outright, which is what keeps "a definition that declares async work always has an executor" true - without it, a swap after `close()` could install async listeners against no executor at all, and `requireAsyncAccepted`'s `TransfluxValidationException` would escape the notify loop past the applier and turn a committed transition into a rolled-back failure. (5) **The entity type is the identity contract** - a replacement declaring a different one, a subtype and a supertype included, is refused - which is why `forEntityType(...)` is required at `build()`. `requirements.md` §2.7 is the contract.

**Entry point.** `Transflux.defineStateMachine(Class<T>)` returns a `StateMachineDef<T>` with its entity type bound; the no-argument form plus `forEntityType(...)` stays, but a Java caller has to write it with a type witness (`Transflux.<X>defineStateMachine()`), since `T` is not inferable at the receiver. **The entity type is required either way** - `build()` refuses a definition that declared none, because it is the handle's identity contract when the definition is replaced. The builder chain (`withStateResolver` → `withStateApplier` → `state(...)` → `transition(id, source, target, ...)` → `build()`) produces a `StateMachine<T>`. **A transition is declared on the state machine, not inside its source state**, so the Java DSL reads as the YAML one does - a list of states and a list of edges - and the loader maps each document entry onto one def call. Declaration order between the two is free; the build rejects a transition whose source or target is not a declared state. `state(id)` declares a state that configures nothing. The state machine itself is parameterized only by entity type — context lives at the transition level, not the SM level.

**Per-transition context.** Each `TransitionDef<T, C>` carries its own context type `C`. There are two ways to set it: (1) `StateMachineDef.transition(id, source, target, Class<C>, configurer)` pre-binds the context at the transition's declaration; (2) the pass-through `StateMachineDef.transition(id, source, target, configurer)` defaults the transition to `Object.class` (accepts any non-null context, also accepts `null`). `Void.class` is a sentinel — a transition declared with `Void` context rejects any non-null firing value at the dispatch boundary in `StateMachineSnapshot`. SM-level reusable components (steps, conditions, operations, mappers) are registered without a context constraint (`step(id, Action<T, ?>)`), or with an explicit context tag via the typed overloads (`step(id, Class<C>, Action<T, C>)`, `operation(id, Class<C>, Consumer<OperationDef<T, C>>)`) or grouped under a `forContext(Class<C>, scope -> ...)` block. A step registers from an instance or through a configurer; an operation is only ever declared through a configurer, so it has the typed form alone. The typed registrations expose a `getContextType()` accessor on the component's def (`StepDef.getContextType()` / `OperationDef.getContextType()` / `MapperDef.getParentType()` / `getChildType()`); a fallback `componentContextTypes` map on `StateMachineDefImpl` covers untyped overloads. The build-time context-compatibility check runs from `StateMachineDefImpl.validateContextCompatibilityAndCycles` into each def's `ActionDefImpl.checkRefs` and on into `ActionSequenceSink.checkRefs`, which walks the sequence's member list — descending into `ActionRef.Choice` to reach branch members and into `ActionRef.InlineOperation` to reach a nested container's — and validates that pass-through references are assignment-compatible and that any supplied mapper's `parentType` / `childType` align with the call site. It is preceded by `collectInlineMemberContexts`, a pass of its own for the same reason member binding is: a reference may name an id declared after it or in an enclosing scope, so nothing can be checked until every declaration has been seen. It records the context each inline declaration runs against — its own when it named one, the enclosing sequence's otherwise — because inline ids never enter `componentContextTypes`, which only registrations write, and a by-id reference to one would otherwise be checked against the `Object` default and admitted whatever the contexts were. That was safe only while every action in a subtree shared one context, which is exactly what declaring a context ends. Existence of a member's id falls out of binding rather than being checked separately: every member binds in `StateMachineDefImpl.bindDeferredMembers`, a pass of its own inside `StateMachineSnapshot`'s constructor, for the reason given under the two-pass rule below.

**One `condition` name, and why the arity carries it.** Every condition-registration form lives under `condition(...)` on both `StateMachineDef` and `ContextScope` — instance, `BiPredicate`, `Predicate` and expression, typed and untyped alike. The forms separate on how many parameters they take, which is what lets an implicitly-typed lambda pick one: `Condition` has three, `BiPredicate` two, `Predicate` one, and an expression is a `String`. The typed family briefly carried distinguishing names (`conditionPredicate` / `conditionExpression`) on the stated grounds that erasure made them indistinguishable from a `Class<? extends Condition>` overload; that was wrong — the two differed in arity and could never both be applicable — and the class form is gone in any case. The single-argument `conditionExpression(String)` / `preConditionExpression(String)` on `TransitionDef`, `BranchDef` and the triggers do keep their own names, where `condition(String)` really is taken by the reference-by-id form.

**One lambda-shaped overload per name.** The rule that keeps the forms above apart generalises, and it is the reason `mapperDef(...)` is not called `mapper(...)`: two overloads whose functional-interface parameters share a descriptor cannot be told apart when the argument is a lambda, and neither an explicitly-typed lambda nor most-specific-method resolution breaks the tie — only a cast does. `ContextMapper<P, N>` and `Function<P, N>` are both `(P) -> N`, which is why the `Function` registration overload was removed rather than kept, and `Consumer<SomeDef>` collides with any of them for the same reason. When adding an overload whose parameter is a functional interface, check what else lives under that name first.

This rule was learned the second time from a shipped violation of it. `run(String, Function<C, ?>)` and `run(String, ContextMapper<C, ?>)` coexisted on `OperationDef` and `ExecutingTransition`, so **`run("id", parent -> child)` — a call shape `requirements.md` documented — did not compile at all**; only a cast disambiguated it. Every spec in the repo is Groovy, and Groovy resolves overloads at runtime against the argument's actual class rather than performing Java's applicability analysis, so nothing caught it. The `Function` overload is gone from both surfaces, and `src/test/java` now exists so the DSL has a Java caller — see the testing conventions below.

**Why there is no `ConditionDef`, and no `Describable`.** Both were proposed in the component-metadata work and both were closed as decisions rather than as code. `ConditionDef` would add a name and a description that nothing reads — there is no `Condition` runtime view, no condition catalog, and no payload carrying one — and making the metadata reach runtime means widening all five `ConditionDescriptor` records plus `BoundCondition`, then mirroring the resulting overload family across six defs. A `Describable` super-type would collapse the per-interface `getName()` / `getDescription()` declarations into a super-type with no behaviour change and no polymorphic consumer: every listener payload reads metadata off a concrete type or carries the fields flat. Both are parked against the YAML work, which is the first thing that might genuinely walk defs polymorphically; reintroducing either then is additive. Do not add them speculatively. **Listener defs are the one family where the question was reopened and answered yes**: `ListenerDef<L, SELF>` carries identity, `using`, and `withAsync`, and `StateListenerDef` / `TransitionListenerDef` / `ActionListenerDef` only bind it. What changed is exactly the gate above — the shared surface gained behaviour (`withAsync`, identical across categories) and a polymorphic caller (Phase 5 applying `config: { async, onRejection }` to any listener) — so it does not reopen `Describable` across all defs. `ListenerDefSpec` pins it: each sub-interface binds `SELF` to itself and declares nothing.

**Null ctx for Object-typed components from Void callers.** When a container member or `view.run(...)` dispatches an `Object.class`-typed component from a `Void.class`-context caller, the component's `ctx` parameter receives `null` at runtime. The build-time pass-through check admits this unconditionally — `Object.class` components always pass through, regardless of caller context. Component bodies registered under `Object.class` must tolerate `null` ctx; the canonical reason to register under `Object.class` is "this component ignores ctx," which the null-tolerance follows from. **`Object.class` is a component's spelling of "no context"; `Void.class` is a transition's.** A component declared with `Void` is unreachable through a mapped call site by construction - a `ContextMapper<C, Void>` can only produce `null`, which the mapped check refuses - so the two are not interchangeable and only the transition-level sentinel means "reject a non-null firing value".

**Every position taking a host executable is contravariant in the entity type.** `Action`, `Condition`, `Compensation`, the `BiPredicate` / `Predicate` condition forms, the three listener interfaces and `StateResolver` / `StateApplier` are all `? super T` - on the `StateMachineDef` and `ContextScope` registrations, the inline `ActionSequence` forms, `using(...)`, `withCompensation(...)` and the listener hooks. One component written against an interface several entity types share therefore registers on a machine for each of them, as the same instance, instead of having to be a generic class. **The context stays invariant**: widening it would make a component's declared context a claim about what it accepts rather than what it runs against, and the call-site check rests on that. No call shape changed, because an implicitly-typed lambda infers `T` from a `? super T` target exactly as it did from `T`. The bound records widened with the surface rather than narrowing at the bind boundary, which leaves exactly one unchecked cast: `TransitionExecution<T>` is the only invariant payload left, `ActionExecution` and `StateChange` being non-generic and `Transition` never having been. `ActionSequenceSpec`'s golden list reads *generic* parameter types for this reason - erasure hides `? super T` completely.

**A context is declared where the action is declared.** For a registered component that is the registration (`smd.operation(id, Class<C>, cfg)`); for an inline one the call site *is* the declaration site, so context and mapper sit on the same entry. Each inline declaration verb on `ActionSequence` carries three shapes: the plain one inherits the enclosing `C`; one taking a `Class<N>` declares its own and runs pass-through, which requires `N` to accept `C` (widen yes, narrow no); one taking a `Class<N>` and a mapper declares its own and crosses the boundary, `mapFrom` write-back included - the mapper a `ContextMapper<C, N>` or a registered one's id, the second so a YAML declaration can name a registration the way a `run:` entry does. The runtime needed almost nothing for this: the three def-carrying `ActionRef` variants gained a `MapperRef`, and `bindMembers` already resolved a `ResolvedContextMapping` for every member regardless of kind, so a mapped inline declaration takes the path a mapped by-id reference already took. A mapped form taking an instance needs no build-time check — javac has already proven `ContextMapper<C, N>`; one naming a registered mapper is checked the way a by-id reference is, its parent type against the enclosing context and its child against the declared one.

**Call-site context mapping.** Mapping is a property of the *call site*, not the callee. `ContextMapper<P, N>` is a first-class reusable component (`mapper(id, P, N, instance)` on `StateMachineDef`, plus `mapperDef(id, P, N, Consumer<MapperDef<P, N>>)` when the registration also wants a name or description) with a default no-op `mapFrom`. `ContextMapper` has a single abstract method, so a lambda *is* the instance form — it supplies `mapTo` and leaves `mapFrom` the no-op. There is deliberately no `Function<P, N>` registration overload: it would be indistinguishable from the instance form at the call site while meaning the same thing. Every by-id reference — `.run(id, ...)` and `.fork(id, ...)` on a container, and `view.run(id, ...)` from inside an action body — accepts the same three forms: pass-through (no mapper), mapper by registered id, or an inline `ContextMapper<C, ?>`, which a lambda satisfies for the read-only projection case. There is no `Function<C, ?>` call-site overload either, for the same reason there is no `Function` registration overload — it shipped for a while and was uncallable from Java; see the rule below. An inline-declared member that names no context of its own is typed against the container's `C` and runs pass-through. `MapperRef` is a sealed type capturing the unresolved call-site choice; `OperationDefImpl.buildBound(stateMachine)` resolves each `MapperRef` to a `ResolvedContextMapping` via the mappers `StateMachineSnapshot` bound in its constructor — the same map `view.run(id, mapperId)` reads, so a built machine never goes back to its def for one. A mapper that returns `null` for a callee which declared a context is refused at the call site — a declared member, a forked one and a dispatch from an action's body alike, the callee's context type riding on `CompositeMember` for the first two — the same way `ForkableContext.fork()` refuses one - host code was asked to produce a context and produced nothing, and letting it past turns a nameable boundary failure into an NPE inside the callee. This is deliberately *not* symmetric with the pass-through check, which lets a `null` caller context through: there the caller genuinely has none and the callee is the sort that does not need one (see the `Object.class` rule below). Failure attribution: `mapTo` and `mapFrom` failures both surface as parent failures (the boundary belongs to the parent). A `mapTo` failure throws before the child starts, so nothing is recorded and no compensation is captured for it; a `mapFrom` failure throws after the child completed, and the child's compensations still run — compensation capture precedes execution and the enclosing transition drains the whole stack on any failure. Idiomatic mapper id: `<child>-from-<parent>` (e.g. `billing-from-send`, `payment-from-order`) — reads naturally at call sites and makes the boundary direction obvious.

**State accessor pair.** `StateResolver<T>` extracts the current state ID from a domain entity (read side); `StateApplier<T>` writes the new state ID after a successful transition (write side). The applier is optional — purely transient transitions, or hosts that mutate state inside steps, can omit it. Transflux never owns storage; both interfaces are host-supplied bridges. When the entity's state is an enum, the canonical pairing is `.withStateResolver(e -> e.getStatus().name())` / `.withStateApplier((e, s) -> e.setStatus(MyState.valueOf(s)))` — two short lambdas, honest about where the bidirectional binding lives. The framework intentionally ships no sugar around this; the host owns how state is stored.

**Identity.** Identity lives on the **definition** side. The `*Def` types (`StateDef`, `TransitionDef`, `ActionDef` and its `StepDef` / `OperationDef` forms, `MapperDef`, the `step(id, ...)` / `condition(id, ...)` / `operation(id, ...)` / `mapper(id, ...)` registrations on `StateMachineDef`, plus `ConditionDescriptor`) carry a stable `id` (used for lookup) and optional `name` / `description`. The runtime executable contracts (`Action<T, C>`, `Condition<T, C>`, `ContextMapper<P, N>`) are pure functional interfaces with no identity — the same class can be registered any number of times under different ids. At runtime the framework carries internal bound records (`BoundAction`, `BoundCondition`, `BoundCompensation`) that pair the executable with the framework-owned id; diagnostics and `executedPath` / `compensatedPath` pull from the bound side. Every position that holds an ordered member list — a container and a choice's branches alike — wraps each bound member in an internal `CompositeMember` record that carries the resolved per-call mapping, the fork flag, the rejection policy and the callee's context alongside the bound action, and dispatches it through that record; pass-through members carry `ResolvedContextMapping.passThrough()`. Per `requirements.md` §2.2.1, ids are required and must be unique within their scope; only **inline expression-based condition descriptors** may omit `id` and have one auto-derived from expression + descriptor path.

**Reentrancy guard.** `StateMachineImpl` - the handle - carries a static `ThreadLocal<Set<EntityKey>>` that tracks in-flight transitions on the current thread, keyed by reference identity of `(handle, entity)`. Keying on the handle rather than on the snapshot is what keeps the guard closed across a definition replacement: a reentrant call arriving after the swap reaches the same handle whichever version answers it. A transition that calls back into the same SM with the same entity (from inside an operation, step, condition, or future listener) throws `TransfluxReentrancyException`. Different-entity reentrant calls are permitted.

**The guard is not carried across a fork, and that is a decision rather than a gap.** Capture/restore would make a branch a continuation of the transition that spawned it, which it is not: a branch outlives that transition, owns a different rollback stack, and reports its outcome to nobody. A snapshot taken at submission would then reject legitimate work whenever the branch ran on after the transition finished. What ships instead is a second, narrower thread-local — a `Deque<StateMachineImpl<?>>` naming the handles whose branches the current thread is running — and a **categorical ban**: an action inside a branch may not call `transitionTo` / `fire` / `processEvent` / `processDataChange` / `executeTransition` on the machine that forked it, *for any entity*. Other state machines are unaffected. It is checked at `entity(T)`, which every entry point routes through (so a `processEvent` that would have matched nothing still throws rather than quietly returning `notFired()`), and again at the top of `executeTransitionInternal` as the backstop for an `EntityBinding` captured before the fork. Note this is stricter than the sync rule, deliberately: the sync guard is a stack-discipline check, while across a thread boundary the same question would be a concurrency control, and §2.1.2 puts concurrency on the host. Forked work is for the dangling cases — notifications, metrics, cleanup — and work that drives the machine belongs on the synchronous path. The deque is popped in a `finally` and removed when empty, or a pooled thread would keep a reference to the state machine, its definition graph and its classloader.

**Exception hierarchy.** All Transflux-thrown exceptions derive from `TransfluxException` (unchecked) and live in `org.transflux.core.exception`. `TransfluxValidationException` covers definition, builder, and lookup errors — raised synchronously. `TransfluxReentrancyException` is raised by the reentrancy guard described above. `TransfluxExecutionException` is what the framework itself refuses mid-transition, and deliberately does **not** extend the validation type: `forException(...)` made exception types contract, and a route has to be able to tell "the framework rejected this" from a broken definition without parsing a message. Its subtypes carry ids — `TransfluxConditionException` (condition id, `PRE_CONDITION` / `POST_CONDITION`, transition id), `TransfluxNoMatchException` (choice id), `TransfluxContextException` (action id; the runtime-only context crossings — body pass-through mismatch, a mapper producing `null` or the wrong type, a null `fork()`). What stays validation is host error rather than outcome: an unknown id from `view.run(...)`, a wrong source state, a missing executor, `BLOCK` against a host executor. `FAIL` stays the JDK's `RejectedExecutionException`.

**TransitionResult.** Transition execution returns a `TransitionResult<T>` rather than throwing on business outcomes — failures from invalid configuration still throw `TransfluxValidationException`. `TransitionResult` carries: success flag, source/target state, transition ID, error, executed-step IDs, compensated-step IDs, started/completed timestamps. The firing-time context object is not stored on the result; callers that need it already have it on their side of the call. There is no forced-state API (host owns initial-state placement).

**Compensation.** Any action optionally declares a `Compensation<T, C>`, through any of three channels: dynamically from `Action.getCompensation(entity, context)`, statically on the action's def via `ActionDef.withCompensation(instance)`, or per kind of failure via `ActionDef.forException(type)[.matching(guard)].withCompensation(instance)`. Whichever supplies it, the action's whole compensation table is captured **before** `execute` runs and pushed onto the per-execution LIFO stack carried by `ExecutingTransitionImpl` — the table rather than one resolved callback, because which entry of it applies depends on a failure that has not happened yet. If `execute` throws (its own or a later action's) — or a post-condition rejects, which throws into the same catch — the enclosing transition drains the stack in LIFO order. A *pre*-condition rejection returns its failure result directly instead, without draining, and that is exact rather than sloppy: a condition receives the read-only `Transition` and so cannot have dispatched anything, which makes the stack provably empty at that point. The asymmetry between the two rejections is the whole difference between them — a pre-condition guards an execution that has not started, a post-condition rejects one that has. Capturing before execute is deliberate: an action that throws partway through producing side effects (e.g., creating remote entities in a loop) still has its rollback handler available. The completion-time-snapshot pattern stays expressible by writing the snapshot into the entity or context during `execute` and reading it back in the compensation. A declarative container is pushed on entry, before it dispatches anything, so its own compensation and its members' all run and unwind members-first — the container's is additive, not a replacement, and it runs even when the first member fails immediately. Four rules to keep: (1) **one action, one compensation** — the rollback is the first of a matching route, the declared fallback, and `getCompensation` that answers for the failure, so `compensatedPath` never carries the same qualified path twice; a declared fallback therefore suppresses the dynamic hook (it answers every failure anyway) while routes alone do not, since a route that misses has said nothing about this failure and must not veto on the action's behalf. `ExecutingTransitionImpl.resolveRouter` is the single place that decides it, at push time rather than at the drain, because the hook is documented to see the same references `execute` will. When nothing answers, the action is not rolled back and stays off `compensatedPath`; (2) **routes are tried in declaration order, first match wins**, and they match on `isInstance`, so subclasses match and an unguarded route on a broad type shadows every narrower one declared after it — the build warns where it can prove that, and rejects a route opened but never closed with a compensation. A guard runs only after the type matched, and one that throws is a non-match rather than a second failure escaping a drain that is already unwinding one. Every stack entry routes against **the failure that ended the transition**, not one it threw itself — most entries being rolled back never threw anything; (3) the def-side declaration is the *only* channel open to a declarative container, which has no Java body to override; (4) **the drain hands each compensation the context its action ran against**, carried on `BoundCompensation` from push time, so a compensation behind a call-site mapper sees the mapped child context rather than the enclosing one. **An `Error` is rolled back and rethrown, unless it is a `VirtualMachineError`.** `ThrowingUtils.isFatal` is the one predicate: out-of-memory and internal errors mean the JVM can no longer be trusted, and driving rollback handlers through network calls and remote deletes from there is more dangerous than abandoning the rollback, so those propagate untouched. Every other `Error` — `AssertionError`, `LinkageError`, a Kotlin `TODO()` — is raised on a healthy JVM, so the transition (and a branch, and `runAction`'s `ERROR` notification) treats it as a failure: drain, notify, then **rethrow**, never a `TransitionResult`. The seams that *contain* a failure — a listener, a compensation mid-drain, a route guard, a listener's `fork()` — contain a non-fatal `Error` exactly as they do an exception, through `ThrowingUtils.rethrowIfFatal` at the top of each catch: an observer's `AssertionError` fails nothing, and one from a compensation does not cost the entries beneath it their rollback. That is also why nothing past the applier can reach the transition's `Error` catch, which therefore needs no "already committed" guard. `forException(...)` rejects a `VirtualMachineError` type, which could never match.

**Fork invariants.** `fork(...)` declares a member the enclosing sequence does not wait for, at any position that holds one — a transition's body included. (1) **The unit is the member, not a block.** There is no `async` block and no `startBefore` / `startAfter`: a member list already expresses position, so the anchor was a named spelling of "before x" / "after x". Each forked member is its own branch — its own task, its own context, its own rollback stack — which is exactly what the block never grouped. (2) **Submission is the commitment point.** Once handed to the executor a branch runs, whatever the sync path does next; there is no cancellation and no timeout, and a `startAfter`-style "only if the previous member succeeded" falls out of position for free. Under `CALLER_RUNS` the commitment point is the inline run instead, which is the same rule reached without an executor thread. (3) **Fire-and-forget.** `TransitionResult` is untouched: a forked member is on neither reported path, and its failure is logged on `execution.async` and drained into its own stack rather than returned. Hosts observe branches through the action listeners already attached to those actions, which fire on a branch exactly as they do in line. (4) **The branch copies where it sits and starts fresh on everything else.** `ExecutingTransitionImpl` gets a second constructor taking a seeded nesting stack and scope stack — copied, never shared, since the spawning thread keeps mutating its own — so paths read `container/member` and `run(id)` still resolves lexically, while the executed path and compensation stack begin empty. (5) **`mapFrom` is unreachable by construction**: `mapTo` runs at submission, so the branch is run with a `null` mapper and the write-back call at the end of `runAction` is dead code for it. There is deliberately no definition-time rejection of a mapper that overrides `mapFrom` — one shipped briefly and was removed, because the reflective probe it needed cannot tell an overriding implementation from a JDK dynamic proxy, which declares every interface method including defaults; it failed builds for AOP-proxied and mocked mappers. The behaviour was already right without it. (6) **Context precedence is mapper, then `ForkableContext.fork()`, then the shared reference**, all resolved on the submitting thread; host code that throws while producing a context fails the transition, per the `mapTo` attribution rule, while a *refused submission* is an operational condition and obeys the declared `AsyncRejectionPolicy`. (7) **One executor per state machine, built if the definition forks *or* asks for a pool** — `definitionForks()` starts from just two roots, SM-level containers and transition bodies, since every other container is declared inside one of them; each root is then walked in full, descending through a choice's branches and through any container declared in place, since a member forks through the same path wherever it sits. `withAsyncPool(...)` is the second reason, and it exists for the third position a fork can sit in (below), which that walk cannot reach. `close()` shuts down only a pool the framework built. (8) **A fork can also be issued from inside an action's body**, through the same six by-id forms `ActionSequence` carries, and the branch inherits the body's lexical position for free — `submitBranch` seeds it from the nesting and scope stacks, which by then already hold the calling action. Forking from a body that is *itself* running on a branch is legal: the async-branch ban stops a branch driving the machine, not spawning more work, and `BLOCK`'s self-deadlock is already answered by the inline-run escape. What such a call site loses is everything the build does by walking declared members — no shared-context warning, no fair queue from `declaresBlockingRejection()`, and no `checkBlockingIsPossible`, which is why `submitAsync` refuses `BLOCK` against a host-supplied executor eagerly, at every submission rather than only at a rejection.

**Async rejection is four answers, and a property of the submission.** `AsyncRejectionPolicy` (`core.action`) answers for an executor that cannot take a submission — a full queue, or a closed pool. `DROP` (the default) loses it with a WARN, `FAIL` raises the rejection so the transition unwinds, `BLOCK` waits for a slot, `CALLER_RUNS` runs it on the submitting thread. Three parties can speak for one submission, and the most specific wins: **the position** (`fork(id, policy)`, on the three by-id forms only), else **the def** (`ActionDef.withAsyncRejectionPolicy(...)`, read only when the action is reached through a `fork*` verb), else **the machine** (`StateMachineDef.withAsyncRejectionPolicy(...)`). Each has a use case the others cannot cover: a notification step does not know whether *this* flow may lose it, only the flow does; a listener, or a `financial-audit` step registered once and forked from many places, does know; the machine covers everything unsaid. The obvious objection to call-site placement — a trailing parameter doubling all fifteen fork verbs — was wrong, because an inline declaration (`forkStep` / `forkOperation` / `forkChoice` with a configurer) *is* its own call site and declares on the def it declares; only the three by-id forms have no configurer, so the call-site rung costs three overloads. The instance form `forkStep(id, Action)` has no def and, as with listeners and compensation, carries no declaration. Resolution happens once, at bind time, onto `CompositeMember` beside the `forked` flag it qualifies (`CompositeMember.of`), so dispatch reads one field and there is nothing to resolve at runtime. Four things not to rediscover. (a) **The mechanism is a `RejectedExecutionHandler`, and the framework keeps no bound of its own.** Waiting for capacity is the one answer that cannot be given from the submitting side — once `execute` has thrown, the chance to enqueue is gone — and a rejection handler runs on the submitting thread at the moment of refusal with the executor in hand. So `AsyncRejectionHandler` (installed only on a pool the framework builds) answers `BLOCK` with `getQueue().put(...)` and declines everything else by throwing, leaving `DROP` / `FAIL` / `CALLER_RUNS` to `submitAsync`'s catch, which is also the whole story for a host executor. The policy rides on the submitted `AsyncWork` record, because a handler is handed the `Runnable` and nothing else. An earlier version metered admission with a `Semaphore` instead and had to be withdrawn: a permit is held until its task *starts*, but a task handed straight to a new worker never enters the queue, so a bound sized on queue capacity refused branches while the queue was empty — a second copy of a number the executor already knows exactly is a copy that can disagree with it. Do not reintroduce one. (b) **`getQueue().put(...)` is off-label** — `getQueue()` is documented for monitoring — and is safe only under the conditions the framework's own pool guarantees: a bounded queue, and a worker count that cannot be zero while the queue is full. That is why `BLOCK` against a host-supplied executor fails the build rather than degrading, naming the def; a host wanting that back-pressure installs a blocking handler on its own pool. The handler also needs the two-sided shutdown check — `isShutdown()` before the `put`, and `isShutdown() && queue.remove(work)` after it — or a task lands in a queue nobody will drain. Saturation is the policy working rather than an anomaly, so a blocked submission and an inline run are each **DEBUG per occurrence with one WARN on entering that state** - a per-submission WARN would spend a host's log budget hardest exactly when its pool is already struggling, which is what the level table forbids. (c) **`BLOCK` does not wait on a thread already running a branch of this machine** — it runs inline instead. A worker parked in `put()` may be waiting for a slot only it could free, which is a real hang rather than a slow path; the thread is already a branch thread, so nothing about isolation changes. The pool's queue is fair only when the definition actually declares `BLOCK` (`declaresBlockingRejection()`), so the fair lock is not charged to machines that never wait. (d) **`CALLER_RUNS` changes the thread and nothing else**: the task is the same `AsyncBranchTask`, so the branch keeps its own stack, its own drain, its swallowed failure, and the ban on driving the machine. The one exception is that an `Error` from inline work reaches the transition rather than dying on a worker: a branch rolls its own stack back and rethrows it, per the `Error` rule above, and inline there is a transition underneath to rethrow into.

**One def walk, and new per-def build checks belong in it.** `ActionDefImpl.visitDefs(Consumer<ActionDefImpl<?, ?, ?>>)` visits a def and everything declared beneath it — a container's members, a choice's branch and default-branch members, inline declarations at any depth — and `StateMachineDefImpl.visitActionDefs(...)` drives it from the three roots a def is reachable through: a registration with a def, an SM-level container, a transition's body. Registered steps are a root of their own because a step declares no members and so is reachable nowhere else; a bare `Action` instance has no def and is correctly outside the walk. Both the listener-id namespace check and the `BLOCK`-against-an-unbounded-executor check ride it, which is the point: a check written as its own recursion is a check that reaches a position the others miss.

**DSL Shape.** Lambda-configurer is the single declaration shape for every Def that owns children — states (`StateMachineDef.state(id, s -> ...)`), transitions (`StateMachineDef.transition(id, source, target [, Class<C>], t -> ...)`), declarative containers (`operation(id, op -> ...)`), choices (`choice(id, cs -> ...)`), branches (`branch(id, b -> ...)`), imperative actions (`step(id, a -> ...)`), and the SM-level grouping block (`forContext(Class<C>, scope -> ...)`). The configurer is the *only* place to declare children: once it returns, the def reference is inert and any further mutation throws `TransfluxValidationException`. To declare another state or build the SM, return from the lambda and continue on the enclosing `StateMachineDef`.

The scope guard applies to **every** def passed to a user lambda — `StateDef`, `TransitionDef`, `OperationDef`, `StepDef`, `ChoiceDef`, `BranchDef`, `DefaultBranchDef`, the `forContext` `ContextScope`, the three `*TriggerDef` kinds, `MapperDef`, `StateListenerDef`, `TransitionListenerDef`, and `ActionListenerDef` — not just the top two. New defs added in later phases are expected to follow the same rule. The guard machinery lives on two abstract bases in `core.impl`: id-bearing defs extend `IdentifiedDefImpl` (which carries `id` + `name` + `description` + the `withName`/`withDescription` setters on top of the guard); id-less guarded defs — `ContextScopeImpl` (keyed by context type), `BranchDefImpl`, `DefaultBranchDefImpl` — extend `ConfigurableDefImpl` directly. A parent runs a child's configurer through `ConfigurableDefImpl.runConfigurer(child, configurer)`, which flips the guard active for the duration of the lambda; each `defLabel()` (`"step 'x'"`, `"operation 'x'"`, `"choice 'x'"`, `"branch 'x'"`, `"default branch"`, `"mapper 'x'"`, `"forContext scope for X"`) names the offending def in the rejection message.

For one-off SM-level component registrations the flat overloads stay alongside `forContext` — `smd.step(id, Class<C>, ...)` / `smd.condition(id, Class<C>, ...)` / `smd.operation(id, Class<C>, ...)` / `smd.mapper(id, P, N, ...)` / `smd.mapperDef(id, P, N, ...)` are meaningfully more compact than wrapping a single registration in a one-line block. `forContext(Class<C>, scope -> ...)` is the right shape for *groups* of components sharing a context; the flat form is the right shape for *one-offs*. Both forms populate the same registry — stylistic choice, not semantic, and the two routes share one registration path per component kind. The scope carries the same configurer forms the flat overloads do (`scope.step(id, cfg)` alongside `scope.step(id, instance)`), so choosing a `forContext` block never costs the ability to name a component or attach listeners to it.

**`forContext` types registrations, and nothing re-types a def after the fact.** `forContext(C, scope -> ...)` on `StateMachineDef` opens a grouping scope ("for context C, register these"). There is no `usingContext` anywhere: `OperationDef`'s returned `SELF`, so the only compilable argument was the enclosing `C` restated, and `TransitionDef`'s survived one round longer on the grounds that a transition had a single action slot the re-type could not strand a member in front of — which stopped being true when the body became a sequence. A transition declares its context at `transition(id, source, target, Class<C>, cfg)`; an action declares its own where it is declared.

**Component resolution and lexical visibility.** Every `StateMachineSnapshot` owns one root `Registry<T>` populated with SM-level actions, conditions, and containers. Every `OperationDefImpl` owns its own `Registry<T>` whose parent is the enclosing scope's registry — the root for a container registered at SM level and for a transition's body, and the enclosing container's scope for one declared in place with `operation(id, cfg)` at a member position, which is what confines a nested container's inline ids to its own subtree while leaving the enclosing chain reachable from inside it (a process-wide registry parents the root once Phase 6.2 lands). Inline-declared members — `op.step(id, ...)` and any choice or container declared inside it — register into the container's scope, not into the root. **A choice owns a scope too**, parented the same way, and its branches' inline members go into *that*: every branch of a choice can reach what any of its branches declares, so a step common to several is declared once, while a sibling of the choice cannot reach in. The choice's own bound action still goes into the enclosing scope, so naming it by id works from either side. `ChoiceBranchExecutor` pushes that scope while it dispatches, so an id dispatched from inside a branch member's body resolves against it before walking out. Ids are still **globally unique** across the SM (the build pipeline maintains a per-build canonical-payload table; same instance / same class under the same id is idempotent, anything else is rejected at build time). What is *not* global is **visibility**: a container's inline id is reachable only from inside that container's subtree (its own member references, choice branches, and any `view.run(id)` issued while the container is executing). Sibling containers cannot resolve another's inline ids — referencing one is a build-time error. SM-level ids are reachable from every container via the parent-chain walk. At the end of construction every registry is `flatten()`-ed so runtime resolution is a single map lookup; `Registry.parent()` stays in place as a public introspection accessor. `ExecutingTransitionImpl` carries an active-scope stack: the container executor pushes its scope on entry to `execute`, pops on exit; `view.run(id)` consults `activeScope().resolve(id)` (falls back to the SM root when the stack is empty).

**Building a container is two passes, and every container uses both.** `buildBound()` produces the `BoundAction` — its executor, listeners and compensation table — and `bindMembers(stateMachine, positionLabel)` resolves the members and installs them on that executor afterwards. They cannot be one pass: a container's or a choice's bound action is registered *into* the very scope its own members resolve against, because a sibling may name it by id and such a reference captures the bound action by value. So the build registers every container first and binds every member second, which is also what frees a member to reference a container declared after its own — a branch could always do this, and containers now agree. A fresh executor per build keeps an earlier machine on the members it was built with. The consequence for new work: **anything that resolves a member belongs in `bindMembers`, not in `buildBound`**, and a new member form that owns children has to be reached by both — a form wired into only one of them builds a machine that NPEs at execution rather than failing at build.

A second consequence is a **publication contract**: because members, and a container's registry contents, are written after the objects holding them are reachable, a built `StateMachine` must be **safely published** before it is shared across threads — assigned to a `final` or `volatile` field, or handed over through a synchronized or concurrent structure. This is not new with deferred binding: `RegistryImpl` holds its component maps in `final` fields but mutates them throughout the build and again in `flatten()`, so the freeze applies to the references and never to the contents. Marking individual executor fields `volatile` would silence one symptom of this and imply a guarantee the graph as a whole does not offer, which is why the contract is stated instead. Concurrency is the host's, per `requirements.md` §2.1.2.

**Position labels are a path.** A build message names where a failure sits by composing the enclosing position with the nested one, `outer > inner`: `transition 't' > operation 'op' > choice 'route' > branch 'critical'`. The label is threaded as a parameter through `checkRefs` and `bindMembers`, so a position reads identically at check time and at bind time; an SM-level container and a transition's body are each a root and name only themselves — the body labels itself `transition 't'`, so a member of it reads `transition 't' > operation 'op'` without the body appearing as a level of its own. `defLabel()` is deliberately *not* part of this — it backs the configurer guard, which names a def the caller is holding a stale reference to, and there the def's own id is the whole point.

**There is no id-carrying-interface overload family, and adding one back is a regression.** Every DSL method takes a `String` id. The family that used to shadow each of them — 191 public declarations and 213 impl members, existing only to accept an enum where a `String` was wanted — is gone. It never delivered the checking it advertised: the interface was *single and untyped*, so `run(MyStates.TRIAL)` compiled where an action id was expected, and the scoped constants it actually bought a host are what a `static final String` holder gives for free. It cost ×2 on every one-id method and ×4 on every two-id method, and it was already incomplete for that reason — `run(Identifiable, ContextMapper)` never existed, and neither the stated parity rule nor `ActionSequenceSpec`'s golden list noticed. It also carried a live resolution trap: `transitionTo(Identifiable target, Object context)` and `transitionTo(Identifiable target, Identifiable transition)` were both applicable when the context happened to implement the interface, and most-specific silently picked the *transition* form. Call sites write `.getId()`. One method changed shape rather than being deleted: `addEventTrigger(Identifiable event)` used its single argument as both the trigger id and the event id and had no String counterpart, so it became `addEventTrigger(String eventId)`.

**The `Identifiable` interface is gone too.** It survived the overload family for a while as the place a def reported its own id, but a single untyped `getId()` super-type has no polymorphic consumer — the loader is per-kind, and so would a definition dumper be — so every `*Def` and every runtime view now declares `getId()` itself. `State` and `Transition` gained one in the process, having inherited theirs. Reintroducing it is additive if a polymorphic walk ever appears; do not do it speculatively.

**The `transflux-yaml` module.** `org.transflux.yaml.source` is the definition sourcing SPI (`requirements.md` §2.6): `DefinitionSource` / `DefinitionResource` and the ships-with `ClasspathDefinitionSource`, `FileSystemDefinitionSource` (with `SymlinkPolicy`) and `CompositeDefinitionSource`. An empty `open(...)` means "no such document" and nothing else — a refused identifier or an unreadable document throws, because the loader reports a miss as a missing import and a failure must not be mistaken for one. The composite is one ordered list: each source declares its own prefixes (`prefixes()`, default empty so a lambda still works), a declared prefix selects its sources and is stripped, anything else scans every source, first found wins. It reports the *whole* identifier, since error messages name a document by it, and passes `location()` through, since after a scan the identifier no longer says which source answered. Source order is a trust decision the host owns (`requirements.md` §2.6.3). `org.transflux.yaml` is the loader, written against the public DSL alone: `YamlDefinitionLoader` (source, class loader, `ComponentFactory`) returns a `StateMachineDef` rather than a machine, since `replaceDefinition` takes one. It reads `imports:` depth first through the source, before the importing document's own sections, each document once per load keyed by the identifier as asked - so a cycle, a miss, a refusal and an imported `stateMachine:` are refused at the entry that wrote them. Beneath it, package-private: `Document` composes one SnakeYAML node tree and refuses anchors, aliases, merge keys, tags outside the core schema, duplicate keys and a second document; `NodeMap` is the position-aware walk - every key a reader asks for is an allowed key, so `rejectUnknownKeys()` needs no second list, and `at(node, call)` reattributes a `TransfluxValidationException` a def call throws to the line that caused it; `Classes` is the one place class names are loaded and instantiated; `TypeArguments` checks a class's declared generic supertypes against what javac would have proven (entity contravariant, context invariant), leaving an unresolved type variable to the runtime checks. `ComponentSections` reads a document's component sections into registrations and `StateMachineSection` the `stateMachine:` block - its metadata, its state accessors, the eight `onAny*` hooks, `config:` (`async` and `logging`, both sizes of the pool or neither), `states:` and `transitions:` - over five readers shared between them: `ActionEntries` (the `steps:` / `operations:` / `choices:` pools, and one walk over an `actions:` list that serves all four `ActionSequence` positions - `run:` to reference, `step:` / `operation:` / `choice:` to declare, `fork:`, and a call-site `mapper:` as a registered id or a block, a `mapFrom:` in a block beside `fork: true` refused because a fork never writes back), `ActionKeys` (the keys every action declaration shares - metadata, compensation and routes, `onRejection`, listeners, disables), `ListenerEntries` (a pool entry, an owner's `listeners:` hook block keyed by hooks that carry their own category, `disableGlobalListeners:`), `ConditionDescriptors` (the descriptor grammar at every condition position, emitting into a per-position `Target`) and `TriggerEntries` (a pool entry, and a transition's `triggers:` entry - a reference, or a declaration in place that takes its transition's context and so has no `context:` key); `Expressions` holds the SpEL the loader evaluates itself - the state resolver and applier, `mapTo`, `mapFrom`, a route guard. Condition and filter expressions are not parsed by the loader: core's def setters parse them (`SpelConditionEvaluator.validate`), and `NodeMap.at` puts the rejection on the document's line. A class is checked against its position as javac would - entity contravariant, context exactly the owner's - `Object` for what is declared on an owner that named none, and for an untyped listener registration - with only a registration's own class left unchecked when it declared no `context:`. Every loader error is a `DefinitionLoadException` (`root -> importer -> identifier:line:column: declaration path: problem`); `Document` carries the import chain, so every error raised against it has it. The declaration path names each declaration by kind and id, one missing its id by kind alone (`NodeMap.requiredId`), and a key-valued block by what it is - `state resolver`, `state applier`, `filter`, `route 2 (java.lang.RuntimeException)`, `guard`, `mapper`, `mapFrom` - through `NodeMap.optionalMap(key, label)`, or `within(label)` where the block is required. `DeclarationSites` records where each id a load declares was first declared, per id set core checks at the def call, and appends that to core's rejection of a duplicate - it checks nothing itself, and a collision core finds only at build is not covered. A failure raised later by the host's `build()` is not attributed to a line - the loader never builds. The module keeps one package-private `Loggers` holder per package, and one `LoggersSpec` (in `org.transflux.yaml`, reaching both by name) mirroring core's; the core module's spec cannot see across the module boundary.

**The JSON Schema and its corpus.** `docs/schema/transflux-v1.schema.json` (JSON Schema 2020-12) is the one copy: GitHub Pages serves `docs/` - as-is, `.nojekyll` - at the schema's `$id`, and the `transflux-yaml` pom copies the file into the jar. It is written by hand, the shared key sets composed under `unevaluatedProperties`, and admits everything the loader accepts but a bare boolean where text is expected and a quoted boolean or number (`requirements.md` §3.1.1). `YamlDefinitionLoaderSchemaSpec` holds it to the loader over `src/test/resources/corpus/`: under `valid/` both accept and the document builds, a copy of a `requirements.md` example excepted, under `invalid/` both refuse, under `loader-only/` only loading can see the fault, under `build-only/` only the host's `build()` does, and the header pins the build's message; a refused document opens with `# error:` (the whole message - the loader's, or the build's under `build-only/` - or its start when the header ends in `…`, kept for text the module does not own, such as the SpEL parser's), an invalid one adds `# schema:` (the JSON pointer the schema's error sits at) and, where a union of definitions reaches that key, `# rule:` (the definition that must raise it); a document under an `imports/` folder is reached only through an import. Documents are read under YAML 1.2's core schema, as editors read them, not through the validator's YAML 1.1 reader. Four things to keep. (1) **A grammar change edits the schema and adds corpus documents** - a valid one writing the new key, an invalid one per constraint it brings - or the two drift apart silently. (2) **Every YAML example in `requirements.md` carries a `<!-- corpus: name -->` anchor** on the line above its fence, and has a copy at `corpus/valid/requirements/<name>.transflux.yml`, wrapped into a document where it is a fragment; `none` marks a sketch no document can hold. The spec fails on an unanchored example, a copy that no longer holds its example, and a copy with no anchor, so an example edited in the spec is edited in its copy. The examples follow the implementation: when one stops loading, the example is what gets fixed. The classes they name are inert stubs under `com.example`, in this module's test sources. (3) **A document is named `*.transflux.yml`**, in the corpus and anywhere else in the repository. A success feature's document written out in full is a corpus resource loaded through `LoaderFixtures.loadResource`; a document a helper builds, and a refusal beside its message, stays inline. (4) **Run `clean` after deleting a corpus document**: Maven leaves the old copy in `target/`, where the spec keeps finding it.

## Logging

**This section supersedes the service-oriented logging guidance in the global instructions for this repository.** Transflux is an embedded library, not a service: it has no request log of its own to complement, and every line it emits lands in a host's log budget that the host did not opt into. The rules below are deliberately stricter about INFO and looser about DEBUG/TRACE than the service default.

**The governing rule: log what a listener cannot observe.** The listener SPI already exposes the execution trace — `ActionListener` gives per-action start/complete/error with the qualified path, the kind, and the context; `TransitionListener` gives start/complete/error with the full `TransitionResult`; `StateListener` gives entry/exit. A host that wants a trace registers a listener — `withExecutionLogging(...)` attaches the shipped ones — and controls the format, the level, and the cost. Framework logging must not reproduce that; it covers the decisions listeners never see — trigger dispatch scans, condition evaluations, registry resolution, call-site context mapping, compensation drains, the build pipeline, and everything §2.4 does before the start hook. Where the two would overlap, the listener wins and the framework stays quiet.

**Levels.**

| Level | What belongs here | Volume |
| --- | --- | --- |
| ERROR | Nothing. Failures are returned on `TransitionResult` or thrown. | — |
| WARN | An observer threw and was swallowed; a compensation threw during a drain; a def setter overwrote a previous value; a `WARN`-mode choice matched nothing; a definition-time smell that is not fatal. | rare |
| INFO | Rare and consequential events invisible from a return value: build completed, definition swapped, compensation drain started, executor lifecycle. **Never per transition.** | per build / per rollback |
| DEBUG | Per transition: resolved source state, pre/post-condition outcomes, the trigger scan and why each candidate was skipped, applier invocation, outcome. Per build: phase boundaries, registry scoping, and each bound component and what it resolved to. | O(transitions) |
| TRACE | Per action: entry/exit with qualified path and mapping decision, and which scope a dispatched id was claimed by. Per branch condition: the evaluated value. | O(actions) |

INFO staying off the per-transition path is the rule to hold hardest — a host running thousands of transitions a second did not ask us for thousands of INFO lines, and the outcome is already on the returned `TransitionResult`.

The level a condition reports at follows its volume, not its kind: a pre- or post-condition runs once per transition and belongs at DEBUG, while a choice's branch selectors run once per branch per action and belong at TRACE alongside the actions they select. `BoundCondition` carries the role, so the split is one branch at one seam rather than a rule spread over call sites.

**Logger names are virtual packages, not classes.** Implementation classes are concentrated in `core.impl` so they can see each other package-privately without widening the public surface, which makes the real package structure useless as a logging hierarchy — a host would get "all of Transflux" or "one class whose name we may refactor next phase". So logger names describe how the code *would* be divided if Java allowed cross-package internal access:

| Logger | Covers |
| --- | --- |
| `org.transflux.build.lifecycle` | build phase boundaries; the one completion line per build |
| `org.transflux.build.validation` | ref / context / cycle checks, id claims, definition-time overwrites |
| `org.transflux.build.registry` | scope population, parenting, flattening |
| `org.transflux.build.binding` | defs to bound records; what each id resolved to, and in which scope |
| `org.transflux.execution.transition` | lifecycle: state resolution, outcome, applier |
| `org.transflux.execution.action` | per-action dispatch, nesting, call-site mapping |
| `org.transflux.execution.condition` | pre / post / branch evaluation |
| `org.transflux.execution.compensation` | capture and drain |
| `org.transflux.execution.async` | executor lifecycle; forked-member submission and outcome |
| `org.transflux.execution.listener` | observer failures |
| `org.transflux.trigger` | dispatch scan, filters, gates |
| `org.transflux.trace.state` / `.transition` / `.action` | the execution trace, written only by the shipped logging listeners a host attached; declared in `core.logging.TraceLine`, the one other holder `LoggersSpec` admits |
| `org.transflux.yaml.source` | which definition source answered an identifier, and where a miss looked (`transflux-yaml`) |
| `org.transflux.yaml.parse` | which documents were read, from where (`transflux-yaml`) |
| `org.transflux.yaml.binding` | which def call each document entry became; type arguments left to the runtime check (`transflux-yaml`) |

The hierarchy gives both granularities: a host silences `org.transflux.execution` wholesale or `org.transflux.execution.action` alone, and `org.transflux` still covers everything. **Only leaves emit** — a name is either a grouping level or a logger, never both, so no line ever arrives from a parent category. The leaf is a *concern*, not a class: one class routinely spans several (`StateMachineImpl` alone carries transition execution, trigger dispatch, listener-failure reporting, and the compensation drain), which is why this is finer-grained than per-class naming rather than a compromise on it.

Declare loggers through the internal `Loggers` holder (`core.impl`) rather than scattered `getLogger("...")` string literals — one place to read the whole tree, no typos, and "does this line belong in that domain?" becomes a visible review question. Reference the constants at the call site (`Loggers.BUILD_VALIDATION.warn(...)`) rather than aliasing one back into a per-class `log` field, which would hide exactly that question. `LoggersSpec` enforces the tree's shape: every leaf under `org.transflux`, no leaf an ancestor of another, and no `LoggerFactory.getLogger` anywhere outside the holder. Name the emitting component in the message only when the domain does not already make it obvious.

The build phase boundaries all go to `build.lifecycle` rather than to the logger of the phase each announces. The point of those lines is that the last one emitted names the phase that threw; split across leaves, that only holds for a host who enabled every one of them.

The README carries a host-facing copy of the tree and the level policy. It is the surface a host configures, so treat it as public contract — when a leaf is added or its scope changes, update both files.

**Never log entity or context contents.** The entity belongs to the host and may be full of PII; so may the context. Log ids, class names, states, and paths — never `entity.toString()`, never a context dump, at any level. The same applies to exception messages, which surface wherever a stack trace is printed. A host that wants its own payloads logged does it through a listener, where the decision is the host's.

**Hot-path cost.** SLF4J's three-or-more-placeholder form is varargs and allocates an array at the call site whether or not the level is enabled. On the per-action and per-condition paths, keep statements to two placeholders or guard them with `isTraceEnabled()` / `isDebugEnabled()`.

**Format.** Message first, then comma-separated `key={}` pairs whose keys match the field or variable names, so logs stay greppable: `log.debug("Trigger skipped, triggerId={}, reason={}", id, reason)`. Always parameterized, never concatenated.

**Not in scope pre-1.0.** MDC keys, correlation ids, and a formally parseable record format are post-1.0 themes. The goal here is narrower: making it possible to understand how the framework behaved — troubleshooting a YAML definition, or a trigger that fired nothing.

## Conventions Specific to This Repo

- **Line endings: LF.** Enforced by recent refactor; do not let editors reintroduce CRLF on Windows.
- **Generics:** prefer `<T>` consistently for the entity type across paired `Def`/runtime interfaces — recent commits explicitly refactored for this consistency.
- **Commit messages:** Conventional Commits (`feat:`, `fix:`, `chore:`, `refactor:`, ...). See README §Contributing.
- **Tests:** Spock (Groovy 4.0 / Spock 2.3 — bump to 2.4 is scheduled for Phase 6.4). Co-locate a spec with each new core class; name it `<ClassName>Spec.groovy` so Surefire picks it up.
- **The DSL needs a Java caller: `src/test/java`.** Groovy cannot check the public API's Java ergonomics. It resolves overloads at runtime against an argument's actual class and coerces closures to whichever functional interface the chosen method wants, so a call javac rejects as ambiguous dispatches happily from a spec — which is exactly how an uncallable `run(id, lambda)` shipped. `org.transflux.dsl.JavaDslSurface` is a Java fixture holding every DSL call shape a host would write, with implicitly-typed lambdas and from outside `core.impl`; `maven-compiler-plugin` compiles it during `test-compile`, before the Groovy specs, so an ambiguous overload family, an uninferable generic signature or a type a host cannot reach fails the build there. `JavaDslSurfaceSpec` then drives it, so the shapes are proven wired and not merely legal. **When adding or changing a DSL overload — especially one taking a functional interface — add its call shape to that fixture.** `transflux-yaml` has a Java caller too: `ParityMachine` is one state machine written through the DSL, which `corpus/valid/parity/` declares again in YAML over the same classes, and `YamlDefinitionLoaderParitySpec` runs the two side by side. Two Groovy traps it also documents: a closure coerced with `as SomeInterface` implements *every* method of that interface, so `{ ... } as ContextMapper` overrides `mapFrom` rather than inheriting the no-op — harmless at a forked call site, which never writes back, but not the lambda a Java host would have written; and a spec asserting "this compiles for a host" proves nothing at all.
- **A listener or trigger shared by id is exercised in its own spec.** `StateMachineDefImplTriggerRegistrationSpec` and `StateMachineDefImplListenerRegistrationSpec` hold the registration, attachment and rejection cases for the two; the per-owner hook specs stay about the hooks. `JavaDslSurface.sharedTriggerShapes()` and `listenerRegistrationShapes()` are their Java call shapes, and both assert a delivery *sequence* rather than a count, so dropping one attachment fails them.
- **Spec naming for IDE navigation.** Every Spock spec name starts with its primary production class name, optionally followed by a feature topic, ending in `Spec` — e.g. `StateMachineImplSpec` (the default class-focused spec) and `StateMachineImplReentrancySpec` (one topic split out). This lets IDEA's *Navigate to Test* (`Ctrl+Shift+T`) surface every related spec by prefix-matching the prod class name. When behavior cuts across multiple classes, the prefix is the *primary* entry point — the class the reader is most likely to be in when they want to find the test.
- **Adding new types** to an existing subpackage is fine; introducing new top-level packages (or any `core.*` subpackage beyond the eight above — the seven semantic ones and `core.impl` — or any `yaml.*` package beyond `yaml` and `yaml.source`) requires updating both this file and the README's "Package Structure" section.
- **Cross-package visibility:** framework-internal types live in `core.impl` and stay package-private by default — siblings in `core.impl` can already see them. Promote to `public` only when the type's name appears in a public-API signature (a parameter, return, generic bound, thrown exception, or `permits` clause of a public sealed type in `core` or one of the seven semantic subpackages); in that case note `<p>This is framework-internal infrastructure; user code should not invoke it directly.</p>` in its JavaDoc. Do **not** promote merely to expose state across `core.impl` files — that's what the consolidated package is for.
- **Public JavaDoc.** Types in the public-API packages (`core` and the seven semantic subpackages) describe **publicly visible behavior** in their JavaDoc. Internal-impl types (`*Impl`, `Bound*`, `*Ref`, `ConditionResolver`, `SpelConditionEvaluator`, `ExpressionIdDerivation`, `ExecutingTransitionImpl`, `CompositeOperationExecutor`, etc.) are not mentioned unless the reference is unavoidable — i.e. it explains an otherwise-surprising behavior, motivates a non-obvious API choice, or names a symbol the caller will see in a stack trace or diagnostic. When in doubt, describe the observable effect, not the mechanism. Public-API JavaDoc may link to other public-API types freely.
- **Source comments and JavaDoc must be time-neutral.** Treat every comment and JavaDoc block in source files as if it has to survive unchanged until 1.0. Do not write phrases like "introduced in Phase 2 Step 1", "wired in Phase X Step Y", "per requirements §2.1.5", "preserves the Phase 1 no-op behavior", "in Phase 2 specs" — anything that ties the prose to a transient point in the build plan. Phase numbers, plan steps, and `requirements.md`/`todo.md` section pointers are scaffolding that decays the moment the next phase lands; the diff is the right place to capture that context (commit message, PR description, the plan file), not the source. **One narrow exception**: `TODO` markers that flag a known placeholder are fine, because their whole purpose is to be removed when the placeholder is filled in — but even then, the body of the TODO should describe what the placeholder needs to do, not the plan step that will do it (write `// TODO: pre-condition evaluation against view`, not `// TODO Phase 2 Step 5: pre-condition evaluation`). Exception messages and log strings follow the same rule, since they surface to users at runtime.
