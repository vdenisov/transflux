# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Transflux is a lightweight, embeddable microflow orchestration library (Java). It coordinates state changes for business entities — transitions, sequencing, pre-/post-conditions, triggers, listeners, and Saga-like compensations — without providing its own persistence. Project status: Phases 1 through 3 complete — all three listener categories, the manual / event / data trigger set, and the unified action model have landed. Phase 4 (Async Operations & Error Handling) is next. The public API is unstable.

`requirements.md` is the canonical spec for the vision and component model; consult it before designing new core abstractions. `todo.md` is the roadmap index (phase map, versioning policy, 1.0 contract, post-1.0 themes). Per-phase task breakdowns live one-file-per-phase: **remaining** phases under `docs/roadmap/`, **shipped** phases (verbatim) under `docs/history/`. A phase moves from `docs/roadmap/` to `docs/history/` when it ships. The toolchain/dependency/cadence baseline is in `docs/project-baseline.md`.

## Build & Test

- Toolchain: Maven builds with **JDK 17+** (enforced via `maven-toolchains-plugin`) and compiles to **Java 17 bytecode** (`<release>17</release>`). A JDK 17+ must be discoverable through `~/.m2/toolchains.xml`.
- Run all tests: `mvn -q clean test`
- Run a single Spock spec: `mvn -q test -Dtest=StateMachineImplSpec`
- Run a single feature method: `mvn -q test -Dtest=StateMachineImplSpec#"feature method name"`
- Coverage report (JaCoCo, generated during `test` phase): `target/site/jacoco/index.html`
- Surefire only picks up classes matching `**/*Spec` — Groovy/Spock specs in `src/test/groovy`. Plain JUnit tests would not be discovered without changing the include pattern.

## Architecture

The core domain is split into a public API surface (six semantic subpackages) and a sibling implementation package:
- `core` — `Transflux` entry point, the `StateMachine` / `StateMachineDef` interfaces, `ContextScope`, the `Identifiable` marker, and the `Preconditions` helpers (`requireNotNull` / `requireNotBlank`) static-imported by public-API types.
- `core.state` — `State` / `StateDef`, the host-supplied `StateResolver` / `StateApplier`, and the state-listener surface: `StateListener` (a functional `onState(entity, context, change)`), its `StateListenerDef` builder, and the `StateChange` payload record (`phase` / `state` / `transition`) with its `StatePhase` (`ENTRY` / `EXIT`) discriminator. Listeners attach per state through `StateDef.onEntry(id, ...)` / `onExit(id, ...)` and to every state through `StateMachineDef.onAnyStateEntry(id, ...)` / `onAnyStateExit(id, ...)`; each hook offers instance, class, and `Consumer<StateListenerDef<T>>` configurer forms plus their `Identifiable` siblings. Listener ids are required and form their own state-machine-wide namespace, claimed at declaration time — listeners do **not** enter `Registry` / `Component`, matching the trigger precedent.
- `core.transition` — `Transition` / `TransitionDef`, `TransitionResult`, `ActionPath` (qualified-id carrier exposed on `TransitionResult.executedPath` / `compensatedPath`), and the transition-listener surface: `TransitionListener` (a functional `onTransition(entity, context, execution)`), its `TransitionListenerDef` builder, and the `TransitionExecution` payload record (`phase` / `transition` / `firedBy` / `result`) with its `TransitionPhase` (`START` / `COMPLETE` / `ERROR`) discriminator. Listeners attach per transition through `TransitionDef.onStart(id, ...)` / `onComplete(id, ...)` / `onError(id, ...)` and to every transition through `StateMachineDef.onAnyTransitionStart(id, ...)` / `onAnyTransitionComplete(id, ...)` / `onAnyTransitionError(id, ...)`; each hook offers instance, class, and `Consumer<TransitionListenerDef<T, C>>` configurer forms plus their `Identifiable` siblings.
- `core.action` — `Action` (the single executable contract: `execute(entity, context, transition)` plus a default `getCompensation(entity, context)`), `ActionKind` (`STEP` / `OPERATION`, the authored form, carried for diagnostics only), `Compensation`, `ContextMapper`, and the def family: `ActionDef` base with `StepDef` (imperative — a Java body) and `OperationDef` (declarative — an ordered member list) as its two forms, plus `ConditionalOperationDef` and the per-branch sub-builders `BranchDef` / `DefaultBranchDef` / `NoMatchBehavior`, and `MapperDef`. Also the action-listener surface: `ActionListener` (a functional `onAction(entity, context, execution)`), its `ActionListenerDef` builder, and the `ActionExecution` payload record (`phase` / `path` / `kind` / `transition` / `error`, plus an `actionId()` reading the leaf off the path) with its `ActionPhase` (`START` / `COMPLETE` / `ERROR`) discriminator. Listeners attach per action through `ActionDef.onStart(id, ...)` / `onComplete(id, ...)` / `onError(id, ...)` — return-type narrowed on `StepDef` / `OperationDef` / `ConditionalOperationDef` — and to every action through `StateMachineDef.onAnyActionStart(id, ...)` / `onAnyActionComplete(id, ...)` / `onAnyActionError(id, ...)`; each hook offers instance, class, and `Consumer<ActionListenerDef<T, C>>` configurer forms plus their `Identifiable` siblings.
- `core.condition` — `Condition` and `ConditionDescriptor` (five-form sealed grammar: Reference, InstanceBased, ClassBased, PredicateBased — carrying a `BiPredicate<T, C>` over `(entity, context)`, with a `Predicate<T>` convenience overload on the DSL surface — and ExpressionBased).
- `core.exception` — `TransfluxException` and its subclasses.
- `core.trigger` — `Trigger` (runtime catalog view: id / name / description / transitionId) and its three public subtypes `ManualTrigger`, `EventTrigger` (adds `getEventId()`), `DataTrigger`; plus the def-side builders `ManualTriggerDef`, `EventTriggerDef` (`onEvent` + `filter`/`filterExpression`), `DataTriggerDef` (a single gate condition in the standard descriptor grammar). Triggers attach to transitions like pre/post-conditions. The catalog supports plain enumeration (`getTriggers()` / `getTrigger(id)`) **and** kind-based discrimination via `<X extends Trigger> getTriggers(Class<X>)` (return-type narrowed; selects on the subtype). Manual triggers fire through `entity(e).fire(id[, ctx])`; event and data triggers fire through the host-driven `entity(e).processEvent(eventId, eventData[, ctx])` / `processDataChange([ctx])`, which return a `ProcessResult<T>` (in `core.transition`, alongside `TransitionResult`) rather than a bare `TransitionResult` — these entry points may match nothing (`ProcessResult.fired()` / `result()` / `firedTriggerId()`; `fired()` does not imply success). For an event trigger, `eventData` is bound for filter evaluation only (SpEL: entity = root, payload = `#event`, context = `#context`) and is **not** the firing context; the first eligible filter-passing trigger fires. For a data trigger, the gate is evaluated against `(entity, context)` via a read-only probe view and the first eligible holding gate fires. Dispatch is first-match in declaration order among triggers on transitions leaving the entity's current state.

**Trigger dispatch invariants.** Three rules hold across both host-driven entry points, and new trigger kinds are expected to keep them. (1) `fire()` is manual-only — it rejects an event or data trigger id, because firing one directly would skip the filter or gate that kind exists to impose; the check is a seam on the internal sealed `TriggerImpl`, not a scattered `instanceof`. (2) Context compatibility is part of *eligibility*: `processEvent` / `processDataChange` skip a trigger whose transition would reject the supplied context and keep scanning, so a filter or gate never sees a context its own transition refuses, and a later compatible trigger still fires; the targeted `fire()` / `transitionTo()` keep throwing on the same mismatch, since they name one specific target. (3) The gate probe is a `TopologyTransition`, not a `TransitionView` — topology accessors answer, `run(...)` dispatch throws. That enforces the contract `Transition`'s JavaDoc already documents, and keeps a gate from running side effects outside the reentrancy guard with its compensations silently discarded. Filter and gate failures are wrapped with the offending trigger's id.

**Transition listener invariants.** (1) **`onComplete` and `onError` partition the outcomes**, and both pair with `onStart`: exactly one terminal notification follows every start, and neither occurs without one. A transition rejected by a pre-condition notifies nothing — it never reached the start hook, which §2.4 places *after* the pre-conditions. A pre-condition that *throws* lands in the same catch block as a failed operation, so a `started` flag gates the error hook rather than the catch itself. (2) **The payload carries the `TransitionResult`** the caller receives — the same instance, so a listener sees the executed path, the compensated path, the error, and the timings. It is `null` at `START`, and the record's compact constructor enforces the phase/result contract (`COMPLETE` ⇒ success, `ERROR` ⇒ failure). (3) **`firedBy` is the origin**, the `Trigger` that caused the execution or `null` for a direct `transitionTo`. It supersedes per-trigger listener bindings: a listener that should react to one invocation path branches on it. All three dispatch paths supply it, which is why `executeTransitionInternal` takes the firing `TriggerImpl` rather than a pre-extracted pre-condition list. (4) **The context is typed** (`TransitionListener<T, C>`) — a transition declares exactly one context type. Global registrations are the exception and take `Object`, since they span transitions that differ. (5) **Ordering mirrors the state rule**: the transition's own listeners first, then the global ones, declaration order within each group, merged onto `BoundTransition` at build time; a class-form global listener is bound once and shared. Interleaved with the state hooks, §2.4's ordering gives start → exit … complete → entry.

**State listener invariants.** (1) **Listeners observe; they never gate.** Each invocation is wrapped individually — a thrown `Exception` is logged at WARN and swallowed, so it does not fail the transition, does not trigger compensation, does not stop the listeners declared after it, and leaves `TransitionResult` untouched. Rejecting a transition is a pre-condition's job. (2) **Firing points are the two gaps in `executeTransitionInternal`**: the source state's exit hook runs once the pre-conditions have passed and before the operation; the target state's entry hook runs after the `StateApplier` has committed (and still fires when no applier is configured, since that is the commit point either way). Two consequences that are documented and tested: a transition rejected by a pre-condition notifies neither hook, and an exit notification does **not** imply the transition succeeded. (3) **The payload's transition is a `TopologyTransition`**, for the same reason the data-trigger gate gets one — a listener runs either before the operation or after the commit, so dispatched work would leave compensations that could never execute. (4) **The context is untyped (`Object`) by design**: a state can be entered from transitions carrying different context types, so there is no `C` to bind. That is the deliberate dividing line — a listener that needs a typed context belongs on a transition. (5) **Ordering is per-state listeners first, then global**, declaration order within each group, merged into a per-state index at build time; a class-form global listener is instantiated once and shared across states rather than once per state.

**Action listener invariants.** (1) **A listener attaches to the action, not to the call site.** It rides on the action's own def and fires at every invocation of that action — transition attachment, container member, conditional branch member, and by-id dispatch from another action's body. That is the rule compensation already follows, and it dissolves the question of how a by-id reference would carry an attachment: it does not have to. (2) **The single firing point is `TransitionView.runAction`**, the seam the action-model unification left behind, so every action notifies at every nesting depth in whichever form it was authored. The transition's root action therefore notifies at almost the same moment as the transition's own `onStart`; that near-duplicate is intended — a listener walking the execution tree wants the root node. (3) **The payload's `path` is the same `ActionPath` the invocation contributes to `executedPath`**, produced by one `qualifyActionPath` call that `runAction` reuses, so a listener lines its record up against the reported tree without reconstructing the nesting. Notification happens *inside* the nesting scope, so the path is the action's own. (4) **`mapFrom` runs after this action's notifications are closed.** A `mapFrom` failure is the parent's, and the child did complete, so it must not turn the child's `COMPLETE` into an `ERROR` as well — this is why the `mapFrom` call sits after the `try`/`finally` rather than inside it. (5) **`ERROR` fires at every enclosing level** as the failure propagates outwards, each reporting the same throwable, and the exception is rethrown unchanged so the transition still reports what actually failed. (6) **The context is the action's own** — the mapped child context at a mapped call site, i.e. the very object the body is handed, not the enclosing transition's. It is typed (`ActionListener<T, C>`); global registrations take `Object`. (7) **Globals are bound once on `StateMachineImpl` and appended at notification time**, rather than merged into each `BoundAction` the way transition listeners merge onto `BoundTransition` — one bound action is shared by every call site that reaches it, so merging would bind the same class-form global once per action. Ordering is still the action's own listeners first, then global, declaration order within each group. (8) **Observe-don't-gate and `TopologyTransition` carry over** from the other two kinds, and here the reasons are sharper: the hook sits in the middle of a live execution, so failing on an observer's behalf would compensate work the transition had no complaint about, and dispatched work would interleave into the executed path and the compensation stack as though the observed action had dispatched it.
- `core.impl` — framework-internal implementations: every `*Impl` (`StateMachineImpl`, `StateMachineDefImpl`, `StateImpl`, `StateDefImpl`, `TransitionDefImpl`, the sealed `TriggerDefImpl` base and its `ManualTriggerDefImpl` / `EventTriggerDefImpl` / `DataTriggerDefImpl` subtypes, the def-hierarchy bases `ConfigurableDefImpl` / `IdentifiedDefImpl`, the sealed `ActionDefImpl` base permitting `StepDefImpl` and `OperationDefImpl`, `ConditionalOperationDefImpl`, `BranchDefImpl`, `DefaultBranchDefImpl`, `MapperDefImpl`, `RegistryImpl`, `ContextScopeImpl`), the lookup machinery (`Registry`, `Component`), the bound-record / action-ref / mapper-ref infrastructure (`BoundAction`, `BoundCompensation`, `BoundCondition`, `BoundTransition`, the sealed `TriggerImpl` base and its `ManualTriggerImpl` / `EventTriggerImpl` / `DataTriggerImpl` subtypes, `EventFilter`, `ActionRef`, `MapperRef`, `InlineRegistrationSink`, `ResolvedContextMapping`, `ResolvedBranch`), the SpEL evaluation utilities (`ConditionResolver`, `SpelConditionEvaluator`, `ExpressionIdDerivation`), `StateListenerDefImpl` and its `BoundStateListener` runtime pairing, `TransitionListenerDefImpl` with `BoundTransitionListener` and the `BoundTransitionListeners` hook-list trio carried on `BoundTransition`, `ActionListenerDefImpl` with `BoundActionListener` and the `BoundActionListeners` hook-list trio (carried on `BoundAction` for an action's own, and once on `StateMachineImpl` for the globals) plus the `ActionListenerSink` backing every action-listener overload family, the runtime-internal `TransitionView` and its read-only sibling `TopologyTransition`, and the shared internal utilities (`ConditionDescriptorSink` backing every condition-descriptor overload family, `ValidationUtils` for the impl-only `warnIfSet` setter pattern, `InstanceOrClassSource` for the instance-XOR-class source pattern, `ThrowingUtils`, `ReflectionUtils`). User code should not depend on this package directly.

**Where the conditional's impl base diverges from its interface.** `ConditionalOperationDef` extends `ActionDef` — a conditional *is* a declarative action, differing from a plain container only in its "first matching branch" ordering rule. `ConditionalOperationDefImpl`, though, extends `IdentifiedDefImpl` rather than the sealed `ActionDefImpl`. That base's abstract hooks (`buildBound`, `checkRefs`, `bindScope`, `flattenScope`, `scanScopeFor`, `getScopeRegistry`) are the contract the SM build pipeline drives registered and transition-attached defs through, and a conditional is neither: it is constructed in exactly one place (`OperationDefImpl.conditional(...)`), only ever exists as an inline container member, and is built by `InlineRegistrationSink` through `buildBoundAction(conditionRegistry)` — a signature `buildBound(StateMachineImpl)` cannot express. Joining the sealed hierarchy would buy uniformity at the cost of one override that has to throw. Do not "fix" this either; if a conditional ever becomes registerable or transition-attachable, revisit it then.

**Action model.** There is one runtime type, `Action<T, C>`, and two authoring forms: a **step** is imperative (a Java body), an **operation** is declarative (an ordered member list whose executable the framework synthesizes). The distinction is what the author wrote, not what the runtime does — both execute through one path and dispatch identically. `BoundAction(id, action, kind)` carries the form so diagnostics can name it; `ActionKind` never selects a runtime path, and if it ever starts to, the split has been reintroduced under a new name. Any action attaches to a transition, in either form. See [docs/design/action-model-unification.md](docs/design/action-model-unification.md) for why the previous `Step` / `Operation` split was collapsed.

**One execution path.** Every action reaches the runtime through `TransitionView.runAction`, whether it is a container member, a by-id reference from inside another action's body, or the action attached to the transition itself. The order is fixed: capture the compensation and push it → record the id on `executedPath` → push the id onto the operation-nesting stack → execute → pop. Capturing and recording *before* the nesting push puts both at the action's own qualified path rather than one level beneath it. Recording before `execute` means a throwing action still appears on `executedPath`, which keeps it consistent with `compensatedPath`. Pushing the nesting stack for every action means anything it dispatches is qualified underneath it, so the reported tree matches the tree that ran at every level rather than only at container boundaries.

**Verbs split by call-site category, not by callee kind.** A **reference** names an action registered elsewhere and uses `run(...)` everywhere it can appear — container member, branch member, transition attachment, and dispatch from inside an action body. The overload count follows the position, not the verb: a container member and a dispatch from an action body carry all 8 (bare id, registered mapper id, inline `Function`, inline `ContextMapper`, plus the `Identifiable` and mixed siblings), because those are the positions that can cross a context boundary; a branch member and a transition attachment carry 2 (`run(String)` / `run(Identifiable)`), since neither takes a mapper. A **declaration** brings a new action into existence at that position and keeps the nouns: `step(...)` imperative, `operation(...)` declarative, `conditional(...)` for the first-matching-branch variant. Declaration cannot collapse to one verb — `action(String, Consumer<StepDef>)` and `action(String, Consumer<OperationDef>)` erase to the same signature — so the asymmetry is forced by the language, not chosen. Do not "fix" it.

**Definition vs. runtime split** — every concept has paired types:
- `*Def` interfaces + `*DefImpl` classes — fluent builders that capture configuration (states, transitions, operations).
- Runtime interfaces (`StateMachine`, `State`, `Transition`, `Operation`) + `*Impl` — immutable instances produced by calling `build()` on the definition.

Read a `*Def` to understand the DSL surface; read the matching runtime interface to understand execution semantics.

**Entry point.** `Transflux.defineStateMachine()` returns a `StateMachineDef<T>`. The builder chain (`forEntityType` → `withStateResolver` → `withStateApplier` → `state(...).transitionsTo(...)` → `build()`) produces a `StateMachine<T>`. The state machine itself is parameterized only by entity type — context lives at the transition level, not the SM level.

**Per-transition context.** Each `TransitionDef<T, C>` carries its own context type `C`. There are three ways to set it: (1) `StateDef.transitionsTo(target, id, Class<C>, configurer)` pre-binds the context inline during the state declaration; (2) calling `.usingContext(Class<C>)` on the transition def inside its configurer re-types it; (3) the pass-through `StateDef.transitionsTo(target, id, configurer)` defaults the transition to `Object.class` (accepts any non-null context, also accepts `null`). `Void.class` is a sentinel — a transition declared with `Void` context rejects any non-null firing value at the dispatch boundary in `StateMachineImpl`. SM-level reusable components (steps, conditions, operations, mappers) are registered without a context constraint (`step(id, Action<T, ?>)`), or with an explicit context tag via the typed overloads (`step(id, Class<C>, Action<T, C>)`, `operation(id, Class<C>, Consumer<OperationDef<T, C>>)`) or grouped under a `forContext(Class<C>, scope -> ...)` block. Note the asymmetry: a step registers from an instance or a class, so it has both untyped and typed forms; an operation is only ever declared through a configurer, so it has the typed form alone. The typed registrations expose a `contextType()` accessor on the component's def (`StepDef.contextType()` / `OperationDef.contextType()` / `MapperDef.parentType()` / `childType()`); a fallback `componentContextTypes` map on `StateMachineDefImpl` covers untyped overloads. The build-time context-compatibility check runs from `StateMachineDefImpl.validateContextCompatibilityAndCycles` into each def's `ActionDefImpl.checkRefs`, which walks the container's `ActionRef` list — descending into `ActionRef.Conditional` to reach branch members — and validates that pass-through references are assignment-compatible and that any supplied mapper's `parentType` / `childType` align with the call site. Existence of a branch member's id is a separate post-construction pass (`StateMachineDefImpl.validateBranchRefs`), because a conditional's bound action is registered into the very scope its branches resolve against.

**Typed condition-registration names.** On `StateMachineDef`, typed-context registrations of the lighter condition forms use distinguishing names — `conditionPredicate(id, Class<C>, BiPredicate|Predicate)` and `conditionExpression(id, Class<C>, String)` — because Java erasure makes them indistinguishable from `condition(id, Class<? extends Condition<T,C>>)` at the call site. Untyped forms keep the single `condition(...)` name; instance and class typed forms also stay as `condition(id, Class<C>, ...)`. The asymmetry is a forced consequence of erasure, not a design preference. Inside `forContext(...)` blocks, the typed context is carried implicitly by the scope, so `ContextScope` registrations use the single `condition(...)` name across all four lighter forms.

**One lambda-shaped overload per name.** The rule behind the naming above generalises, and it is the reason `mapperDef(...)` is not called `mapper(...)`: two overloads whose functional-interface parameters share a descriptor cannot be told apart when the argument is a lambda, and neither an explicitly-typed lambda nor most-specific-method resolution breaks the tie — only a cast does. `ContextMapper<P, N>` and `Function<P, N>` are both `(P) -> N`, which is why the `Function` registration overload was removed rather than kept, and `Consumer<SomeDef>` collides with any of them for the same reason. When adding an overload whose parameter is a functional interface, check what else lives under that name first.

**Why there is no `ConditionDef`, and no `Describable`.** Both were proposed in the component-metadata work and both were closed as decisions rather than as code. `ConditionDef` would add a name and a description that nothing reads — there is no `Condition` runtime view, no condition catalog, and no payload carrying one — and making the metadata reach runtime means widening all five `ConditionDescriptor` records plus `BoundCondition`, then mirroring the resulting overload family across six defs. `Describable extends Identifiable` would collapse the per-interface `getName()` / `getDescription()` declarations into a super-type with no behaviour change and no polymorphic consumer: every listener payload reads metadata off a concrete type or carries the fields flat. Both are parked against the YAML work, which is the first thing that might genuinely walk defs polymorphically; reintroducing either then is additive. Do not add them speculatively.

**Null ctx for Object-typed components from Void callers.** When a container member or `view.run(...)` dispatches an `Object.class`-typed component from a `Void.class`-context caller, the component's `ctx` parameter receives `null` at runtime. The build-time pass-through check admits this unconditionally — `Object.class` components always pass through, regardless of caller context. Component bodies registered under `Object.class` must tolerate `null` ctx; the canonical reason to register under `Object.class` is "this component ignores ctx," which the null-tolerance follows from.

**Call-site context mapping.** Mapping is a property of the *call site*, not the callee. `ContextMapper<P, N>` is a first-class reusable component (`mapper(id, P, N, instance|class)` on `StateMachineDef`, plus `mapperDef(id, P, N, Consumer<MapperDef<P, N>>)` when the registration also wants a name or description) with a default no-op `mapFrom`. `ContextMapper` has a single abstract method, so a lambda *is* the instance form — it supplies `mapTo` and leaves `mapFrom` the no-op. There is deliberately no `Function<P, N>` registration overload: it would be indistinguishable from the instance form at the call site while meaning the same thing. Every by-id reference — `.run(id, ...)` on a container or branch, and `view.run(id, ...)` from inside an action body — accepts the same forms: pass-through (no mapper), mapper by registered id, inline `Function<C, ?>` (wrapped with default no-op `mapFrom`), or inline `ContextMapper<C, ?>` instance. The class form is registry-only — Java erasure collides with inline-class action declaration. Inline-declared members (`step(id, Action<T, C>)` and its class variant) are typed against the container's own `C` and always run pass-through. `MapperRef` is a sealed type capturing the unresolved call-site choice; `OperationDefImpl.buildBound(stateMachine)` resolves each `MapperRef` to a `ResolvedContextMapping` via the SM's mapper registry. Failure attribution: `mapTo` and `mapFrom` failures both surface as parent failures (the boundary belongs to the parent). A `mapTo` failure throws before the child starts, so nothing is recorded and no compensation is captured for it; a `mapFrom` failure throws after the child completed, and the child's compensations still run — compensation capture precedes execution and the enclosing transition drains the whole stack on any failure. Idiomatic mapper id: `<child>-from-<parent>` (e.g. `billing-from-send`, `payment-from-order`) — reads naturally at call sites and makes the boundary direction obvious.

**State accessor pair.** `StateResolver<T>` extracts the current state ID from a domain entity (read side); `StateApplier<T>` writes the new state ID after a successful transition (write side). The applier is optional — purely transient transitions, or hosts that mutate state inside steps, can omit it. Transflux never owns storage; both interfaces are host-supplied bridges. When the entity's state is an enum implementing `Identifiable`, the canonical pairing is `.withStateResolver(e -> e.getStatus().name())` / `.withStateApplier((e, s) -> e.setStatus(MyState.valueOf(s)))` — two short lambdas, honest about where the bidirectional binding lives. The framework intentionally ships no sugar around this; the host owns how state is stored.

**Identifiable.** Identity lives on the **definition** side. The `*Def` types (`StateDef`, `TransitionDef`, `ActionDef` and its `StepDef` / `OperationDef` forms, `MapperDef`, the `step(id, ...)` / `condition(id, ...)` / `operation(id, ...)` / `mapper(id, ...)` registrations on `StateMachineDef`, plus `ConditionDescriptor`) carry a stable `id` (used for lookup) and optional `name` / `description`. The runtime executable contracts (`Action<T, C>`, `Condition<T, C>`, `ContextMapper<P, N>`) are pure functional interfaces with no identity — the same class can be registered any number of times under different ids. At runtime the framework carries internal bound records (`BoundAction`, `BoundCondition`, `BoundCompensation`) that pair the executable with the framework-owned id; diagnostics and `executedPath` / `compensatedPath` pull from the bound side. The container executor wraps each bound member in an internal `CompositeMember(BoundAction, ResolvedContextMapping)` record that carries the resolved per-call mapping alongside the bound action; pass-through members carry `ResolvedContextMapping.passThrough()`. Per `requirements.md` §2.2.1, ids are required and must be unique within their scope; only **inline expression-based condition descriptors** may omit `id` and have one auto-derived from expression + descriptor path.

**Reentrancy guard.** `StateMachineImpl` carries a static `ThreadLocal<Set<EntityKey>>` that tracks in-flight transitions on the current thread, keyed by reference identity of `(StateMachineImpl, entity)`. A transition that calls back into the same SM with the same entity (from inside an operation, step, condition, or future listener) throws `TransfluxReentrancyException`. Different-entity reentrant calls are permitted. Phase 4 async will extend the guard across the async-submission boundary via capture/restore — the TODO at the TL declaration marks that future seam.

**Exception hierarchy.** All Transflux-thrown exceptions derive from `TransfluxException` (unchecked) and live in `org.transflux.core.exception`. `TransfluxValidationException` covers definition, builder, and lookup errors — raised synchronously. `TransfluxReentrancyException` is raised by the reentrancy guard described above.

**TransitionResult.** Transition execution returns a `TransitionResult<T>` rather than throwing on business outcomes — failures from invalid configuration still throw `TransfluxValidationException`. `TransitionResult` carries: success flag, source/target state, transition ID, error, executed-step IDs, compensated-step IDs, started/completed timestamps. The firing-time context object is not stored on the result; callers that need it already have it on their side of the call. There is no forced-state API (host owns initial-state placement).

**Compensation.** Any action optionally declares a `Compensation<T, C>` via `Action.getCompensation(entity, context)` — captured **before** `execute` runs and pushed onto the per-execution LIFO stack carried by `TransitionView`. If `execute` throws (its own or a later action's), the enclosing transition catch drains the stack in LIFO order. Capturing before execute is deliberate: an action that throws partway through producing side effects (e.g., creating remote entities in a loop) still has its rollback handler available. The completion-time-snapshot pattern stays expressible by writing the snapshot into the entity or context during `execute` and reading it back in the compensation. A declarative container is pushed on entry, before it dispatches anything, so its own compensation and its members' all run and unwind members-first — the container's is additive, not a replacement. Phase 4 adds the static def-side `withCompensation(...)` and exception-specific routing; today only the dynamic hook exists, and a synthesized container returns `null` from it.

**DSL Shape.** Lambda-configurer is the single declaration shape for every Def that owns children — states (`StateMachineDef.state(id, s -> ...)`), transitions (`StateDef.transitionsTo(target, id [, Class<C>], t -> ...)`), declarative containers (`operation(id, op -> ...)`), conditionals (`conditional(id, cs -> ...)`), branches (`branch(id, b -> ...)`), imperative actions (`step(id, a -> ...)`), and the SM-level grouping block (`forContext(Class<C>, scope -> ...)`). The configurer is the *only* place to declare children: once it returns, the def reference is inert and any further mutation throws `TransfluxValidationException`. To declare another state or build the SM, return from the lambda and continue on the enclosing `StateMachineDef`.

The scope guard applies to **every** def passed to a user lambda — `StateDef`, `TransitionDef`, `OperationDef`, `StepDef`, `ConditionalOperationDef`, `BranchDef`, `DefaultBranchDef`, the `forContext` `ContextScope`, the three `*TriggerDef` kinds, `MapperDef`, `StateListenerDef`, `TransitionListenerDef`, and `ActionListenerDef` — not just the top two. New defs added in later phases are expected to follow the same rule. The guard machinery lives on two abstract bases in `core.impl`: id-bearing defs extend `IdentifiedDefImpl` (which carries `id` + `name` + `description` + the `withName`/`withDescription` setters on top of the guard); id-less guarded defs — `ContextScopeImpl` (keyed by context type), `BranchDefImpl`, `DefaultBranchDefImpl` — extend `ConfigurableDefImpl` directly. A parent runs a child's configurer through `ConfigurableDefImpl.runConfigurer(child, configurer)`, which flips the guard active for the duration of the lambda; each `defLabel()` (`"step 'x'"`, `"operation 'x'"`, `"conditional operation 'x'"`, `"branch 'x'"`, `"default branch"`, `"mapper 'x'"`, `"forContext scope for X"`) names the offending def in the rejection message.

For one-off SM-level component registrations the flat overloads stay alongside `forContext` — `smd.step(id, Class<C>, ...)` / `smd.condition(id, Class<C>, ...)` / `smd.operation(id, Class<C>, ...)` / `smd.mapper(id, P, N, ...)` / `smd.mapperDef(id, P, N, ...)` are meaningfully more compact than wrapping a single registration in a one-line block. `forContext(Class<C>, scope -> ...)` is the right shape for *groups* of components sharing a context; the flat form is the right shape for *one-offs*. Both forms populate the same registry — stylistic choice, not semantic, and the two routes share one registration path per component kind. The scope carries the same configurer forms the flat overloads do (`scope.step(id, cfg)` alongside `scope.step(id, instance|class)`), so choosing a `forContext` block never costs the ability to name a component or attach listeners to it.

**`forContext` vs `usingContext`.** The verbs split the semantics: `forContext(C, scope -> ...)` on `StateMachineDef` **opens a grouping scope** ("for context C, register these"); `usingContext(C)` on `TransitionDef` / `OperationDef` is a **property setter** ("this transition / operation uses context C").

**Component resolution and lexical visibility.** Every `StateMachineImpl` owns one root `Registry<T>` populated with SM-level actions, conditions, and containers. Every `OperationDefImpl` owns its own `Registry<T>` whose parent is the enclosing scope's registry (root today; a process-wide registry once Phase 6.2 lands). Inline-declared members — `op.step(id, ...)`, conditionals declared inside it, and inline actions inside those conditionals — register into the container's scope, not into the root. Ids are still **globally unique** across the SM (the build pipeline maintains a per-build canonical-payload table; same instance / same class under the same id is idempotent, anything else is rejected at build time). What is *not* global is **visibility**: a container's inline id is reachable only from inside that container's subtree (its own member references, conditional branches, and any `view.run(id)` issued while the container is executing). Sibling containers cannot resolve another's inline ids — referencing one is a build-time error. SM-level ids are reachable from every container via the parent-chain walk. At the end of construction every registry is `flatten()`-ed so runtime resolution is a single map lookup; `Registry.parent()` stays in place as a public introspection accessor. `TransitionView` carries an active-scope stack: the container executor pushes its scope on entry to `execute`, pops on exit; `view.run(id)` consults `activeScope().resolve(id)` (falls back to the SM root when the stack is empty).

**`Identifiable` overload parity.** Every DSL method that takes a `String id` exposes an `Identifiable` sibling overload that delegates via `.getId()`. The Identifiable overload is a one-line delegate with a `requireNotNull` guard; behaviour and error messages otherwise match the String form. The point is twofold: callers can tag ids with enum constants (`enum State implements Identifiable { TRIAL, ACTIVE; @Override String getId() { return name(); } }`) for compile-checked refactoring at every reference site, and they can pass a held-onto `*Def` reference verbatim wherever an id is expected (every `*Def` already extends `Identifiable`). **New DSL methods added in later phases follow the rule** — when adding a `String id` parameter to a new method, add the `Identifiable` sibling at the same time. Two narrow exceptions live in the current surface: `addEventTrigger(Identifiable event)` uses its single argument as **both** the event id and the trigger id, so a bare single-arg trigger-id form (id only) would collide — callers wanting a distinct trigger id pair the trigger Identifiable with an event arg (`addEventTrigger(Identifiable trigger, Identifiable event)` / `(Identifiable trigger, String eventId)`); and the four `ConditionDescriptor.{instanceBased,classBased,predicate,expression}` factories take a String id as the *new* descriptor's id rather than a reference — only `ref(Identifiable)` exists. Disambiguating null at a call site (Java sees both `(String)` and `(Identifiable)` as applicable) requires an explicit cast: `td.preCondition((String) null)`.

## Conventions Specific to This Repo

- **Line endings: LF.** Enforced by recent refactor; do not let editors reintroduce CRLF on Windows.
- **Generics:** prefer `<T>` consistently for the entity type across paired `Def`/runtime interfaces — recent commits explicitly refactored for this consistency.
- **Commit messages:** Conventional Commits (`feat:`, `fix:`, `chore:`, `refactor:`, ...). See README §Contributing.
- **Tests:** Spock (Groovy 4.0 / Spock 2.3 — bump to 2.4 is scheduled for Phase 6.4). Co-locate a spec with each new core class; name it `<ClassName>Spec.groovy` so Surefire picks it up.
- **Spec naming for IDE navigation.** Every Spock spec name starts with its primary production class name, optionally followed by a feature topic, ending in `Spec` — e.g. `StateMachineImplSpec` (the default class-focused spec) and `StateMachineImplReentrancySpec` (one topic split out). This lets IDEA's *Navigate to Test* (`Ctrl+Shift+T`) surface every related spec by prefix-matching the prod class name. When behavior cuts across multiple classes, the prefix is the *primary* entry point — the class the reader is most likely to be in when they want to find the test.
- **Adding new types** to an existing subpackage is fine; introducing new top-level packages (or any `core.*` subpackage beyond the eight above) requires updating both this file and the README's "Package Structure" section.
- **Cross-package visibility:** framework-internal types live in `core.impl` and stay package-private by default — siblings in `core.impl` can already see them. Promote to `public` only when the type's name appears in a public-API signature (a parameter, return, generic bound, thrown exception, or `permits` clause of a public sealed type in one of the six semantic subpackages); in that case note `<p>This is framework-internal infrastructure; user code should not invoke it directly.</p>` in its JavaDoc. Do **not** promote merely to expose state across `core.impl` files — that's what the consolidated package is for.
- **Public JavaDoc.** Types in the public-API packages (`core` and the six semantic subpackages) describe **publicly visible behavior** in their JavaDoc. Internal-impl types (`*Impl`, `Bound*`, `*Ref`, `ConditionResolver`, `SpelConditionEvaluator`, `ExpressionIdDerivation`, `TransitionView`, `CompositeOperationExecutor`, etc.) are not mentioned unless the reference is unavoidable — i.e. it explains an otherwise-surprising behavior, motivates a non-obvious API choice, or names a symbol the caller will see in a stack trace or diagnostic. When in doubt, describe the observable effect, not the mechanism. Public-API JavaDoc may link to other public-API types freely.
- **Source comments and JavaDoc must be time-neutral.** Treat every comment and JavaDoc block in source files as if it has to survive unchanged until 1.0. Do not write phrases like "introduced in Phase 2 Step 1", "wired in Phase X Step Y", "per requirements §2.1.5", "preserves the Phase 1 no-op behavior", "in Phase 2 specs" — anything that ties the prose to a transient point in the build plan. Phase numbers, plan steps, and `requirements.md`/`todo.md` section pointers are scaffolding that decays the moment the next phase lands; the diff is the right place to capture that context (commit message, PR description, the plan file), not the source. **One narrow exception**: `TODO` markers that flag a known placeholder are fine, because their whole purpose is to be removed when the placeholder is filled in — but even then, the body of the TODO should describe what the placeholder needs to do, not the plan step that will do it (write `// TODO: pre-condition evaluation against view`, not `// TODO Phase 2 Step 5: pre-condition evaluation`). Exception messages and log strings follow the same rule, since they surface to users at runtime.
